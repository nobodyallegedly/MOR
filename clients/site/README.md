# mor-site

Websites on MOR (roadmap step 10a), in TypeScript, with the core library through WebAssembly: the website cMIP (`cmips/cmip-website-draft-3.md`, draft 3), a gateway that serves the sites its operator chose, each at its addresses, and the command line. `dubsar.org` is the first site (`docs/dubsar.org/`).

## In plain words

A site is a few files: pages, a stylesheet, pictures. Its owner publishes a list of them, each with its fingerprint, signed with their identity, on relays, exactly as a release of the code is published. Nothing is ever updated: a new version is a new list, naming the one before.

A gateway stands at the domain. It carries the sites its operator chose, and no others; the address a browser asks for says which. For each site it fetches a version from the relays and checks all of it: the owner's identity chain, the list, every file. Only then does it serve it. Which version: for a site someone else publishes, by default, the publisher's latest, since when their content changes is their call; for the operator's own sites, as the operator sets, following the latest or pinned to one version (which guards against a stolen key). With no clock, "latest" is read from the versions themselves: each names the one before, so the gateway follows the line from the version it was given, every few minutes; where two versions name the same one, it stops before them and says so. And it never sends a page on its own: at every address of the site it sends the same small program, the display client, which runs in the visitor's browser with MOR's core library. The display client checks again, for the visitor: who signed this site, and whether the page the gateway handed over is exactly the page they signed. It says so in a bar above the page. A page that does not match is not shown.

Whatever version the gateway serves, the display client looks for later ones itself, after showing the page, and says when a newer one exists.

The display client is the gateway's code, not the site's, so a hostile gateway could change it. Nothing a page does can rule that out. What is done about it: the display client is the same for every site, not minified, and released as MOR's code, its built files in the release (`built/`), so anyone can compare what a gateway serves with the release from another machine (`mor-site check`); its build is reproducible, so anyone can also rebuild those files from the source and get the same bytes; and every byte of a site can be checked with no gateway at all (`mor-site verify`).

Pages are for reading. No script in a page ever runs, and a page loads nothing from anywhere else: only its own stylesheets and pictures, as bytes already checked. To show an act (the first act, on dubsar.org's front page), a page names it, and the display client fetches it and judges it on its own, as the reader does, and lists it in the bar with its signer.

## Precisely

| File | What |
| --- | --- |
| `src/manifest.ts` | The site manifest: encoding, strict decoding, paths and their kinds, addresses both ways, references within a page. |
| `src/verify.ts` | What counts as a version (cMIP, "What counts as a version", "Verifying"): the publication, the signer's chain and the publication's standing, the identity expected, not a collective (until Law draft 7 is approved), no withdrawal found, the manifest; a file checked from any source. Runs on the server, on the command line and in the browser. |
| `src/latest.ts` | Later versions (cMIP, "Later versions"): the signer's site publications found at the places asked, each with the version its manifest names as previous; from a version, its successors, each checked in full, followed while there is exactly one; a fork stops it. Runs on the server (a gateway following) and in the browser (the newer-version notice). |
| `src/publish.ts` | Publishing a version from a folder: the files checked first (paths, kinds, a front page, JPEGs stripped, UTF-8), unchanged files reusing the previous version's objects, the publication first, then the manifest and the new files. |
| `src/gateway.ts` | The gateway's server: the sites it carries, by host name, any other address answered with "no site"; for each, the version to serve checked before serving it (pinned, or the latest followed); the display client at every address, the settings of that site at `/_mor/site.json`, the display client's files at `/_mor/`, and the site's files only as bytes at `/_mor/file/PATH` (`application/octet-stream`, `attachment`). |
| `src/settings.ts`, `src/headers.ts` | The gateway's settings (`listen`, `release`, `look`, and `sites`, each with `hosts`, `identity`, `name`, `relays`, `version` and `serve`: `latest` by default, or `pinned`), checked; the headers of every answer, with the content security policy. |
| `src/released.ts`, `built/` | The display client as published in the release (cMIP rule 20a): its four built files, and `BUILT-WITH.txt`, the versions of the tools that built them and each file's work hash. A gateway serves `built/` by default; `mor-site check` compares with it by default. |
| `src/shell/` | The display client: `app.ts` (the flow, the page's frame as tall as the page so nothing scrolls inside it, the tab's icon, then the look for later versions), `page.ts` (a page made ready: code and references to elsewhere dropped, pictures and stylesheets replaced by their checked bytes, links rewritten, acts boxed, the page's icon kept as checked bytes for the tab), `view.ts` (the bar and the styles; on a narrow or short screen, a phone, the bar's top sentence gives way to a brief one, "Verified: signed by" and the name, with everything else under "Who signed it, and how to check" as on every screen), `cannot.ts` (when the display client cannot run: the browser blocks WebAssembly, or the core library does not start; the bar says why and how to see the site, and nothing is shown). |
| `src/web/core.ts` | The core library in the browser, loaded from `/_mor/` whatever the page's address; if it cannot start, `cannot.ts` says so, and after twenty seconds still loading, the bar says a slow connection can take a minute. |
| `src/cli.ts` | `mor-site publish`, `verify`, `check`, `gateway`, `strip` (`npm run cli -- help`). |
| `scripts/marks.ts` | Draws dubsar.org's marks (`docs/marks/*.svg`) as the JPEGs the site holds: the clay tablet on the page's light and dark colours, and the KI icon (`node --import tsx scripts/marks.ts`). A site holds no SVG (cMIP rule 4). |
| `scripts/first-screen.ts` | Screenshots of dubsar.org's first screen on a phone (390 × 844, and 390 × 664 as Safari leaves it), light and dark, and held sideways, with where each part sits (`node --import tsx scripts/first-screen.ts <folder>`; WebKit with `MOR_BROWSER=webkit`). |
| `scripts/build.ts` | Builds the display client into `dist/` (not minified), or with `--release` (`npm run release`) into `built/`, recording the tools. The build fails if anything from Node reaches the bundle. Reproducible: the bundle's paths are relative to this folder, and the WebAssembly is built by `../genesis/scripts/build-wasm.sh` with the build machine's folders replaced by fixed names. |
| `gateway.example.json` | Settings to copy and fill in. |

It reuses the genesis client (identities, the relay transport, looking an identity up), the barebone client (reading a post, rendering it), the long-form client, the web reader's browser helpers and wording of standings, and the JPEG Module (stripping).

## Decided (Nobody, allegedly, 1 October 2026)

Draft 1's five main questions, written into the cMIP's draft 2 and built:

1. **What a page may be:** HTML with no scripts. Styling may move or hide words, so a site page is never terms: anything signed is shown as plain text in a client (cMIP rules 11, 15).
2. **Who supplies the checking code:** MOR's own released display client, the same for every site, "to keep it all in check" (rule 20).
3. **The display client in the release: both.** Its built files are published in the release (`built/`), and its build is reproducible: the compiled core library no longer carries the build machine's folder names, and two builds in two folders give identical bytes (rule 20a; `test/build/reproducible.test.ts`).
4. **Which version a gateway serves: set per site.** A site others publish follows the publisher's latest signed version by default; the operator's own sites are set as the operator wishes (pinning guards against a stolen key); any other arrangement is a deal between operator and publisher (rule 23). The display client always looks for later versions and says when a newer one exists (rule 24).
5. **A collective's site:** allowed once Law draft 7 is approved, published by whoever holds the collective's Envelope lane, as its releases are ("What counts as a version", rule 3). Until then the code refuses it, saying so. And **a gateway carries only the sites its operator chose**; a publisher refused by one carries their site elsewhere (rule 22).

## Leans taken, to check at the end of the roadmap

Draft 1's other five questions. Their leans are built and taken as they stand, so that the work goes on; listed here for Nobody, allegedly, to check at the end of the roadmap, like the readings of the Law redraft.

6. **The first act on the front page** is shown as the act itself (`<mor-act act="…">`), fetched and judged on its own with its own signer and standing, not copied into the site. *The other way:* a copy of its words and picture in the site, with a link to the act.
7. **The gateway's server is in TypeScript,** running the very same checking code as the browser half. *The other ways:* the server in Rust, or built into `mor-relay` as the management page is.
8. **The reader's own code** gets the same settlement as the display client: released code anyone can compare with its release. Say so in the reader's README and teach `mor-site check` to compare a reader too. *Not done in this window. The other way:* leave the reader's reading 12 as it is.
9. **The footnote's email address,** a placeholder for now, becomes the address the reader already shows, until a dubsar.org one exists, so the two never disagree. *The other way:* only the reader's message over MOR.
10. **The site lives in the repository at `docs/dubsar.org/`,** beside the documents it leads to. *The other way:* a folder of its own at the top.

## Open in draft 2: where the decisions are silent

Building the decisions raised these. Each is built on its lean so that it can be tested; **none is settled until you say so.**

- **D1. What "latest" means, with no clock.** *Plain words:* the decision says a gateway follows the publisher's latest version; MOR has no clock, so something must say which is latest. *Options:* (a) the end of the line of versions naming each other, followed from the version the operator named, each checked in full; a fork stops it (cMIP "Later versions"; built); (b) the version furthest along the publisher's sequence of acts: but an owner may keep several sequences, one per device, with no order between them; (c) a new signed act by which the owner names their current version. *Lean:* (a). It needs nothing new: versions already name the one before, as routes acts do.
- **D2. What a following gateway does at a fork** (two versions, both signed by the owner, naming the same one). *Options:* (a) serve the last version before the fork, and say so to the operator, and to the visitor through the display client (built); (b) serve nothing of the site until the owner settles it; (c) keep serving whatever it served before. *Lean:* (a): the site stays up at a version nobody disputes, and the fork is shown, not hidden.
- **D3. How often a following gateway looks for later versions.** *Options:* (a) every `look` seconds, 600 by default, set by the operator, and on reload (built); (b) holding a request open at each relay (the feed's `wait`), so that a new version is served at once; (c) only when the operator reloads. *Lean:* (a) now, (b) later if a delay of minutes matters.
- **D4. Which Rust the reproducible build uses.** *Plain words:* the same source gives the same bytes only with the same compiler. *Options:* (a) record the tools in `built/BUILT-WITH.txt`, and the build test says when a machine's differ (built); (b) also pin the Rust version for the whole repository (`rust-toolchain.toml`), so every machine builds with it, downloading it if needed; (c) pin it only for the WebAssembly build. *Lean:* (a) now, and (b) before the first real release (step 17), since anyone must then be able to rebuild what was released.
- **D5. Whether a collective must adopt the website cMIP before publishing a site.** Releases name the release manifest cMIP as an extension (terms field 15). *Options:* (a) no: a site's version is an Envelope publication, in the Envelope lane; its manifest is a format, as a JPEG is (written in rule 3); (b) yes, as an extension, adopted in the Production lane first. *Lean:* (a), which is what "published by whoever holds the Envelope lane" says.
- **D6. A collective whose agreement gives no one the Envelope layer.** Law draft 7 (rule 36a): an act no area reaches counts on the collective's own signature. So such a collective's site needs only its key. *Options:* (a) as Law draft 7 says (written in rule 3); (b) ask for members' signatures anyway. *Lean:* (a): this cMIP adds no rule of its own to Law.
- **D7. Whose site is "the operator's own".** The decision gives a different default to others' sites and to the operator's own; the gateway cannot tell which is which, so the default is the same for both, `latest`, and the operator sets `pinned` where they wish. *Options:* (a) as built; (b) a setting naming the operator's identity, with `pinned` the default for its sites. *Lean:* (a): following is the default the decision names; pinning one's own site is a choice to make, not a default.
- **D8. The newer-version notice:** a line under the top sentence of the bar, in bold, naming the newer version; it does not link to it, since this gateway does not serve it. *Options:* (a) as built; (b) a link that opens the newer version through the reader or another gateway. *Lean:* (a).
- **D9. Onion addresses for the server's homes** (the relay change). A home whose test operator it holds signs the operator's next routes naming the new address; a home whose operator was made elsewhere signs none, since two signers could fork the routes, and the operator publishes them from where its identity is kept. *Found:* the genesis client cannot yet write a route scoped to `IDENTITY`, which the relay transport cMIP names for a home's addresses. Not needed for the server's homes (test operators). *Lean:* leave it until a home under an operator made elsewhere needs a second address. The management page cannot add an address either; *lean:* the command line only, as for setting up.

## Readings

Smaller choices, taken the same way, for you to confirm:

1. **Paths** are lower-case ASCII letters, digits, `-`, `_` and `.`, segments of at most 100 characters, not starting with `.`; a path ends in `.html`, `.css`, `.jpg` or `.txt`; a site has `index.html`. Addresses are never decoded: a valid path needs no escape.
2. **Four kinds of file**, no more: pages, stylesheets, JPEG pictures, plain text. PNG and PDF can carry hidden data and have no Module; files to download belong in a release.
3. **Pictures are stripped** before publishing, as a posting client strips them (the decision of step 9, for posts, applied to sites): `mor-site publish` refuses a JPEG that still carries anything but the picture, and `mor-site strip` strips it.
4. **The display client takes a site's files only from the gateway that serves it**, and never falls back to a relay for a file the gateway served wrongly: what a gateway alters is what a visitor needs to know (cMIP rule 10). The publication, the signer's chain and the manifest come from the relays in the gateway's settings, then from those the publication names.
5. **One wrong file fails the whole page**: a page whose stylesheet or picture does not match is not shown at all.
6. **What is dropped from a page**: the elements and attributes in cMIP rule 11, plus `template`, `applet`, `portal`, `svg` and `math`, and any `src` or `href` on elements that are not pictures, links or stylesheets. A stylesheet's `@import` and `url()` are made inert. A link to a page the site does not hold, a `javascript:` link, or a link to a place within the same page, is shown as its text. The page is then shown in a frame whose sandbox forbids scripts, and the content security policy refuses inline styles, a `base` and anything from elsewhere, as walls behind the first one.
7. **Links leaving the site** open in a new tab; the address is shown when the pointer rests on the link (cMIP rule 14).
8. **Acts in a page** are fetched from the gateway's relays, read and judged as the barebone client reads a post, shown in a frame of their own, apart from the page's styles, and listed in the bar with their standing and their signer. An `act` attribute that is not an act id (such as the placeholder `FIRST-ACT`) shows "Not an act id".
9. **The gateway checks when it starts, when told to** (`SIGHUP`), **and, for the sites it follows, every `look` seconds**; it switches only to a version that verifies, and otherwise keeps serving the version it checked before. Withdrawals are looked for at the places asked: by the server at each check, by the browser at every page.
10. **The settings may name the release** the display client comes from (`release`); the bar shows it.
11. **Host names** in the settings are lower-case, without a port; a request's `Host` is matched without its port, so the same site answers behind Caddy on 443 and on the onion address. A host given to two sites is refused.
12. **The bar says how the version was chosen** ("follows the owner's latest version, as far as it last looked", or "its operator chose this version"), as the gateway's word.
13. **Looking for later versions in the browser** reads every site publication of the signer that the relays hold, and their manifests, on every page shown: a cost in requests to the relays, paid after the page is shown.

## Run a gateway

*A machine session: the build window cannot reach the server.* On the server that runs the homes, behind the same Caddy.

1. **Publish the site** from the machine that holds the owner's test identity, with the first act's id in place of `FIRST-ACT` (until step 17, a test post's id):
   ```
   cd clients/site && npm install
   cp -r ../../docs/dubsar.org /tmp/dubsar.org
   sed -i.bak 's/act="FIRST-ACT"/act="POST_ID"/' /tmp/dubsar.org/index.html && rm /tmp/dubsar.org/index.html.bak
   npm run -s cli -- publish --file ../genesis/me.json --dir /tmp/dubsar.org --name dubsar.org --relay RELAY1 --relay RELAY2
   ```
   It prints the version's id. Check it from anywhere: `npm run -s cli -- verify VERSION --identity OWNER --at RELAY1`. A later version: the same with `--previous VERSION`; a gateway following the site moves to it. The two shortcuts, **MOR in one page** and **Thank you for the shower**, keep their placeholder links (`#ONE-PAGE`, `#SHOWER-TEXT`) until the documents' acts exist, at step 17; then put each act's id in its place the same way as the first act's.
2. **The display client** is in `clients/site/built/`, as committed: nothing to build. Copy the client to the server with Node 22 or later: the repository's `clients/` (with `genesis/wasm` built) and `modules/`, then `npm install` in `clients/site`, `clients/genesis`, `clients/barebone`, `clients/longform` and `clients/reader`.
3. **Settings:** copy `gateway.example.json` to the server; fill in the site: its host names (`dubsar.org`, and the onion address once Tor gives it), the owner's identity, the relays, the version just published; `serve` stays `latest`, or `pinned` to hold that version.
4. **Run it** as a service under an account of its own, like the homes (`ExecStart=/usr/bin/node --import tsx src/cli.ts gateway --settings /etc/mor-site/gateway.json`, `WorkingDirectory` the `clients/site` folder, `ExecReload=/bin/kill -HUP $MAINPID`). To change the settings: edit them, then `systemctl reload`.
5. **Caddy:** `dubsar.org { reverse_proxy 127.0.0.1:8090 }`. The gateway sends its own security headers; Caddy adds HTTPS.
6. **Check on a fresh device**, a phone off the home network in a private window: every page says "Verified" with the owner's fingerprint, the same as `mor-genesis show` gives. From another machine: `npm run -s cli -- check https://dubsar.org` says SAME (it compares with `built/` in that machine's checkout).
