## In plain words

A reviewer found that Finance rule 14 said MUST, and no code checked it. This audit looks for every other rule like that. It takes each numbered rule, and each MUST, MUST NOT, SHOULD and MAY in the normal text, of the seven documents above. For each one it finds the code that checks it and the test that shows it. Then it marks the rule with one of six states:

- **CHECKED AND TESTED:** code enforces the rule, and a test exercises it.
- **CHECKED, NOT TESTED:** code enforces the rule, but no test makes it fail.
- **NOT CHECKED:** a verifier could check the rule, and no code does.
- **CLIENT CONFORMANCE:** the rule binds a client's behaviour, and no verifier of acts can check it.
- **FORMAT OPEN:** the text itself says the format is still open.
- **UNCLEAR:** the rule cannot be checked as written. These are findings for Nobody, allegedly.

Most of the protocol is checked and tested: 507 of 737 items are enforced by code, 446 of them with a test (484 and 422 at the audit; 489 and 427 after the Finance counting gaps were closed). The identity chain, canonical text, the envelope and the Law of agreements, tiers and collectives are thorough.

Some of the 101 NOT CHECKED items (123 at the audit) have nothing a verifier could check: definitions, and duties of an operator or a payer that leave no act behind. Each table says which these are. The rest are real gaps. They cluster in four places:

1. **Money arriving and leaving.** The payment cMIP checks a single payment against its rail. Nothing checks what that payment is then counted for: which debts it settles, whether the split of it matches the deal, whether the split was ever paid. *Closed 6 October for debts (`paid_toward`) and for splits (`LawView::split`, `service_account`); the split plan's format stays open.*
2. **Payments and forks of the pointer chain.** Rule 14, now built, compares only version numbers. A thief can fork the pointer chain instead of extending it.
3. **Grants.** A grant's scope, the agreements it names and its limits are read from the act but never enforced. *Closed 6 October: `backing` enforces the scope and the agreements named; limits answer unknown until a limits cMIP exists.*
4. **Specifications themselves.** No code reads a specification. Every specification hash in the code is a test value. That will matter the day a client fetches one.

Two facts sit under many rows:

- **No product code runs the payment cMIP.** `wasm/src/lib.rs` does not link `cmips/payment`, and no client calls it. Only the tests and the regtest harness run it. Law's view (`LawView::paid_toward`, `purchase`) counts receipts with no rail answer at all. *Closed 6 October for debts: `paid_toward` now counts a receipt or claim only with the rail's answer, which the caller states (`LawView::rail_valid`, from `mor_payment::verify` and `paid_at`). No product code states one yet, so in the clients no payment pays a debt (they settle debts by release). `purchase` still does not ask for it.*
- **The core verifier does not decode some payloads.** It skips Finance payloads, and Identity types 3 to 8 (routes, names, links). A malformed one is "valid" under `Verifier::status`, unless a caller decodes it.

### The gaps that matter most, ranked by what a thief or a cheat could do

Five of these were checked by hand against the code before ranking: 1, 2, 4, 7 and 9. The rest rest on the audit's reading of the code (see "How this was done").

1. **Closed 6 October 2026.** *The payment cMIP's `pointer_in_force` and Law's `paid_toward` now apply rule 12 (`finance::pointer_counts`): a pointer past a fork counts for nothing. Tests: `flow_theft.rs::a_thiefs_same_version_pointer_cannot_collect_debts_naming_the_owners`, `law_collective.rs::a_debt_is_paid_only_where_the_creditors_rules_let_it_count`.* **A thief forks the payee pointer, and rule 14 lets the backlog through.** Finance rule 12, payment cMIP "judged beside". `pointer_in_force` (`cmips/payment/src/lib.rs`) compares only version numbers.
   - With the stolen everyday key, a thief signs a second pointer with the *same* version as the owner's current one, naming the same predecessor.
   - Every debt naming the owner's current pointer then counts when paid to the thief's wallet. The F133 citation check passes as well, because the agreement did cite the owner's pointer.
   - Rule 12 says a forked chain counts only up to the fork. `finance::latest_pointer`, which would say so, is never consulted when a payment is judged, and no test forks the chain.
   - This is the same kind of gap as the one the reviewer found, one step further on.
2. **Closed 6 October 2026, except grant-key backing.** *`paid_toward` counts a receipt only with the rail's answer, valid, in the debt's unit, and paid where rules 12, 12a, 14 and 14a let it count. Tests: `law_collective.rs::a_receipt_pays_a_debt_only_with_the_rails_answer_and_in_its_unit`, `a_debt_is_paid_only_where_the_creditors_rules_let_it_count`. Still open: a receipt signed with a grant key is not judged by `backing` (Finance R7, item 6).* **A debt is settled by any receipt its creditor signs, with no rail answer and no unit check.** Finance rules 4 and 7. `LawView::paid_toward` (`core/src/law/view.rs`) adds up every receipt that the creditor signed and that names the debt.
   - It never asks for the rail's answer, and Law tests pay debts with empty proofs. It does not apply rules 14, 14a or 12a.
   - It adds up amounts without looking at their unit, so 100 units of anything pay a debt of 100 satoshis.
   - Whoever holds a key that signs for the creditor can therefore wipe out a debt in Law's view: a thief, or a split service holding the creditor's grant key. A debtor collective can then close or fork "owing nothing".
3. **Closed 6 October 2026.** *`LawView::service_account` lists every receipt the service's grant key signed, and every payer's claim with the rail's answer for a grantor of the service, that no split of the service's own key names, and every payout of its splits that no receipt of the receiver naming the split discharges in full, each naming its receiver and agreement (rule 55); a revoked service still owes on what it received (rule 30). Test: `law_collective.rs::a_split_service_is_held_to_account`. Wasm: `lawServiceAccount`; no client shows it yet.* **A split service can take the money and never split it, or split it and never pay.** Law rules 20a, 23 to 25, 29, 30b, 46b and 55. No code lists an incoming receipt or payer's claim with no matching split, or a payout with no receipt. Rule 31 says this is what makes theft provable, and today nothing shows it.
4. **A stolen safety key plus a censor.** Identity, "re-homed without audit", line 356. The text says keepers, vault payments and agreements MUST NOT rely on a homeless rotation that counts only because the reader itself failed to reach the old home.
   - The verifier records this basis (`Basis::OwnAttempt` in `core/src/chain.rs`), and the wasm build only uses it as a label.
   - `LawView` and the payment cMIP never look at it.
   - Readers behind the censor then accept the thief's key in agreements and pay the vault the thief declared.
5. **Closed 6 October 2026, except one unclear case (Finance U5).** *A valid payer's claim counts toward the debt it names; where the receiver signed no receipt, or one for less, the greater amount counts, and `LawView::disagreements` shows it as an open question on the receiver. Test: `law_collective.rs::a_payers_claim_counts_and_shows_what_the_receiver_hides`.* **Double entry is not built.** Finance rule 10. Payer claims are never compared with receipts, and a valid claim never counts as money arrived. A receiver who signs no receipt, or signs one for less, hides income and keeps the debt open: exactly what the rule says it prevents.
6. **Closed 6 October 2026.** *The payment cMIP judges a payment received against the vault (`followed_vault`, and `beside` for rules 12, 14, 14a and 15 together); Law's `paid_toward` does too. Tests: `flow_theft.rs::the_vault_rules_judge_a_payment_received_on_the_flow`, `law_collective.rs::a_debt_is_paid_only_where_the_creditors_rules_let_it_count`.* **The vault's protection is applied only by the payer.** Finance rules 14a and 15. The vault limit and the uncovered-unit rule work when a payer chooses where to pay (`destination`, `choose`), but no verifier applies them to a payment received. A thief who redirects the flow pointer can take payments above the vault limit, or in a unit the vault does not cover. They verify valid and settle debts.
7. **Closed 6 October 2026.** *`LawView::release` judges each stake against the claiming agreement in force (its latest version), which the version named must be or descend to; the holders, the release rule and the time reference are read there. Test: `law_collective.rs::a_release_is_judged_by_the_agreement_in_force`.* **One owner releases a work under an older, looser rule.** Law, Release, line 434. `LawView::release` judges a release against the agreement version it *names* (`lineage(ag)[0]`), not the version in force.
   - Suppose the owners tightened the release rule by a clone every owner signed.
   - One owner can still release the work, citing the old version. That ends the work's claim, and every owner's income from it.
8. **Closed 6 October 2026, but for what only the split plan can say.** *`LawView::split` judges the payouts against the stakes of the version in force, shows a split naming another version, a signer that is no split service the agreement in force names, or a grant key, as `problems`; applies `role_evidence` to every role payout (`unevidenced`); and lists fee and named-receiver payouts as `unplanned`, which only the plan (terms field 8, format open) could justify. Test: `law_collective.rs::a_split_is_the_named_services_act_under_the_version_in_force`.* **A split is judged against whichever deal version it picks, and anyone can sign one.** Law rules 20b, 22a and 26. `LawView::split` had four gaps:
   - It takes the agreement version the split names, without checking that this version is in force, or that it names this service.
   - It never calls `role_evidence`.
   - It does not constrain role, fee or receiver payouts.
   - It does not check who signed the split.

   A service can name an old version in which an accomplice still held a stake, or take a cut as a "fee", and nothing is flagged.
9. **Closed 6 October 2026.** *`backing` applies the scope (field 1): scope 0 backs the terms of a new agreement and signature acts on them; scope 1 backs only acts naming one of the agreements of field 2, in any version, or an act named there (rule 40); scope 2 backs no act on an agreement. Readings stated in the code, for Nobody, allegedly, to confirm. Test: `law_collective.rs::a_grant_reaches_only_its_scope_and_its_limits_answer_unknown`.* **A grant reaches beyond its scope.** Law rule 38 (and rule 40). `LawView::backing` never reads a grant's scope (field 1) or the agreements it names (field 2). A grantee hired to manage one named deal can sign new deals within the grant's kinds, and they bind the collective.
10. **Closed 6 October 2026.** *A grant carrying field 3 or 4 answers `Backing::Unknown` (`Consent::Unknown`, counting for nothing), never "Backed"; the collective's own adoption still binds (rule 40). Same test.* **A grant's limits are ignored, so it fails open.** Law rule 18d. Grant fields 3 and 4 (limits, and the cMIP defining them) are decoded, but `backing` never reads them. An act beyond the owners' cap, rail or holding period is judged "Backed". When the limits cMIP is not implemented, the safe answer is "unknown".

### UNCLEAR: rules that cannot be checked as written

Each is a question for Nobody, allegedly. The detail is in the document's own section.

1. **Identity, line 215 against line 75.** "A private link is stored as encrypted acts", but "every act defined by this MIP is public". As written, a private link cannot exist, and the core refuses any private Identity act.
2. **Identity, line 439.** "The same answer to every conforming verifier holding the same identity chain, acknowledgements and keeper records" is not true as written. Answers also depend on the verifier's own failed attempts (rule 32a) and on the inclusion proofs it holds.
3. **Finance, line 149/152: a likely flaw.** An anonymous claim's key 8 signature does not cover fields 5, 6 and 9. Anyone can re-wrap an anonymous payer's claim with a different referral, so "signed by the payer" (rule 10b) does not hold for the referral.
4. **Finance rule 14 for a payment for an agreement or offer, and rule 15 "through the agreement"** (R14-3, open since 6 October). Law's terms name no payee pointer, so there is nothing to compare.
5. **Finance rule 15, good faith after a rotation** (R14-2, open since 6 October). Telling a payment made before the rotation from one made after needs a "when" the protocol does not have.
6. **Payment cMIP, line 37.** Whether a rail is a request rail or a push rail changes purchase verdicts, but no machine-readable field carries it. `push_rails` is filled in by hand.
7. **Law, act-type table, lines 108 and 109, against Fork, line 403.** The table says a fork or closing is completed by signature acts. §Fork (F132) says members sign by chain signatures, and that a signature act does not count. The code follows §Fork.
8. **Law, abandonment clause key 2, line 181.** It is not said what "one" refers to in "(only with one)".
9. **Law rule 15a (and 21), line 492.** "The first party listed in the terms" is not the same as a stake's first holder. The code gives the leftover to the stake's first holder. *Decided, F140 item 4: the stake's first holder, as the code did.*
10. **Law rule 16, line 494.** No format marks an identity as a publisher, so a verifier cannot tell a publisher's stake from an owner's.
11. **Law rule 27b, line 519.** The split format has no list of the modules a split ran under, so an omitted declared fee leaves no trace.
12. **Law rule 28, line 520.** The split format has no field for a metric or its module, and "the identity running the service" cannot be told from any third party.
13. **Law rule 46b, line 623.** "A fee paid to a service the members own is public": a verifier cannot see who owns a service.
14. **Law rule 49, line 650.** "Absence" is measured on a time reference no cMIP defines, and rule 51's list of what the core checks leaves it out. With rule 57a, a named authority could remove an active member's voice. *Decided, F136, and built 6 October: where the clause names a period, a declaration counts only on the anchoring answer the verifier states (`LawView::absence_anchored`), the anchoring format being open; unstated, it does not count.*
15. **Production rule 17b, line 134.** No MIP defines the "use record" act. The code takes any third party's act as evidence that a service was used.

Text also carries two wording findings inside CLIENT CONFORMANCE rows:

- Rule 5's list of characters to warn about ends in "and similar", so no client can know when it is complete.
- The format task's "letters or digits" names no definition or Unicode version.

### Smaller things worth knowing

- **Checked but never shown failing.** 62 rules are checked in code that no test makes fail. Most are in Identity part 1 (21) and the Law act formats (15): the fork act's shape, the record format, the succession plan, the keeper rule, and a grant key signing a decision.
- **Checked only in the relay.** Identity rule 2 (a safety key signs only rotations and chain signatures) is enforced explicitly in the relay. The core verifier enforces it only indirectly.
- **A sequence check that nothing calls.** `Sequence::check_next` (`core/src/act.rs`) is correct and tested, but no verifier, relay or client calls it. An act with a false position, a false running summary or two `prev` entries counts as valid until a rotation voids it.
- **A dev tool that signs without showing.** The repo client's `words` command (`clients/repo/src/cli.ts`) signs a clone carrying typed text without showing the text first, which Text rule 5a requires.

## How this was done

Eight read-only passes, one per slice of the texts, read each rule and then the code and the tests: `core/`, `wasm/`, `cmips/`, `modules/`, `relay/`, `harness/` and `clients/`. A rule counts as checked only where the function was opened and found to enforce it, not merely to mention it. A test counts only where it exercises the rule, a refusal where the rule forbids something. No tests were run: the states come from reading. The five ranked gaps marked above were confirmed again by hand afterwards.

**How rows are counted.** A row is one rule or one sentence. Rules quoted in two slices (links, unsplit receipts) appear in both. Severity labels (HIGH, MEDIUM, LOW) are the audit's judgement of what a thief or a cheat could do, not a decided priority. Each document below lists its own gaps first, ranked, then its UNCLEAR items, then every row.

Abbreviations inside the tables are defined at the top of each part.

#### Gaps a verifier could check, ranked

1. **HIGH, §Re-homed reliance (line 356).** "Keepers, vault payments and agreements MUST NOT rely on" a homeless rotation that counts only through the reader's own failed attempt. Neither the Law view nor the payment cMIP looks at how a rotation counted. A thief with the safety key, helped by a censor who blocks the real home, gets the rotation counted for readers behind the censor. Law then accepts the thief's key in agreements and consents, and those readers pay the vault the thief declared.
2. **MEDIUM, VP-Decl 5 Links (line 389) and §Link confirmation (line 215).** No code decides whether a link counts or who may confirm it. A service binding accounts to MOR identities could accept a confirmation signed by someone other than the named identity, and so tie an attacker's account to a victim.
3. **LOW-MEDIUM, §Link termination (line 215).** Nothing checks that a termination is signed by the MOR side. A naive client could let a stranger end someone's link.
4. **LOW, §Types 3-8 shape (lines 182-215).** The core verifier never decodes name or link payloads (or routes, outside `latest`), so `status()` calls a malformed one valid.
5. **LOW, VP-Decl 4 Names (line 388) and §Name withdrawal (line 204).** No code judges names or withdrawals. A withdrawal by another identity is not refused anywhere.
6. **LOW, §Finality (line 354).** Code treats a homeless rotation as final once *any* rotation counts at n+1, even another homeless one under its own rule. The text says "under the home rule the homeless rotation declared". The thief gains little, since it already controls those homes.
7. **LOW, §Schemes "used by" (lines 24, 58-60).** Scheme roles are not enforced. A genesis may commit a non-post-quantum (Schnorr) safety key or declare an SLH-DSA signing key. The core verifier then accepts SLH-signed everyday acts (the relay refuses them). The owner weakens only their own identity.
8. **LOW, §Envelope prev (line 79).** The verifier accepts an everyday act with several `prev` ids. Such an act cannot be in a kept line, so only its signer loses.
9. **LOW, §Receipt counter (line 177).** Nobody checks that a home's log positions increase by one for unaudited identities. Nothing relies on them there.

#### Gaps a verifier could check, ranked

1. **R23, link counts only with both sides (MEDIUM).** No code decides whether a link counts: link claim, confirmation and termination decode as `Payload::Other`, with no shape check and no rule that the confirmation is signed by the identity the claim names. A home serves claims by *other* identities that name the owner in that owner's record. So Mallory can publish "Mallory's account X is the same entity as Alice's identity", and any sign-in service or bridge reading the record has no library function to reject it.
2. **R24, either side may end a link (LOW-MEDIUM).** Terminations are never judged, so a link ended by one side can never be shown as ended. A bridge could go on acting on a link the owner withdrew. Today this matters only once links are used (see 1).
3. **R1a, a scoped key never signs an Identity act (LOW).** An Identity act (routes, witness act, objection, receipt) signed with a grant key and bound to a Law grant gets status "scoped" instead of invalid. Law's `valid()` and `backing` exclude only Law decisions, so a grant whose reach is "all" could make such an act look backed. A grantee could then put out a routes or witness act in the collective's name. Identity's own consumers require Valid or a bound key, so no inbox actually moves today.

Not ranked (no verifier could check them, or nothing to check): R8 (no obligation), R25 (definition, holds by absence), R14-keepers (a keeper's duty, defined in Law).

## Envelope (`spec/MIP-envelope-draft-7.md`)

Slice: `spec/MIP-envelope-draft-7.md` (all of it). Italic commentary skipped. Paths are relative to the repo root.

### Gaps a verifier could check, ranked

Only items a verifier could check. Items that are definitions or duties of other parties are left out.

1. **R16 / For whom (L274, L208), MEDIUM.** Nothing works out who a publication's payment is owed to (`for`, otherwise the signer). Today no wallet pays a publication, so the gap is waiting for the first one. Then a wallet, or a cheat claiming to have paid, could pay the publisher instead of the identity in `for`, and no verifier would say the creator is still owed.
2. **Withdrawal, past deals (L228), MEDIUM.** A payment that arrives after a publication is withdrawn should be "no deal, refund owed". Law's `purchase` never looks at Envelope withdrawals. A seller could withdraw a publication and keep taking payments from wallets that missed the withdrawal, and nothing would show the refund as owed. Law calls this its own rule, so check whether the Law slice covers it.
3. **R15 withdrawal authority (L273), MEDIUM.** The core has no withdrawal check. The barebone reader (`clients/barebone/src/post.ts` `findWithdrawal`) accepts any valid withdrawal a relay returns for "signer = author" and never checks who signed it. One hostile relay among the reader's hints can serve a withdrawal signed by Mallory and hide the author's picture, even when other relays serve it honestly. The existing test passes only because the test relay is honest. The site client does check the signer, but it ignores `for` and has no negative test.
4. **R4 sequence position, summary and single `prev` (L249), LOW.** `Sequence::check_next` exists and is tested, but no verifier, relay or client applies it to held acts. An everyday act with a false position, a false running summary or two `prev` entries counts as Valid. Only the signer's key can make one (or a thief, who can already sign anything). A rotation later voids such acts, because they fall outside the kept ancestry. Still, a core MUST is not enforced, and the single-line guarantee (F24) is broken for anyone reading before the next rotation.
5. **R8, encryption keys public (L258, L104), LOW.** Identity-spec acts are refused when private. Envelope type-4 encryption keys are not checked, though L104 lists them as Identity acts. Suppose a client holds a private encryption-key act with its key, for example one delivered inside a sealed container. `Verifier::latest` could then pick it as the current key, so a thief with the signing key could swap the key for one victim only, without it ever appearing on relays. This is conditional: no client was confirmed to add delivered inner acts to the verifier it uses for look-ups.
6. **Types table, publics (L233-239), LOW.** No verifier refuses a private publication, withdrawal or commitment. The effect is mostly confusion, since a private withdrawal is unreadable to most readers anyway.
7. **Publication format (L193-206), LOW.** There is no strict decoder. Unknown keys, wrong lengths and a non-hash field 8 are accepted wherever clients read loosely. Byte-different publications of the same media would pass, and a malformed `for` would be ignored silently instead of refused.
8. **R9 content-key reuse (L259), LOW.** A verifier could flag two public objects that carry the same content key. Nothing does. The harm falls on the signer: publishing one key opens every object locked with it.
9. **Withdrawal effect (L227), LOW.** No code closes offers or stops releasing keys when an Envelope withdrawal arrives. Nothing releases keys by delegation yet, so this is latent.

## Text (`spec/MIP-text-draft-6.md`)

Slice: `spec/MIP-text-draft-6.md` (all of it). Italic commentary skipped.

### Gaps a verifier could check, ranked

1. **Text act format (L41-48), LOW.** Nothing decodes the text payload strictly. A text act with extra payload keys, or a field 1 that is not a 32-byte hash, is read as an ordinary text act. Nothing can be stolen this way, but it weakens "one form, one hash": the same words and format can be signed as two byte-different acts, and a malformed format field is ignored instead of refused.

### UNCLEAR: findings for Nobody, allegedly

- **R5 "and similar" (L56).** The list of invisible characters to warn about ends in "and similar". No client can tell when it has covered the list, and two clients will warn differently. It is only a SHOULD, but it needs a fixed list or an explicit "client's judgement".
- **§Tasks "letters or digits" (L62).** The text does not say which definition decides what counts as a letter or digit (Unicode general categories L* and N*? Nd only?), nor which Unicode version. The long-form format tests `\p{L}\p{N}` under the system's Unicode, whatever version that is. The rule needs the same pinning as rule 6 to be checkable the same way by everyone.

### Gaps a verifier could check, ranked

Only items a verifier could check. Duty-only and scope rows (fresh address, R8, R11, R19, R20) are left out.

1. **Closed 6 October 2026** (see R12). **HIGH: R12 not applied to payments, which bypasses the rule 14 fix.** `pointer_in_force` compares only version numbers. A thief with the everyday key signs a second pointer of the *same* version as the owner's current one, naming the same predecessor: a fork. Every debt naming the owner's current pointer then passes rule 14 when paid to the thief's fork (n ≥ n). The agreement does cite the owner's pointer, so F133 passes too. Rule 12 says a contested chain counts only up to the fork, but `latest_pointer` is never consulted. No test covers a fork in `flow_theft.rs`.
2. **Closed 6 October 2026, except grant-key backing** (see R7 discharge). **HIGH: R7 discharge (`LawView::paid_toward`) counts receipts unchecked.** It sums any Identity-valid receipt signed by the creditor that names the debt. It does no rail check (empty proofs pass in the tests), no rule 14, no 14a, no 12a, **no unit check**, and no grant-key backing. So:
   - A split service holding the creditor's grant key, or a thief with the creditor's key, can sign a receipt that erases a debt in Law's view.
   - A debtor collective that holds such a key can then close or fork "owing nothing".
   - A receipt for 100 units of a worthless unit pays a 100-satoshi debt.
3. **Closed 6 October 2026, except U5** (see R10). **HIGH: R10 double entry not built.** Claims are never compared with receipts, and a valid payer claim never counts as money arrived. A receiver who signs no receipt, or an under-reporting one, keeps the debt open and hides the income. Double entry is exactly what the rule promises.
4. **Closed 6 October 2026** (see R14a counts as flow). **MEDIUM: R14a / R15 not applied to received payments.** No verifier rejects a payment paid to the flow above the vault limit, or in a unit the vault does not cover. A thief who takes the everyday key and redirects the flow can take large payments, or payments in an uncovered unit, and they verify valid and discharge debts in Law. The vault exists to stop exactly this.
5. **MEDIUM: R12a "in force" is not checked for vaults, and the agreement's cMIP is never resolved.** A payment to a vault entry from an old rotation (for example, a compromised node the owner rotated away from) verifies valid and counts for any debt. Under an agreement, nothing supplies `under`, so a Module implementing another cMIP is not refused in practice.
6. **MEDIUM: R10b referral.** Any third party's act (a post) counts as referral evidence. The payer's signed claim field 6 is never read. A referrer can self-certify and earn role shares.
7. **MEDIUM: R18a payout fees.** The payout's `rail_fee` is never compared with the plan's maximum, so a split service can skim through "fees".
8. **Closed 6 October 2026 for debts; open for purchases.** **MEDIUM: R4.** Nothing that counts money requires a valid rail answer. No product code (`wasm`, clients) runs `mor_payment::verify` at all.
9. **LOW to MEDIUM: R8a.** No "counts neither" rule, and no batch sum check. Two creditor receipts sharing one proof both count toward debts in Law.
10. **LOW (MEDIUM once conversion hops exist): R5, R6, R9.** No route code: a short forward or a swallowed forward is never flagged.
11. **LOW: R7 states.** Past its terms, closed by clone and redirected are not computed. There is no per-obligation state for people.
12. **LOW: R10c (tip names nothing).** A tip or obligation payment carrying field 9 is judged as a purchase instead of refused.
13. **LOW: receipt's previous hop in `objects`** is not compared with field 6.
14. **LOW: publication pays `for`.** A receipt from another payee for a publication is not flagged.

#### Gaps a verifier could check, ranked

1. **Closed 6 October 2026** (`latest_version`; TC `a_release_is_judged_by_the_agreement_in_force`). **MEDIUM. §Release rule in force (line 434).** `LawView::release` (`core/src/law/view.rs`) applies the release rule and the holders of the agreement version the release *names*, not the version in force. Suppose the owners tightened the release rule from "any one holder" to "every holder" by a clone everyone signed (N8). One owner can still release the work by naming the older version. That ends the claim (`released`, `claim_after_release`), and owners lose their income from the work. A former holder bought out by a clone could do the same under the old version. Fix: judge the release against the latest version of the claiming agreement (`latest_version` already exists in the view).
2. **LOW. §Release signer (line 434).** Nobody checks that the release's own signer is a direct owner. Under a threshold release rule, a stranger can draft a release that k owners then co-sign. Owners still decide, so the harm is only that an outsider authors the act.
3. **LOW. §Area number ≤ holders (lines 194-196).** Founding terms may give an area a number above its holder count. Rule 44d then needs every holder, so no power is gained. It only leaves two encodings for one meaning, against the B8 principle.
4. **LOW. §Negotiation acks (line 295).** An ack naming one's own message, an unrelated act, or carried on a thread's first message is ignored rather than flagged. A side could show a misleading acknowledgement to a reader of the raw act. The record's proven completeness is unaffected.
5. **LOW. §Clone objects (line 219).** A clone's `objects` predecessor is never checked to be an act of the parent's chain. A clone can claim to follow any act, which misleads readers about what it saw. The agreement in force is decided by records and rotations, not by this entry.

- **§Types 19, 20 (lines 108-109) against §Fork (line 403).** The act-type table says a fork and a closing are "completed by the signature acts of every other member", but §Fork says, since F132, that members sign by Identity chain signatures and that "a signature act (type 1), or the fork act itself, is no member's signature on it". #### Gaps a verifier could check, ranked

1. **Closed 6 October 2026** (`LawView::service_account`). **R29 / R20a: unsplit receipts and unpaid payouts are never shown (HIGH).** No function finds an incoming receipt or payer's claim without a matching split, or a payout without its receipt. A split service can take the money and publish nothing, or publish an honest split and never pay it, and no verdict or client says so. This is the rule that makes theft provable (rule 31).
2. **Closed 6 October 2026** (`Backing::Unknown`). **R18d: grant limits are ignored (MEDIUM).** Grant fields 3 and 4 (limits, and the cMIP defining them) are decoded but `backing` never reads them, so an act beyond the owners' limits (a cap, a rail, a holding period) is judged "Backed". 3. **Closed 6 October 2026** (`in_force`, `problems`, `unplanned`). **R26: the split is judged against whatever version it names (MEDIUM).** `LawView::split` uses the agreement the split itself names, without checking it is the version in force or that it names this service, and leaves role, fee and receiver payouts unconstrained. 4. **Closed 6 October 2026** (`unevidenced`). **R22a: role evidence is checked in a helper nobody calls (MEDIUM).** `role_evidence` is right and tested, but `LawView::split` never applies it. A role payout with no evidence, or with evidence the service signed itself, passes.
5. **Closed 6 October 2026** (`problems`). **R20b: a split's signer is never checked (MEDIUM).** Anyone can publish a split of someone else's receipt, and it is judged and displayed like the service's. Once R29 is built, a forged split would also hide an unsplit receipt.
6. **Closed 6 October 2026** (with R29). **R23, R24, R25, R30b: payouts, held amounts, batches, the old service's debts (MEDIUM).** All part of R29: nothing tracks them as open obligations.
7. **Closed 6 October 2026** (the status quo stands). **R5b: forks of a deal's clones (LOW).** `latest_version` picks the first existing child clone by hash, where the text says the status quo stands. Two rival clones every party signed make one silently current for purchases.

#### Gaps a verifier could check, ranked

Items a verifier could check, worst first. Definitions and permissions with nothing to check (rows 35, 108, 128, 133, 138) are left out.

1. **Closed 6 October 2026.** **MEDIUM. Row 49 (R38): grant scope and named agreements are never checked.** A grant says "manage these named deals" (scope 1, field 2) or "sign new deals" (scope 0), but the core backs any act of the grant key within its kinds. A grantee hired to look after one deal can sign other deals or acts in the collective's name, and they bind the collective. (Row 60, managing an adopted act "under its own grant (scope 1, naming it)", is the same gap.)
2. **Closed 6 October 2026.** **MEDIUM. Row 130 (R55) with row 91 (R46b): missing splits and unpaid shares are not shown as open obligations.** A split service can take money and publish no split, or pay a holder nothing, and the core never lists that as an open debt; only the owners' own comparison would catch it.
3. **MEDIUM. Row 127 (R53): declaration outcomes 1 to 4 have no effect.** A declaration may say "stake transferred" or "agreement closed", and the core checks only that the clause allows it. Payments still follow field 7, so the absent holder keeps being paid and the rightful transferee is shown as wrongly paid; a "closed" agreement keeps counting.
4. **LOW. Row 118 (R49): the absence authority need not be an identity.** Founding terms can name a cMIP hash or a hash nobody holds as the authority. Rule 36b's coverage check accepts it, so the constitution looks covered while nobody can ever declare absence; a dead member then freezes it. Every founder signs such terms, which limits the risk.
5. **LOW. Row 96 (R47a.B): a successor's "forked from" back-link is not checked.** A fork can hand the original's stakes and debts to an existing collective whose terms never name the original.
6. **LOW. Row 113 (R48c): a stake cannot pass by succession.** A plan clone may not touch field 7, and a nomination clone needs the absent holder's own signature to lower their stake, so heirs are never paid. It fails closed; nothing is stolen.
7. **LOW. Row 34 (R37a): a removed stake holder need not be listed in the departed members entry (field 22).** Their stake stays in field 7, so only the record is incomplete.
8. **LOW. Row 80 (R45): a clone's "parent's latest act" is not checked.** Law never checks the act a clone names on its parent's chain.
9. **LOW. Row 82 (R45): "obligations before that point settle under the parent."** Nothing judges a deal's obligations under the version in force when they were made.
10. **LOW. Row 116 (R48d): identity-level succession is never consulted by Law.**
11. **LOW. Row 110 (R48b): a living party cannot trigger their own plan.** The clone stays a draft. It fails closed.
12. **LOW. Row 132 (R56): negotiation messages need not be locked.** A public message only discloses early.
13. **LOW. Row 136 (Tasks): the condition, time-reference and anchoring tasks have no cMIP.** The core only consumes their answers.
14. **LOW. Row 106 (R47b): the deal behind a release against future terms is not checked.** This is by the spec's own reading 3; the deal binds on its own.
15. **No severity. Row 35 (R37a):** an escrowed-share release on resignation is the authority's off-chain duty.

#### UNCLEAR: findings for Nobody, allegedly

- **Row 122 (R49): "Absence means... no act by the party on the agreement, for a period measured on the agreement's time reference."** Rule 51 lists what the core checks, and this is not among them. No time-reference cMIP exists to measure the period. As written, a named authority can declare an active member absent and remove their voice, and rule 57a says a contest never changes validity. Question for the author: should a verifier at least refuse a declaration when it holds an act by the party on the agreement within the period, or is this the authority's judgment alone, answerable only by contest?
- **Row 90 (R46b): "a fee paid to a service the members own is public."** A verifier cannot know who owns a service. Rule 46b's own mechanism, delivering every split to every holder it pays (row 89), is checked, but the clause as written cannot be checked.
- **Related to row 50 (R38 limits, FORMAT OPEN):** the encoding of grant limits is open, yet a grant that carries a limits value (fields 3, 4) is backed as if unlimited, not refused. Rule 41 says a verifier refuses an import whose format is open; the spec says nothing for limits. Question for the author: should a verifier refuse an act under a grant whose limits it cannot read, rather than ignore them? No client writes limits today, so nothing is exposed yet. *Built 6 October as rule 18d reads: the answer is unknown (`Backing::Unknown`), never "backed", and the act counts for nothing until a verifier implements the limits cMIP.*

## Production (`spec/MIP-production-draft-6.md`)

Main finding first: **no code reads a specification.** No code encodes or decodes the `spec` map (fields 0 to 10). No code checks that content hashes to its spec hash, that a creator signed the publication, or what field 4 (dependencies), field 5 (implements), field 7 (fee terms) or field 8 (predecessor) say. There is no RV32IM machine.

- `core/src/hash.rs::spec_hash` exists, but nothing calls it on real content.
- Every spec hash in the code is a test value. Examples: `cmips/payment/src/lib.rs::spec`, `modules/lightning/src/lib.rs::spec`, `clients/genesis/src/core.ts` `MIPS`, `clients/repo/src/specs.ts`.
- What the code does check is how agreements *use* spec hashes: task numbers, at most one cMIP per task, extension lanes, a rail Module's `implements`, and unknown schemes.
- The facts a specification would supply (`ext_layers`, `push_rails`, `implements()`) are handed in by the caller or hard-coded in Rust.

Many rows below follow from that one gap.

### Gaps a verifier could check, ranked

These are gaps a verifier could close. Duties of other parties, permissions and definitions (R5, R6, R14, R18, R19, R21) are left out. Severity is low for now in most cases because no code reads specifications yet. Every gap below becomes live the day one does.

1. **R16, fee consent (MEDIUM).** A split's fees are listed but never checked against terms the bearer signed. A split service can pay a "module fee" to a friend from every incoming payment. Each stake loses alike, so the stake check passes, and nothing flags the fee as unconsented.
2. **R3 / field 1, creator signature (MEDIUM).** Nothing checks that a cMIP or Module was published by the creator it names. A cheat can publish a specification "by" a well-known builder, with fee terms or reputation borrowed from them, and no code can tell.
3. **R1 / R4 / spec hash, content matches hash (MEDIUM, once specs are fetched).** No code fetches a specification and checks its content against its hash. A client built on this would let a host swap the text of a cMIP. The user would adopt different rules than the hash in their agreement names.
4. **Field 10 validity (LOW).** An extension's declared layers are never checked to be in 0..3, ascending and without repeats; the client passes them in raw. A malformed specification is used instead of refused. With an unknown layer the change needs the clone rule, so this does not lead to theft.
5. **R17c, tip with module fees (LOW).** `split` does not check that the receipt it splits is not a plain tip. A split service could take module fees from a tip, which Finance forbids.
6. **Field 0 kind, field 9 canonical text, publication act (LOW).** None of these is decoded or checked. Each is harmless until specifications are read.
7. **Spec hash (partial, LOW).** The function exists but is never applied to real content. Covered by item 3.

### UNCLEAR: findings for Nobody, allegedly

- **R17b, service "use record" (line 134).** The rule names a "use record signed by the identity running the service", but no MIP defines that act: no type and no format. The code (`role_evidence`, `Role::Other`) takes *any* valid act signed by anyone other than the split service and the payee. An unrelated act by any third party can therefore count as evidence that a service was used. The spec needs either a defined use-record act or an explicit statement that any third-party act suffices (F75 reading). This is a question for Nobody, allegedly.

## Payment cMIP (`cmips/cmip-payment-draft-2.md`)

Slice: `cmips/cmip-payment-draft-2.md`. Code: `cmips/payment/src/lib.rs`, `modules/lightning/src/lib.rs`, tests in `modules/lightning/tests/{rule,flow_theft}.rs` and `harness/tests/lightning_rail.rs` (regtest, skipped unless `MOR_LN_REGTEST` is set). The cMIP is **not linked into wasm or any client**: every check below runs only in tests and the harness.

### Gaps a verifier could check, ranked

1. **Closed 6 October 2026** (see §Verify: judged beside). **HIGH: §Verify "judged beside", rules 12, 14a and 15 not judged.** A thief can fork the flow pointer at the current version and collect debts that name it (rule 14's version check passes). A payment to the flow above the vault limit is accepted as well. Both verify valid, and no function says "does not count".
2. **LOW: §Verify signer first.** `verify` never checks a receipt's signer. A caller using it alone accepts a receipt signed by anyone.
3. **LOW: §Rail Modules spec.** `implements()` is self-declared in code, not read from the published specification's field 5. A Module can claim this cMIP regardless of its spec.

(§Commitment 1 and "signs nothing" are duties or design, with nothing for a verifier to check.)

### UNCLEAR: findings for Nobody, allegedly

- **U2 (line 37): request rail or push rail has no machine-readable home.** Whether a payment is a purchase depends on it (Finance 10c), yet it lives only in a Module's prose. Core's `LawView.push_rails` must be filled in by hand, and two verifiers that read the prose differently reach different purchase verdicts. A field in the Module's specification (Production), or a rule that every Module under draft 2 is a request rail, would settle it.
