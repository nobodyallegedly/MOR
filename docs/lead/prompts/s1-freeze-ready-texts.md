The freeze-ready texts: the clean-up pass of MOR's core, in the MOR repository (`nobodyallegedly/MOR`). Texts only: no code changes in this session.

**What this is for.** After you, a separate session will build a MOR verifier in C from these texts alone: no code, no findings log, nobody to answer its questions. Then the texts freeze. So every text you write must stand on its own: a careful stranger holding only the six MIRs, the MICS document and the freeze test suite must be able to understand and check every rule. Where that is impossible, the text is wrong, and you say so.

**What freeze-ready means** (a checklist for every text):
1. **No history.** The old numbers beside rules ("Rule 76 (was 40)") and the tables from old to new go (decided at F251: "the next, freeze-ready draft drops the old numbers"); the current numbers stay, so the code and the tests keep citing them. Every "new in draft N", "new in version N", "taken", "reading", "mechanic", transition note, version history and approval note goes. The header is one line: the text's name, its draft, and that it is freeze-ready, for Nobody, allegedly, to approve. A retired rule or type keeps one line saying it is retired and its number is never reused.
2. **No finding numbers** (pending Nobody, allegedly's confirmation; the lead's lean): no "F123" or review label anywhere in the eight texts. Where a reason helps a reader understand or check a rule, it stays as italic commentary in the text's own words. Build the provenance map as you go: `docs/freeze-provenance.md`, each rule (text and number) with the findings that shaped it. It stays in the repository, outside what the C session receives.
3. **Nothing open.** MICS "Open before freeze" ends empty. Anything still marked open in any text becomes a question in your report, never a silent choice.
4. **Every cross-reference resolves** within the eight texts, by text and rule number of the new drafts. No pointer to `docs/`, a finding, a review, a client or the code. A cMIP or Module is named by its role or its task, never by a file of this repository.
5. **One meaning per word**, across all eight. Keep a glossary as you go (`docs/freeze-ready-glossary.md`). Known case: Agreements rule 60's note calls an area reaching a whole layer that layer's "lane"; "lane" means a person's grant to an app elsewhere, so the MIR says "area" only (decided). Look for others: verdict words (valid, invalid, unknown, disputed, void, pending), the two keys (chain key, signing key), act, type, layer, sequence, line, chain, grant, scoped key, keeper, anchor. Where two words mean one thing, pick the one the MICS uses; where one word means two things, put the choice in your report.
6. **The voice the texts already use:** normal text is the protocol, italics are commentary; MUST, SHOULD and MAY in the verifier's rules; plain sentences. The core never names a particular use, place, jurisdiction or example from the case studies.

**The decisions to write in** (read each finding in full; the finding decides, this list only points):
- **Keepers redefined (F358, 3 and 4):** a keeper is a signed ordering mechanism serving proofs: it signs a sequence (this act, then this, then this rotation), checkable from any copy. The keeper record's format goes into the core (type 2, `{ 0 => [act, signer] }`, as Agreements already sketches), with what a verifier checks of it. Only anchors place anything on the clock; a keeper may anchor its own sequence. Rule 33: a deadline is shown missed only by an anchor, of the act itself or of a keeper's sequence; a keeper's word alone never says late. The remaining trust, that a keeper records acts as they arrive, is rule 42's, stated.
- **An act under a revoked grant (F359):** an act the revocation does not hold is void, unless another identity acknowledged it, or a keeper the rules allow recorded it before recording the revocation; then it is shown disputed. Write it in Agreements (rule 76 and the grant section) in the same words as Identity's rule for a rotation's disowning (F57), so a reader sees one principle twice. Keep F352's (A′): a revocation cites every act under the grant. If you find the two would read better as one rule written once, propose it in the report; do not restructure the texts for it.
- **Money rule 7 as built (F358, 1):** Money draft 10 carries it; check it reads cleanly with Agreements 17.
- **A grant to oneself (F351) and a holder's member key named by their founding signature (F353):** in Agreements 15 and 16; check they read cleanly.
- **F295:** an act outside its own specification's format is invalid, whichever MIR or cMIP defines it; check every text applies it the same way, Agreements' counting included (only acts valid in their own format count).
- **Written for people (F349):** Identity 14's section, named in MICS and suite.
- **Text 9 and 10 (F334, F343)** named by MICS and suite.

**Do not:** change any rule beyond these decisions; rename cMIPs or Modules (another session does, F356); touch code, tests or vectors (the next session aligns the code and writes the vectors from your texts); write any F number into the eight texts (if Nobody, allegedly, decides otherwise, the lead will tell you).

**When cleaning finds a problem** (a gap, two rules that disagree, a rule nobody can check, a term used two ways, a reference that cannot resolve): that is the point of this pass. If it is wording only and no verdict can change, fix it and list it in the report as taken. If a verdict could change, do not choose: write the question in plain words first, then precisely, with the options, your lean and each option's cost, leave the text as it was at that point, mark it in the progress file, and continue with the rest. If it shows a MIR is flawed at its foundations, stop and say so first in the report.

**A stranger's reading.** After each MIR, and once at the end over all eight, have a subagent read the new text with no access to `docs/`, the findings or the code (the C session's view), asked to list every rule it cannot understand or check from the eight texts alone, and every term used two ways. Fix what is wording; list the rest as questions. Put its lists in the report.

**Keep a progress file** (`docs/freeze-ready-progress.md`): which texts are done, the glossary's state, the questions so far, where you are. If your context runs long or the session must stop, it is what the next session starts from. Stop at a clean point: a committed text.
