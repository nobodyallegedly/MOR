# Money software earns trust by rehearsing failure

Research report for DubPay (part of the Dubsar Suite): how Lightning and ecash software is tested and operated, and what a small team can check before releasing anything that touches payments. Research only: no code, no keys, no real money.

## Summary (one minute)

- **Private test chains.** Node projects test on *regtest* (a private Bitcoin chain where the tester makes the blocks) with real node programs: [Core Lightning](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/contribute-to-core-lightning/testing.md), [Eclair](https://raw.githubusercontent.com/ACINQ/eclair/master/eclair-core/src/test/scala/fr/acinq/eclair/integration/IntegrationSpec.scala), [LND](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lntest/README.md). *Signet* (a shared test chain with signed blocks) is for trials between several parties ([BIP 325](https://raw.githubusercontent.com/bitcoin/bips/master/bip-0325.mediawiki)).
- **Fake first, real second.** Cashu *mints* (servers that issue ecash) run every test on a fake Lightning backend, then on real regtest nodes ([Nutshell CI](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.github/workflows/ci.yml)).
- **Money rules are whole-number rules.** Cashu checks `sum(inputs) - fees == sum(outputs)` and rounds fees up ([NUT-02](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/02.md)); Lightning rounds down and the leftover goes to fees ([BOLT 3](https://github.com/lightning/bolts/blob/master/03-transactions.md)).
- **Stop when the books break.** Fedimint halts if liabilities exceed assets ([source](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/fedimint-server/src/consensus/engine.rs)).
- **Fuzzing** (throwing masses of malformed input at a program) found one LND bug "in less than a minute" ([write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/lnd-onion-bomb.md)).
- **Idempotency** (a repeated request takes effect once): the sender makes the ID and saves it before sending ([TigerBeetle](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/coding/reliable-transaction-submission.md)).
- **A timeout is not a failure.** LNbits booked an in-flight payment as failed ([advisory](https://github.com/lnbits/lnbits/security/advisories/GHSA-3j4h-h3fp-vwww)).
- **Reconciliation** (checking your books against the other side's own record): nodes list each payment's hash, fee and *preimage*, the secret revealed when a payment completes ([LND](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)).
- **Old versions carry known theft bugs.** Fixes ship quietly, details come months later ([example](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/lnd-excessive-failback-exploit.md)).
- **No simple rollback.** Restoring an old LND channel database "should never be done" ([LND safety](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/safety.md)).
- **Gap.** No public post-mortem was found where routine reconciliation caught a Lightning or ecash discrepancy before a loss; the nearest case was found as a vulnerability ([advisory](https://github.com/lnbits/lnbits/security/advisories/GHSA-3j4h-h3fp-vwww)).

## Method and limits

Sources were read on 2026-11-20. The research session's network allowed GitHub but blocked most other sites, so non-GitHub sources (Stripe, Google SRE, Monzo, the Money-pattern book, Modern Treasury, Adyen, regulators, press) are known only from search excerpts; every such claim is marked "(unverified: search excerpt only)".
Where a blocked site's content was read from the GitHub repository it is built from (PagerDuty's incident docs, Bitcoin Optech, a Lightning security researcher's disclosure blog, Core Lightning docs, bitcoincore.org, the IETF idempotency draft, the idempotency-keys articles, Hypothesis docs) or from a GitHub archive mirror (the Cashu HTLC disclosure), the link goes to that copy and the source list says so.
Limits: pages were read through a tool that returns summaries with quotations; Cashu and Fedimint links are pinned to the commits read and were built from commit and path, not each opened; this report uses only what the research notes contain, and reasoning that no source states is labelled "Inference:".

## Checklist before releasing any tool that touches payments

Each item is a check a small team can tick. "Documented" means a source states the practice; "Inference" means the item is the team's adaptation of what the sources show.

Terms used below: an *HTLC* is one in-flight part of a Lightning payment; in Cashu a *proof* is one ecash token, a *quote* is the mint's record of a requested payment, a *keyset* is one set of the mint's signing keys, a *swap* exchanges tokens for fresh ones, and a *melt* spends tokens to make the mint pay a Lightning invoice ([NUT-00](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/00.md), [NUT-05](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/05.md), [BOLT 2](https://github.com/lightning/bolts/blob/master/02-peer-protocol.md)).

### Test networks and harnesses

- [ ] **The automated suite runs on regtest against the real node programs DubPay must work with.** Inference: no source tells an application team this directly; the precedents are Core Lightning's tests, which "set up a mini-regtest environment and test `lightningd` as a whole" ([CLN testing](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/contribute-to-core-lightning/testing.md)), and an application project keeping a three-implementation regtest stack for its own runs ([LNbits regtest](https://raw.githubusercontent.com/lnbits/legend-regtest-enviroment/main/README.md)).
- [ ] **A fake Lightning backend exists and can be scripted to succeed, fail, hang then succeed, hang then fail, and return an error on pay or on status check.** Documented: both Cashu mints script these outcomes per invoice ([Nutshell tests](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/mint/test_mint_fake_invoice_states.py), [CDK fake wallet](https://github.com/cashubtc/cdk/blob/a982d66c0d1b1de345a86f8faa14390c8aefdc28/crates/cdk-fake-wallet/README.md)).
- [ ] **The suite runs on every database the tool supports.** Documented: Nutshell runs all tests on SQLite and PostgreSQL ([Nutshell CI](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.github/workflows/ci.yml)); CDK on memory, SQLite, redb and PostgreSQL ([CDK CI](https://github.com/cashubtc/cdk/blob/a982d66c0d1b1de345a86f8faa14390c8aefdc28/.github/workflows/ci.yml)).
- [ ] **Node and mint versions in the test network are pinned.** Documented: the Cashu regtest stack pins images "by multiarchitecture manifest digest" and Nutshell pins the stack's commit ([cashu-regtest](https://raw.githubusercontent.com/callebtc/cashu-regtest/main/README.md), [Nutshell workflow](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.github/workflows/regtest-mint.yml)).
- [ ] **Tests also run against released versions of the other side, and a nightly job runs against its newest build.** Documented: Nutshell tests its wallet against older released mints ([workflow](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.github/workflows/wallet-compatibility.yml)); cashu-ts runs nightly against `:latest` images "to catch upstream drift the day it ships" ([workflow](https://github.com/cashubtc/cashu-ts/blob/main/.github/workflows/nightly-mint-drift.yml)).
- [ ] **Every test ends by checking nothing is left over, and by saving and reloading state.** Documented: LND's harness checks for leftover mempool transactions or open channels ([lntest](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lntest/README.md)); LDK reloads every node's state when a test node is dropped ([LDK test utilities](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/functional_test_utils.rs)).
- [ ] **A restart is tested in each pending state, for each answer the backend can give (success, failure, still pending, error).** Documented: Nutshell's startup tests are named for exactly these cases ([test file](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/mint/test_mint_init.py)).
- [ ] **A deliberately dishonest test peer exists (wrong amount, wrong keyset, extra or missing signature).** Documented, with one secondary source: a CDK wallet fix added regression tests for invalid amount, keyset and signature counts ([CDK PR #2547](https://github.com/cashubtc/cdk/pull/2547)); a third-party issue says the earlier mock mint "returned honest responses" ([issue](https://github.com/Amperstrand/cashu-audit/issues/36)).
- [ ] **Results from a mocked network are not counted as covering reserves, on-chain fees or dust.** Inference from SimLN's own list of what its mocked mode does not model ([SimLN](https://raw.githubusercontent.com/bitcoin-dev-project/sim-ln/main/README.md)).
- [ ] **Upgrade and downgrade are tested, not assumed.** Documented: Core Lightning CI has a "Check we can downgrade the node" job ([CLN CI](https://raw.githubusercontent.com/ElementsProject/lightning/master/.github/workflows/ci.yaml)); Fedimint runs upgrade tests daily and on pull requests ([workflow](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/.github/workflows/upgrade-tests.yml)).
- [ ] **Test-only settings cannot reach a release.** Inference from two documented facts: LND built for integration tests runs different code ([lntest](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lntest/README.md)), and one LND flag "is only used for integration tests and should never be used on mainnet" ([LND safety](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/safety.md)).
- [ ] **Public test networks are used only for trials with other parties, never as proof that money is safe.** Inference from BIP 325, which says regtest "is not suitable for longer-term scenarios involving multiple independent parties" and that signet aims at "a predictable amount of unreliability" ([BIP 325](https://raw.githubusercontent.com/bitcoin/bips/master/bip-0325.mediawiki)).

### Invariants (rules that must always hold)

- [ ] **"No money created or lost" is written as one equation and asserted at every state change.** Documented: "The mint checks the following equation: `sum(inputs) - fees == sum(outputs)`" ([NUT-02](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/02.md)); Fedimint asserts it inside the transaction that makes each change ([engine](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/fedimint-server/src/consensus/engine.rs)).
- [ ] **Amounts are whole numbers in the smallest unit; no floating point anywhere.** Documented: NUT-02 says floating-point rounding "is not recommended ... due to the non-deterministic behavior of floating point division" ([NUT-02](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/02.md)); TigerBeetle: "calculations should be performed on the integers" ([data modeling](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/coding/data-modeling.md)).
- [ ] **Each unit (millisatoshi, satoshi, a mint's unit) is its own type, and every conversion names its rounding direction.** Documented in Core Lightning, whose conversion is named `amount_msat_to_sat_round_down` ([fuzz-amount-arith](https://github.com/ElementsProject/lightning/blob/master/tests/fuzz/fuzz-amount-arith.c)). Inference: applying this to DubPay's types.
- [ ] **Sums use checked addition, the running total is range-checked after each addition, and there is a hard maximum.** Documented: Bitcoin Core range-checks each output and the running total under a comment naming CVE-2010-5139 ([tx_check.cpp](https://github.com/bitcoin/bitcoin/blob/master/src/consensus/tx_check.cpp)).
- [ ] **Zero, negative and finer-than-smallest-unit amounts are rejected.** Documented: BOLT 2 "MUST offer `amount_msat` greater than 0" ([BOLT 2](https://github.com/lightning/bolts/blob/master/02-peer-protocol.md)); BOLT 11 readers must fail sub-millisatoshi amounts ([BOLT 11](https://github.com/lightning/bolts/blob/master/11-payment-encoding.md)).
- [ ] **Every remainder rule is written as an integer formula plus an ordering rule plus a worked example, with the rounding direction stated by DubPay itself.** Inference, modelled on NUT-02's `(sum_fees + 999) // 1000` ([NUT-02](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/02.md)) and NUT-08's "leading blank outputs ... in the same order" ([NUT-08](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/08.md)); needed because BOLT 7 gives a fee formula with no rounding sentence ([BOLT 7](https://github.com/lightning/bolts/blob/master/07-routing-gossip.md)).
- [ ] **A property test checks that any split adds up to the total and that the same inputs in the same order always give the same parts.** Inference; the guarantee to copy is RubyMoney's "The total of the allocated amounts will always equal the original amount" ([allocation.rb](https://github.com/RubyMoney/money/blob/main/lib/money/money/allocation.rb)).
- [ ] **Every amount, in every unit, survives format-then-parse unchanged.** Documented: Core Lightning asserts every formatted amount parses again ([fuzz-amount](https://github.com/ElementsProject/lightning/blob/master/tests/fuzz/fuzz-amount.c)); Bitcoin Core does the same ([integer fuzz target](https://github.com/bitcoin/bitcoin/blob/master/src/test/fuzz/integer.cpp)).
- [ ] **One stateful test drives random sequences of operations against a simple model and checks the conservation rule after every step; failing seeds are committed.** Documented as a method by Hypothesis ([stateful docs](https://github.com/HypothesisWorks/hypothesis/blob/master/hypothesis/docs/stateful.rst)) and proptest, which saves "a seed that can be used to deterministically repeat the found case" ([proptest](https://github.com/proptest-rs/proptest/blob/main/book/src/proptest/state-machine.md)). Inference: adopting it for DubPay.
- [ ] **Any amount that arrives from the other side is compared with what was agreed before acting on it.** Inference from fixes of this kind: LDK paid the amount in a returned invoice instead of the amount intended ([LDK changelog](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/CHANGELOG.md)); the CDK wallet stored mint-supplied amounts unchecked ([CDK PR #2547](https://github.com/cashubtc/cdk/pull/2547)).
- [ ] **Conservation is computed on amounts actually received, and overpayment has a named destination.** Inference: BOLT 11 says a payee "SHOULD accept up to twice the expected `amount`" ([BOLT 11](https://github.com/lightning/bolts/blob/master/11-payment-encoding.md)), so received can differ from invoiced.
- [ ] **Issued never exceeds paid, tested as a rule.** Documented: "`amount_issued` MUST NOT exceed `amount_paid`" ([NUT-04](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/04.md)).
- [ ] **The team has decided, in writing, whether a broken invariant halts the tool, and has measured how often the halt fires falsely.** Inference from three documented positions: TigerBeetle, "it is far better to stop operating than to continue operating in an incorrect state" ([VOPR](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md)); Fedimint halts ([server core](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/fedimint-server-core/src/lib.rs)); Nutshell turned a halt-on-error feature off by default because it "triggers in too many unrelated cases" ([releases](https://github.com/cashubtc/nutshell/releases?page=2)).
- [ ] **Every "counted exactly once" check has a named test that fails if the check is removed.** Inference from CVE-2018-17144, where a duplicate-input check was skipped as an optimisation ([Bitcoin Core disclosure](https://github.com/bitcoin-core/bitcoincore.org/blob/master/_posts/en/posts/2018-09-20-notice.md)).
- [ ] **Amounts crossing between Rust and TypeScript are tested at the largest values.** Inference only (no source on JavaScript number precision was consulted); the nearest documented fact is a NUT-01 test vector whose amount is "one unit over what can fit into a 64-bit signed integer" ([NUT-01 vectors](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/tests/01-tests.md)).

### Parsers and fuzzing

- [ ] **Every reader of untrusted input has a fuzz test: invoices, bech32 strings, Cashu tokens in both forms, amount strings, payment links.** Documented as a rule: "Any API that consumes untrusted inputs should be fuzz tested" ([CLN invoice parsing write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/cln-invoice-parsing.md)). Inference: the list of DubPay's inputs.
- [ ] **Fuzz tests assert round trip (decode, encode, decode gives the same thing), not only "does not crash".** Documented: LDK asserts "Our data serialization is loss-less" ([bolt11_deser](https://github.com/lightningdevkit/rust-lightning/blob/main/fuzz/src/bolt11_deser.rs)); LND reads, writes and reads each message again ([lnwire fuzz](https://github.com/lightningnetwork/lnd/blob/master/lnwire/fuzz_test.go)).
- [ ] **Inputs that once caused a failure are kept in the repository and replayed on every change.** Documented: Core Lightning replays checked-in corpora as a regression check ([CLN testing](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/contribute-to-core-lightning/testing.md)); Bitcoin Core tests every pull request against its corpus repository ([fuzzing.md](https://github.com/bitcoin/bitcoin/blob/master/doc/fuzzing.md)).
- [ ] **Someone has confirmed the memory and undefined-behaviour checkers are really switched on in CI.** Documented: two Core Lightning bugs were missed because one checker was misconfigured locally and "accidentally disabled" in CI ([write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/cln-invoice-parsing.md)).
- [ ] **The fuzzer is helped past checksums.** Documented: plain fuzzers "get stuck at the bech32 decoding stage" ([write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/cln-invoice-parsing.md)); LND's invoice fuzz test adds a valid prefix and checksum ([zpay32 fuzz](https://github.com/lightningnetwork/lnd/blob/master/zpay32/fuzz_test.go)).
- [ ] **No fuzz finding is waved through without a written reason.** Inference from the same write-up, where a real bug was first dismissed and hard-coded as an exception ([write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/cln-invoice-parsing.md)).
- [ ] **Every size and length supplied by the other side has a limit, with a test.** Inference from two documented failures: Nutshell did "not validate the size of preimage" ([advisory](https://github.com/advisories/GHSA-xwrw-2crp-46q4)); LND trusted a length field up to 4 GB ([onion bomb](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/lnd-onion-bomb.md)).
- [ ] **HTTP endpoints are fuzzed with a fixed list of acceptable status codes.** Documented: Nutshell fuzzes every mint endpoint and allows only `[400, 404, 405, 422, 503]` ([test file](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/fuzz/test_fuzz_mint_api.py)).
- [ ] **Long fuzz runs are scheduled outside CI.** Documented: LDK says crashes found in CI's short runs are ones "caused relatively easily" ([fuzz README](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/fuzz/README.md)).
- [ ] **Where parsing is delegated to a library, DubPay's reading of amount, expiry and payee is compared with a second library.** Inference from differential fuzzing results, e.g. Core Lightning accepting invoice fallback addresses that LND and LDK rejected ([CLN PR #8219](https://github.com/ElementsProject/lightning/pull/8219), [bitcoinfuzz](https://github.com/bitcoinfuzz/bitcoinfuzz)).
- [ ] **Published test vectors are run, including the ones that must fail.** Documented: NUT-00 vectors include malformed tokens that must be rejected ([NUT-00 vectors](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/tests/00-tests.md)); the BOLT process says "test vectors are necessary" for new constructions ([BOLT process](https://raw.githubusercontent.com/lightning/bolts/master/CONTRIBUTING.md)).
- [ ] **Mutation testing (deliberately breaking the code to see whether tests notice) runs on a schedule for money code.** Documented: weekly in CDK ([workflow](https://github.com/cashubtc/cdk/blob/a982d66c0d1b1de345a86f8faa14390c8aefdc28/.github/workflows/mutation-testing-weekly.yml)), scheduled in Nutshell ([workflow](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.github/workflows/_mutation-profile.yml)) and cashu-ts ([workflow](https://github.com/cashubtc/cashu-ts/blob/main/.github/workflows/mutation-testing-weekly.yml)).

### Idempotency and unknown outcomes

- [ ] **The sender creates the payment ID, saves it before sending, and reuses it on every retry.** Documented: "This `id` should be persisted locally before submission, and the same `id` should be used for subsequent retries" ([TigerBeetle](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/coding/reliable-transaction-submission.md)).
- [ ] **The same ID with a different amount or destination is a distinct, loud error.** Documented: the IETF draft says a key "MUST NOT be reused with another request with a different request payload" ([IETF draft](https://raw.githubusercontent.com/ietf-wg-httpapi/idempotency/main/draft-ietf-httpapi-idempotency-key-header.md)); Core Lightning error 201 is "Already paid with this *hash* using different amount or destination" ([pay schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/pay.json)).
- [ ] **For each retry-safe operation these five answers are written down: who the key is scoped to; how long it is honoured; what happens on same key with different content; what happens while the first call still runs; which outcomes are stored.** Inference built on the structure of the IETF draft ([IETF draft](https://raw.githubusercontent.com/ietf-wg-httpapi/idempotency/main/draft-ietf-httpapi-idempotency-key-header.md)).
- [ ] **DubPay keeps its own durable record of "have I paid this hash", and does not rely on the node to remember.** Documented for LDK: "you should implement your own tracking of payments, including state to indicate once a payment has completed" ([channelmanager.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/channelmanager.rs)).
- [ ] **A timeout leaves the payment pending with funds reserved, and the next step is to ask the rail.** Documented: "Once HTLCs are in flight, the payment will not be aborted until the HTLCs are either settled or failed" ([LND router.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/routerrpc/router.proto)); the LNbits advisory describes the loss when this is ignored ([advisory](https://github.com/lnbits/lnbits/security/advisories/GHSA-3j4h-h3fp-vwww)).
- [ ] **A test delays settlement past DubPay's own timeout, then settles, and checks the books stayed "pending".** Inference from the LNbits advisory ([advisory](https://github.com/lnbits/lnbits/security/advisories/GHSA-3j4h-h3fp-vwww)); Nutshell has tests of this shape, e.g. `test_pending_invoice_settles_on_check` ([test file](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/mint/test_mint_fake_invoice_states.py)).
- [ ] **No second payment is started while the first one's outcome is unknown.** Documented for mints: "Payments awaiting a definitive backend result remain pending" and recovery happens "without sending another payment" ([Nutshell README](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/README.md)).
- [ ] **Event handlers can run twice safely, and each integration's delivery guarantee is written down.** Documented: LDK, "Event handling must be idempotent - in effect, Events may be replayed" ([events](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/events/mod.rs)); LND's HTLC events are "best-effort ... delivery is not guaranteed" ([router.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/routerrpc/router.proto)).
- [ ] **After a disconnect, DubPay catches up from a stored index, not from "latest".** Documented: LND's invoice subscription replays from a given index ([lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)); Core Lightning's `waitanyinvoice` loop "ensures that no paid invoice is missed" ([schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/waitanyinvoice.json)).
- [ ] **For Cashu, the exact request (including its blinded outputs) is saved before sending, and recovery does not depend on the mint's response cache alone.** Inference from NUT-19, which keys the cache on method, path and payload ([NUT-19](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/19.md)), and Nutshell's statement that the cache "does not guarantee recovery after eviction, restart, or a retry routed to another worker" ([caching doc](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/docs/response-caching.md)); the fallbacks are state checks ([NUT-07](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/07.md)) and restore ([NUT-09](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/09.md)).
- [ ] **Older answers never overwrite newer ones.** Documented: wallets "MUST NOT replace locally stored quote data with a response whose `updated_at` is lower" ([NUT-04](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/04.md)).
- [ ] **Incoming money is credited from the amounts of finished payment parts, not from an invoice's status word.** Documented on LND's development branch: "Check the relevant finalized successful HTLC amounts before crediting" ([lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)).
- [ ] **The preimage is stored as the receipt for every outgoing payment.** Documented: "this serves as a payment receipt, if you wish to have such a thing, you must store it somehow!" ([LDK events](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/events/mod.rs)).
- [ ] **Records of payments still in flight cannot be deleted.** Documented: LND "will not attempt to delete an In-Flight payment, since that would be unsafe" ([lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)); Core Lightning deletes only finished ones ([delpay](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/delpay.json)).
- [ ] **Two identical requests at the same moment are tested (same quote, same invoice).** Documented: CDK has `test_concurrent_melt_same_invoice` and `test_fake_mint_concurrent_same_quote_different_outputs` ([test file](https://github.com/cashubtc/cdk/blob/a982d66c0d1b1de345a86f8faa14390c8aefdc28/crates/cdk-integration-tests/tests/fake_wallet.rs)); Nutshell fixed "double-execution of melt quotes for the same invoice" ([releases](https://github.com/cashubtc/nutshell/releases?page=2)).
- [ ] **Operations that cannot be completed land in a list a person reads.** Documented: put them "in a list somewhere so that a human can find out what failed" ([idempotency-keys article](https://raw.githubusercontent.com/brandur/sorg/master/content/articles/idempotency-keys.md)).

### Reconciliation

- [ ] **DubPay's books are compared with the rail's own records (the node's payment list, the mint's quote and proof states), not with DubPay's saved copy of them.** Inference; the rail records exist ([LND lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto), [NUT-07](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/07.md)). The only source for the "independent record" principle is Monzo (unverified: search excerpt only) ([Monzo](https://monzo.com/blog/2022/02/18/how-we-calculate-balances)).
- [ ] **For each outgoing payment the check covers status, amount, fee, and that the stored preimage hashes to the payment hash.** Inference from the fields LND reports per payment ([lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)) and BOLT 11's "Preimage of this provides proof of payment" ([BOLT 11](https://github.com/lightning/bolts/blob/master/11-payment-encoding.md)).
- [ ] **Fees are booked as their own entries.** Documented: Faraday's reports give fees separate entries that reference the payment ([Faraday accounting](https://raw.githubusercontent.com/lightninglabs/faraday/master/docs/accounting.md)).
- [ ] **A balance-level check exists as well as an item-by-item one, and it counts unsettled payments and channels that are opening or closing.** Inference from what the node reports separately ([lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)) and Faraday's "Known Omissions" ([Faraday accounting](https://raw.githubusercontent.com/lightninglabs/faraday/master/docs/accounting.md)).
- [ ] **An automatic "liabilities never exceed backing" check runs continuously.** Documented in three forms: Fedimint in consensus ([engine](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/fedimint-server/src/consensus/engine.rs)); Nutshell's optional watchdog ([watchdog.py](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/cashu/mint/watchdog.py)); Core Lightning's bookkeeper logs a **BROKEN** line when an account's debits exceed credits ([schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/bkpr-listbalances.json)).
- [ ] **Unmatched items are held under a named status with an owner; nothing is force-matched.** Only unverified sources state this for reconciliation: Modern Treasury says ambiguous matches "won't be automatically reconciled" (unverified: search excerpt only) ([Modern Treasury](https://docs.moderntreasury.com/payments/docs/exception-handling-manual-reconciliation)). The verified neighbour is the human-readable failure list above ([idempotency-keys article](https://raw.githubusercontent.com/brandur/sorg/master/content/articles/idempotency-keys.md)).
- [ ] **Reconciliation runs at least daily.** Only unverified sources support a cadence: Monzo's daily job and the UK client-money rule (unverified: search excerpt only) ([Monzo](https://monzo.com/blog/2022/02/08/processing-payments-safely-at-scale), [FCA CASS 7.15](https://handbook.fca.org.uk/handbook/CASS/7/15.html)).
- [ ] **Pending outgoing payments are re-checked in the background on a timer.** Documented: "Mints now check pending melt quotes in the background every hour" ([Nutshell releases](https://github.com/cashubtc/nutshell/releases?page=2)).
- [ ] **Before anyone resolves a stuck payment by hand, they confirm the real outcome with the Lightning backend.** Documented: "verify the current payment outcome with the Lightning backend" ([Nutshell README](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/README.md)).
- [ ] **Records are append-only; a correction is a new entry.** Documented: in Core Lightning's bookkeeper "no previously emitted event will be subsequently updated, rather we add a new event" ([schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/bkpr-listaccountevents.json)).

### Release and rollback

- [ ] **The database is backed up and all old workers are stopped before every upgrade.** Documented: "Back up your databases and stop all older mint workers before upgrading" ([Nutshell releases](https://github.com/cashubtc/nutshell/releases)).
- [ ] **The release notes say whether the step can be undone, and the upgrade was rehearsed on a throwaway copy.** Inference from LND's `dry-run-migration` setting, which leaves the database "still compatible with the previously active version" only if the migration is not committed ([sample config](https://raw.githubusercontent.com/lightningnetwork/lnd/master/sample-lnd.conf)).
- [ ] **No one will ever restore an old Lightning channel database; the runbook names what is backed up instead.** Documented: "having an old state of a channel basically means forfeiting the balance to the other party" ([LND safety](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/safety.md)); Core Lightning: snapshot backups are "discouraged, as any loss of state may result in permanent loss of funds" ([CLN backup](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/beginners-guide/backup.md)).
- [ ] **The same seed never runs on two nodes.** Documented: "You should never run two different `lnd` nodes with the same seed!" ([LND safety](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/safety.md)).
- [ ] **Each dependency is on a maintained version line, on its latest minor release, and someone is subscribed to its security announcements.** Documented: "A maintained line only protects you if you are on its latest minor release" ([LND SECURITY](https://raw.githubusercontent.com/lightningnetwork/lnd/master/SECURITY.md)); Optech recommends signing up for security announcements ([Optech 2022-10-19](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_posts/en/newsletters/2022-10-19-newsletter.md)).
- [ ] **Someone reads each dependency's release notes, not only its advisories page.** Inference: Nutshell and CDK had no published repository advisories on 2026-11-20 ([Nutshell](https://github.com/cashubtc/nutshell/security/advisories), [CDK](https://github.com/cashubtc/cdk/security/advisories)) although their release notes list fund-safety fixes ([Nutshell releases](https://github.com/cashubtc/nutshell/releases?page=2)).
- [ ] **Releases are signed, built as a draft, checked, then published; a published tag is never replaced.** Documented: "Do not delete or replace a real tag or a published release" ([LND release.md](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/release.md)).
- [ ] **The package is installed from scratch before it is published.** Documented: Nutshell "Added clean-install validation before package publishing" ([releases](https://github.com/cashubtc/nutshell/releases)).
- [ ] **The compatibility tests against older versions pass before a release is published.** Documented: "Wait for tests to pass before publishing" ([Fedimint release process](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/docs/release-process.md)).
- [ ] **A second person checks each deployment.** Only an unverified source supports this: the SEC order on Knight Capital (unverified: search excerpt only) ([SEC](https://www.sec.gov/files/litigation/admin/2013/34-70694.pdf)).
- [ ] **The rollback itself has been tried.** Only an unverified source supports this: Stripe's 2019 analysis, in which a rollback caused the second outage (unverified: search excerpt only) ([Stripe RCA](https://stripe.com/rcas/2019-07-10)).
- [ ] **While the tool is new there is a hard cap on amounts, a label on the release, and unfinished features are held back.** Inference from LND's default channel-size limit that needs a deliberate opt-in to raise ([sample config](https://raw.githubusercontent.com/lightningnetwork/lnd/master/sample-lnd.conf)), Nutshell's `MINT_MAX_BALANCE` ([.env.example](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.env.example)) and CDK's "ALPHA" label ([CDK README](https://raw.githubusercontent.com/cashubtc/cdk/main/README.md)).
- [ ] **Where behaviour is deliberately cautious, a comment says why, and a regression test protects it.** Documented: "A single comment in the code would likely have been enough to prevent later contributors from introducing the buggy behavior" ([LDK disclosure](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/ldk-duplicate-htlc-force-close-griefing.md)).

### Incident readiness

- [ ] **A SECURITY file gives a private contact, says which versions get fixes, and asks for no exploit detail in public.** Documented: "Do not include exploit details in public places: issues, pull requests ..., commit messages, or code comments" ([Nutshell SECURITY](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/SECURITY.md)); BTCPay adds target times ([BTCPay SECURITY](https://raw.githubusercontent.com/btcpayserver/btcpayserver/master/SECURITY.md)).
- [ ] **Severity levels are written down in advance; when unsure, the higher one is used.** Documented: "If you are unsure which level an incident is ... treat it as the higher one" ([PagerDuty severity levels](https://raw.githubusercontent.com/PagerDuty/incident-response-docs/master/docs/before/severity_levels.md)).
- [ ] **One named person runs each incident and does not do the fixing.** Documented: "You should not be performing any actions or remediations, checking graphs, or investigating logs" ([PagerDuty incident commander](https://raw.githubusercontent.com/PagerDuty/incident-response-docs/master/docs/training/incident_commander.md)).
- [ ] **A blame-free post-mortem template is ready: timeline with evidence for each entry, impact, cause, how it could have been caught, customer message, a few follow-ups; review within days.** Documented ([PagerDuty post-mortem process](https://raw.githubusercontent.com/PagerDuty/incident-response-docs/master/docs/after/post_mortem_process.md)).
- [ ] **Impact is stated as money at risk and money lost, not only users affected.** Inference; Fedimint asks reporters to say "What an attacker can do with it (steal funds, ...)" ([Fedimint SECURITY](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/SECURITY.md)).
- [ ] **There is a "stop taking new payments" switch that does not depend on rolling anything back.** Inference from LND's 2022 advisory workaround ([advisory](https://github.com/lightningnetwork/lnd/security/advisories/GHSA-hc82-w9v8-83pr)) and Nutshell's switches to disable minting or melting ([.env.example](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.env.example)).
- [ ] **An advisory template says plainly: can funds be lost, which versions, what to do now, what to do if you cannot update yet.** Inference from LND's advisory ([advisory](https://github.com/lightningnetwork/lnd/security/advisories/GHSA-hc82-w9v8-83pr)) and Bitcoin Core's format ([example](https://raw.githubusercontent.com/bitcoin-core/bitcoincore.org/master/_posts/en/posts/2024-07-03-disclose-unbounded-banlist.md)).
- [ ] **The plan covers stolen credentials: rotating keys and moving funds, not only updating.** LNbits' urgent release "Rotates auth keys" ([LNbits releases](https://github.com/lnbits/lnbits/releases)); the fuller lesson, that updating does not undo stolen node credentials, rests on BTCPay's posts (unverified: search excerpt only) ([BTCPay blog](https://blog.btcpayserver.org/btcpay-server-security-incident-response-and-next-steps/)).
- [ ] **Node downtime is treated as a money risk: it is monitored, and significant funds have a watchtower on a separate machine.** Documented: "it's cheap insurance to run a private watchtower on a separate machine" ([fake channels write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/fake-channel-dos.md)); LND recommends regular monitoring ([LND safety](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/safety.md)).
- [ ] **Every incident ends with a permanent test.** Documented: "If a stress test based on the DoS program had been added to CLN's CI pipeline or release process, this vulnerability could have been caught much earlier" ([write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/cln-channel-open-race.md)).
- [ ] **Alerts reach a person who knows what they mean, and the health check exercises the real path.** Only unverified sources support this: Knight's 97 unheeded emails and Monzo's write-and-read-back check (unverified: search excerpt only) ([SEC](https://www.sec.gov/files/litigation/admin/2013/34-70694.pdf), [Monzo](https://monzo.com/blog/2019/09/08/why-monzo-wasnt-working-on-july-29th/)).
- [ ] **A disclosure deadline is agreed with anyone who reports a bug.** Documented from the reporter's side: "Set disclosure deadlines to improve security outcomes" ([write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/lnd-replacement-stalling-attack.md)).

## How each project tests

### LND: real node processes driven by a harness, with flake hunting built in

LND's integration suite starts real `lnd` processes and steers them with a harness that is responsible for "managing `lnd` nodes, chain backends and miners, advancing nodes' states and providing assertions" ([lntest README](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lntest/README.md)). In plain terms: a test opens channels, makes payments and mines blocks on a private chain, then checks what the nodes report. Each test case runs with its own harness and a cleanup step that looks for leftover state such as mempool transactions or open channels ([lntest README](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lntest/README.md)). The suite can run against several chain backends (btcd by default, neutrino, or bitcoind in three modes) and three databases (bbolt by default, etcd, postgres) ([itest README](https://raw.githubusercontent.com/lightningnetwork/lnd/master/itest/README.md)).

Two details matter for anyone copying the approach. First, the program under integration test is not identical to the released one: with the integration build flag LND uses a faster polling interval, weaker key-stretching parameters and different protocol defaults ([lntest README](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lntest/README.md)). Second, intermittent failures ("flakes") get their own tooling: documented targets repeat unit tests, the whole integration suite, or one case in parallel until something fails, and the test directory keeps a flakes file, an exclusion list and a log-error check beside the tests ([MAKEFILE.md](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/MAKEFILE.md), [itest directory](https://github.com/lightningnetwork/lnd/tree/master/itest)). File names in the directory show the categories covered: channel opening, cooperative and force close, breach, payments including multi-part, multi-hop routing, backup and recovery, fee bumping and sweeping, and data migrations ([itest directory](https://github.com/lightningnetwork/lnd/tree/master/itest)). LND fuzzes four packages by default: the transport handshake, wire messages, watchtower messages and invoice parsing ([fuzz.md](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/fuzz.md)).

Inference: no file named for "restart" appears in the listing; restart behaviour seems to be exercised inside other cases, which was not confirmed by opening them ([itest directory](https://github.com/lightningnetwork/lnd/tree/master/itest)).

### Core Lightning: four layers, run several times over

Core Lightning documents source checks, unit tests, "blackbox" tests that "set up a mini-regtest environment and test `lightningd` as a whole", and fuzz targets with stored inputs ([testing.md](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/contribute-to-core-lightning/testing.md)). Its test library provides fixtures that "allow the management of a test network of a given topology" and is also used by community plugins ([pyln-testing](https://raw.githubusercontent.com/ElementsProject/lightning/master/contrib/pyln-testing/README.md)).

The continuous-integration file shows the same blackbox suite run in many forms: plain, under Valgrind (a memory-error detector), under address and undefined-behaviour sanitizers, on PostgreSQL, on Liquid, against the minimum supported Bitcoin Core version, and as a downgrade check against the previous release; a fuzz-regression job replays the stored inputs ([CI workflow](https://raw.githubusercontent.com/ElementsProject/lightning/master/.github/workflows/ci.yaml)). The docs give an order of preference when Valgrind complains about code the project does not control: add a suppression, exclude the third-party process, and only last skip the test ([testing.md](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/contribute-to-core-lightning/testing.md)).

A separate tool, lnprototest, tests an implementation against the protocol text itself. Tests are built from events (send this message, expect that one), must quote the specification text they test ("This is vital to make your tests readable, and to ensure they change with the spec"), and reviewers are asked "Does your test check failures as well as successes?" ([HACKING.md](https://raw.githubusercontent.com/rustyrussell/lnprototest/master/HACKING.md)). "So far, core-lightning is supported" ([README](https://raw.githubusercontent.com/rustyrussell/lnprototest/master/README.md)).

### LDK: a whole network inside one test, plus fuzzers aimed at ordering and saving

LDK is a library, and its tests build several nodes and a simulated chain inside one test program. Its contributor guide says "Any bug may cost users real money", that every new feature should have functional tests, and that "Fuzzing is heavily encouraged" ([CONTRIBUTING](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/CONTRIBUTING.md)). The shared test utilities pick one of eleven ways of telling a node about new blocks at random on each run (including duplicated and out-of-order confirmations), and when a test node is discarded they assert there are no unprocessed events and then save, reload and compare the node's state ([functional_test_utils.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/functional_test_utils.rs)). So every functional test is also a save-and-reload test.

Two fuzz targets go beyond parsing. `full_stack` aims to "Test that no series of bytes received over the wire/connections created/payments sent can result in a crash" ([full_stack.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/fuzz/src/full_stack.rs)). `chanmon_consistency` connects three nodes and lets the random input choose actions, including what the storage layer answers; the test fails "if any action results in a channel being force-closed" ([chanmon_consistency.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/fuzz/src/chanmon_consistency.rs)). LDK states the limit of its own practice: crashes found in CI's short fuzz runs are ones "caused relatively easily" ([fuzz README](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/fuzz/README.md)).

LDK Node, the ready-made node built on LDK, tests against real programs: its integration tests "require Bitcoin Core and Esplora-enabled `electrs` binaries" ([README](https://raw.githubusercontent.com/lightningdevkit/ldk-node/main/README.md)), and it keeps separate test files and CI workflows for interoperability with Core Lightning, LND and Eclair, plus upgrade/downgrade tests and a property-based chain-reorganisation test with saved failing cases ([tests directory](https://github.com/lightningdevkit/ldk-node/tree/main/tests), [workflows](https://github.com/lightningdevkit/ldk-node/tree/main/.github/workflows)).

Inference: LDK makes ordering and persistence the test subject; the random block delivery, the reload on every node drop and a fuzzer that varies storage answers all target two parties' records drifting apart after a crash or delay ([functional_test_utils.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/functional_test_utils.rs), [chanmon_consistency.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/fuzz/src/chanmon_consistency.rs)).

### Eclair: state-by-state suites, regtest integration, and a deliberately unreliable pipe

Eclair's tests are suites run through its build tool; a particular Bitcoin Core version can be selected for them ([BUILD.md](https://raw.githubusercontent.com/ACINQ/eclair/master/BUILD.md)). Integration tests start a real `bitcoind` on regtest and several Eclair nodes inside one process, wait until "all nodes have the same value" for block height, and stop bitcoind cleanly so its state is kept "for later debugging" ([IntegrationSpec](https://raw.githubusercontent.com/ACINQ/eclair/master/eclair-core/src/test/scala/fr/acinq/eclair/integration/IntegrationSpec.scala)). The channel tests include a `FuzzySpec` that pushes many payments with randomised amounts through an unreliable connection between two channel state machines; individual payments may fail, but all senders must finish within two minutes and both channels must end in a normal, offline or syncing state ([FuzzySpec](https://raw.githubusercontent.com/ACINQ/eclair/master/eclair-core/src/test/scala/fr/acinq/eclair/channel/FuzzySpec.scala)). The test tree also has directories for balance, database, payment, router and wire code ([test directory](https://github.com/ACINQ/eclair/tree/master/eclair-core/src/test/scala/fr/acinq/eclair), [channel tests](https://github.com/ACINQ/eclair/tree/master/eclair-core/src/test/scala/fr/acinq/eclair/channel), [integration tests](https://github.com/ACINQ/eclair/tree/master/eclair-core/src/test/scala/fr/acinq/eclair/integration)).

Inference: `FuzzySpec` is randomised stress testing, not coverage-guided fuzzing; the file that injects the faults was not opened ([FuzzySpec](https://raw.githubusercontent.com/ACINQ/eclair/master/eclair-core/src/test/scala/fr/acinq/eclair/channel/FuzzySpec.scala)). No prose document describing Eclair's testing approach was found; the above is read from build instructions and the test tree ([test directory](https://github.com/ACINQ/eclair/tree/master/eclair-core/src/test/scala/fr/acinq/eclair)). A 2024 presentation is reported to say Eclair then had no modern fuzz tests (unverified: search excerpt only) ([Brink slides](https://brink.dev/assets/files/2024-06-25-eng-fuzzing_ln.pdf)).

### Shared tools and test networks

The Lightning specification process requires "two independent implementations which successfully inter-operate" before a protocol change is accepted, and says "test vectors are necessary" for new low-level constructions ([BOLT process](https://raw.githubusercontent.com/lightning/bolts/master/CONTRIBUTING.md)). BOLT 3 carries test-vector appendices for transactions and keys ([BOLT 3](https://github.com/lightning/bolts/blob/master/03-transactions.md)).

| Tool | What it is, in its own words or by its README | Source |
|---|---|---|
| Polar | "One-click Bitcoin Lightning networks for local app development & testing"; desktop, regtest only; LND, Core Lightning, Eclair | [README](https://raw.githubusercontent.com/jamaljsr/polar/master/README.md) |
| Nigiri | Command-line regtest environment with a faucet; can start a Core Lightning node and an LND node | [README](https://raw.githubusercontent.com/vulpemventures/nigiri/master/README.md) |
| LNbits regtest stack | Three LND nodes, two Core Lightning nodes, one Eclair node; starts the network "and also run tests" | [README](https://raw.githubusercontent.com/lnbits/legend-regtest-enviroment/main/README.md) |
| Scaling Lightning | Kubernetes-based; "either a public signet Lightning Network or a private regtest network"; "still far from complete" | [README](https://raw.githubusercontent.com/scaling-lightning/scaling-lightning/main/README.md) |
| SimLN | Generates "realistic payment activity on any lightning network topology"; its mocked mode does not model channel reserves, on-chain fees or dust | [README](https://raw.githubusercontent.com/bitcoin-dev-project/sim-ln/main/README.md) |
| Warnet | Deploys Bitcoin networks to "Monitor and analyze the emergent behaviors"; can add a Lightning network | [README](https://raw.githubusercontent.com/bitcoin-dev-project/warnet/main/README.md) |

On choosing a network, the primary sources are direct. Regtest lets you "instantly create a brand-new private block chain" where "you choose when to create new blocks" ([developer.bitcoin.org source](https://raw.githubusercontent.com/bitcoin-dot-org/developer.bitcoin.org/master/examples/testing.rst)). Testnet "is notoriously unreliable" ([BIP 325](https://raw.githubusercontent.com/bitcoin/bips/master/bip-0325.mediawiki)), and testnet3 was replaced because "the fundamental principle of testnet coins having no value has been broken" ([BIP 94](https://raw.githubusercontent.com/bitcoin/bips/master/bip-0094.mediawiki)). Signet adds block signing to give "a predictable amount of unreliability" and is "more suitable for integration testing by organizations such as exchanges" ([BIP 325](https://raw.githubusercontent.com/bitcoin/bips/master/bip-0325.mediawiki)). Mutinynet is a custom signet with "30s block time" ([README](https://raw.githubusercontent.com/MutinyWallet/mutiny-net/master/README.md)).

Inference: every automated suite examined runs on regtest or, for LDK, a simulated chain; none of the fetched documents describes a public network as part of pre-merge testing ([CLN testing](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/contribute-to-core-lightning/testing.md), [IntegrationSpec](https://raw.githubusercontent.com/ACINQ/eclair/master/eclair-core/src/test/scala/fr/acinq/eclair/integration/IntegrationSpec.scala), [LDK test utilities](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/functional_test_utils.rs)). Inference: none of these networks reproduces real fee pressure by default; no primary source states this limit, it follows from how they are defined ([BIP 325](https://raw.githubusercontent.com/bitcoin/bips/master/bip-0325.mediawiki)).

### Cashu mints: Nutshell

Nutshell's CI runs the full suite against a fake Lightning backend on SQLite and PostgreSQL, then against real regtest nodes through four backend types on both databases ([CI workflow](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.github/workflows/ci.yml)). The regtest stack pins its node releases, has a dedicated fee topology (a routing node "charging 1 sat + 1,000 ppm"), and on every start "tests twelve real payments" where both sides "must report settlement with matching payment hashes and preimages" ([cashu-regtest](https://raw.githubusercontent.com/callebtc/cashu-regtest/main/README.md)). Interoperability runs both ways: the current wallet against older released mints ([workflow](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.github/workflows/wallet-compatibility.yml)), and the released CDK wallet against this mint at fee settings 0 and 100 ([workflow](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.github/workflows/cdk-wallet.yml)).

The fake backend is the tool for the hard cases. "For testing, you can use Nutshell without a Lightning backend" ([README](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/README.md)); it has settings for delays, forced payment states and exceptions ([settings.py](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/cashu/core/settings.py)), and one invoice can carry its own scripted behaviour, which is how tests such as `test_failing_invoice_releases_proofs` and `test_check_err_keeps_melt_pending` work ([test file](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/mint/test_mint_fake_invoice_states.py)). The suite has a fuzz directory using the Hypothesis library ([fuzz test](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/fuzz/test_fuzz_mint_api.py)), scheduled mutation testing ([workflow](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.github/workflows/_mutation-profile.yml)), and test files named for accounting, fees, migrations, shutdown and the watchdog ([tests directory](https://github.com/cashubtc/nutshell/tree/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests)).

Nutshell documents how it prevents the same ecash being used twice at once: database locks derived from each proof's identifier, "deduplicated, and acquired in sorted order", with "database uniqueness constraints" still applying ([proof coordination doc](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/docs/postgresql-proof-coordination.md)). Outgoing payments run under "a renewable database lease", and "After a lease expires, status polling or periodic reconciliation can claim recovery without sending another payment" ([README](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/README.md)).

Inference: scripting the fake backend per invoice is the practical way these projects test the "unknown outcome" branch without real nodes ([test file](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/mint/test_mint_fake_invoice_states.py)). Gap: no written test plan or coverage target was found; the structure is read from files and workflows ([tests directory](https://github.com/cashubtc/nutshell/tree/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests)).

Gap: no fuzz target that drives sequences of mint operations was found in CDK ([fuzz targets](https://github.com/cashubtc/cdk/tree/a982d66c0d1b1de345a86f8faa14390c8aefdc28/fuzz/fuzz_targets)).

### Fedimint: a solvency rule inside consensus, and a version matrix as a release gate

Fedimint's servers each ask every module for its assets and liabilities after processing each item, and "if liabilities > assets then an error has occurred in the database and consensus should halt" ([server core](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/fedimint-server-core/src/lib.rs)). The check runs inside the same database transaction as the change, with the message "Balance sheet of the fed has gone negative, this should never happen!" ([engine](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/fedimint-server/src/consensus/engine.rs)). Operators can read the balance sheet through an authenticated endpoint ([API docs](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/docs/api.md)).

Testing centres on `devimint`, a tool that starts a real local federation with Lightning nodes and gateways ([devimint](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/devimint/src/lib.rs)) and runs named scenarios, for example one "to ensure an already spent input cannot be replayed" ([script](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/scripts/tests/cannot-replay-tx.sh)). The full CI script lists scenarios for reconnection, gateway reboot, refunds of refused payments, duplicate payments, federation outage, backup and recovery, and latency ([test script](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/scripts/tests/test-ci-all.sh)); latency tests have regression limits ([regression tests](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/devimint/src/tests/regression_tests.rs)), and a load-test tool exists ([README](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/fedimint-load-test-tool/README.md)). Older versions are tested on every pull request against a 25% sample of combinations ([workflow](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/.github/workflows/ci-backwards-compatibility.yml)), and "Release testing runs the full matrix against each tag", including direct and sequential upgrades ([release process](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/docs/release-process.md)). Fuzz targets cover encoding and decoding of core types ([fuzzing doc](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/docs/fuzzing.md)). One server-side defence was added against client mistakes: the federation "will now reject attempt to reuse ecash blind nonces, preventing possibility of loss of funds even in the event of client-side bugs" ([changelog](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/CHANGELOG.md)).

Inference: because the audit compares internal records only, it detects accounting bugs, not theft of the underlying funds ([audit.rs](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/fedimint-core/src/module/audit.rs)).

## Invariants and remainder rules: the exact wording

### No money created or lost

The plain idea: what goes in, minus fees, equals what comes out. The precise statements found:

| Source | Rule as written |
|---|---|
| Cashu | "The mint checks the following equation: `sum(inputs) - fees == sum(outputs)`"; failure has error code 11005, "Transaction is not balanced" ([NUT-02](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/02.md), [error codes](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/error_codes.md)) |
| Cashu, minting | "`amount_issued` MUST NOT exceed `amount_paid`"; "Mints MUST NOT issue ecash whose total output amount exceeds `amount_paid - amount_issued`" ([NUT-04](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/04.md)) |
| Cashu, units | The mint "MUST reject a swap that mixes units" ([NUT-03](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/03.md)) |
| Fedimint | Summing over modules, "if liabilities > assets ... consensus should halt" ([server core](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/fedimint-server-core/src/lib.rs)) |
| TigerBeetle | "one invariant (every debit has an equal and opposite credit)"; "Money never appears from nowhere or disappears." ([debit-credit](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/concepts/debit-credit.md)) |
| Cardano formal spec | "the amount of created value ... equals the amount of destroyed value" (property "Preserve Balance"), with "Absence of Double-Spend" as a separate property ([properties.tex](https://github.com/IntersectMBO/cardano-ledger/blob/master/eras/shelley/formal-spec/properties.tex)) |
| Bitcoin Core | Each output and the running total must be in range; a repeated input is rejected ([tx_check.cpp](https://github.com/bitcoin/bitcoin/blob/master/src/consensus/tx_check.cpp)) |

Bitcoin's history supplies the two cautionary cases. The source code's maximum-amount constant is described as "a sanity check" against "a(nother) overflow bug that allowed for the creation of coins out of thin air" ([amount.h](https://github.com/bitcoin/bitcoin/blob/master/src/consensus/amount.h)). In 2018 a duplicate-input check dating from 2012 was skipped as an optimisation, leaving only "a sanity assertion without full error handling"; later versions allowed the same output to be spent twice ([Bitcoin Core disclosure](https://github.com/bitcoin-core/bitcoincore.org/blob/master/_posts/en/posts/2018-09-20-notice.md)). The 2010 overflow incident's details (block 74638, two outputs of about 92 billion bitcoin each) are known here only second-hand (unverified: search excerpt only) ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2010-5139)).

TigerBeetle documents the supporting habits: amounts are unsigned integers, and accounts and transfers are "immutable once created" ([data modeling](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/coding/data-modeling.md)); overflow and limit breaches are named result codes, including `exists_with_different_amount` for a retry whose amount differs ([create_transfers](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/reference/requests/create_transfers.md)); "The assertion density of the code must average a minimum of two assertions per function", with the warning that "a fuzzer can prove only the presence of bugs, not their absence" ([Tiger Style](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/TIGER_STYLE.md)); and assertions stay on in production ([VOPR](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md), [safety](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/concepts/safety.md)). Company ledgers are described similarly but could not be read: Stripe's Ledger as an "immutable and auditable log" (unverified: search excerpt only) ([Stripe](https://stripe.com/blog/ledger-stripe-system-for-tracking-and-validating-money-movement)); Square's Books as immutable (unverified: search excerpt only) ([Square](https://developer.squareup.com/blog/books-an-immutable-double-entry-accounting-database-service/)); Modern Treasury's rule to "group Entries by currency and validate that credits and debits for each currency match" (unverified: search excerpt only) ([Modern Treasury](https://moderntreasury.com/journal/how-to-scale-a-ledger-part-ii)).

### Remainders assigned by a fixed rule

The plain idea: money comes in indivisible units, so splits leave leftovers; the rule for who gets the leftover must be written down and always give the same answer.

**Lightning rounds down, and the leftover goes to fees.**
- Commitment transactions: "The amounts for each output MUST be rounded down to whole satoshis." If an output would be below the dust limit, "the output MUST NOT be produced (thus the funds add to fees)" ([BOLT 3](https://github.com/lightning/bolts/blob/master/03-transactions.md)).
- Fee calculation: "Multiply `feerate_per_kw` by `weight`, divide by 1000 (rounding down)", with the admission that "The actual fee may be higher than the amount calculated here, due to rounding and trimmed outputs" ([BOLT 3](https://github.com/lightning/bolts/blob/master/03-transactions.md)).
- Closing: "MUST round each output down to whole satoshis" ([BOLT 3](https://github.com/lightning/bolts/blob/master/03-transactions.md)); the closing fee is "rounded down to whole satoshis" ([BOLT 2](https://github.com/lightning/bolts/blob/master/02-peer-protocol.md)).
- Routing fee: "fee_base_msat + ( amount_to_forward * fee_proportional_millionths / 1000000 )", with the worked example "200 + ( 4999999 * 2000 / 1000000 ) = 10199" and no sentence on rounding ([BOLT 7](https://github.com/lightning/bolts/blob/master/07-routing-gossip.md)).
- Invoices: with the smallest multiplier, "the last decimal of `amount` MUST be `0`", because sub-millisatoshi amounts "cannot be transferred on the network" ([BOLT 11](https://github.com/lightning/bolts/blob/master/11-payment-encoding.md)). LDK turns this into named errors such as `ImpreciseAmount` ([lightning-invoice](https://github.com/lightningdevkit/rust-lightning/blob/main/lightning-invoice/src/lib.rs)).
- Receiving: "if the amount paid is less than the amount expected: MUST fail the HTLC"; "if the amount paid is more than twice the amount expected: SHOULD fail the HTLC" ([BOLT 4](https://github.com/lightning/bolts/blob/master/04-onion-routing.md)).

**Cashu rounds fees up, and returns change in a fixed order.**
- Fees: "The total fee for a transaction is the sum of all fees per input rounded up to the next larger integer", computed as `(sum_fees + 999) // 1000`; example, at 100 parts per thousand "the fees for spending 1-10 inputs is 1 sat, 11-20 inputs is 2 sat" ([NUT-02](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/02.md)).
- Who adjusts: "wallets **MUST** add fees to the inputs or, vice versa, subtract from the outputs" ([NUT-02](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/02.md)).
- Paying out over Lightning: the wallet provides ecash covering at least `amount + fee_reserve + fee` ([NUT-05](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/05.md)) and sends "blank outputs", empty slots for change, numbering `max(ceil(log2(fee_reserve)), 1)` ([NUT-08](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/08.md)).
- Change: the mint computes `overpaid_fees = input_amount - fees - total_paid` and "MUST imprint the amounts into the leading blank outputs, MUST return all blind signatures with a value greater than 0 in the same order as the blank outputs were received, and MUST omit all blind signatures with value 0" ([NUT-08](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/08.md)).
- Worked example in the spec: invoice 100,000 sat, reserve 1,000, actual fee 100, so 900 comes back as `4, 128, 256, 512` ([NUT-08](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/08.md)).

**General money libraries guarantee the sum, less often the recipient.** RubyMoney documents that "The total of the allocated amounts will always equal the original amount" ([allocation.rb](https://github.com/RubyMoney/money/blob/main/lib/money/money/allocation.rb)). Dinero.js says `allocate` distributes "the remainder as evenly as possible" and shows 1003 split 50/50 giving 502 and 501, but does not state in words which share gets the extra unit ([allocate docs](https://github.com/dinerojs/dinero.js/blob/main/docs/api/mutations/allocate.md)). The Money pattern's allocation is described as giving leftover units one at a time from the front of the list (unverified: search excerpt only, secondary) ([Stack Overflow mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/1679292/proof-that-fowler-s-money-allocation-algorithm-is-correct)); Betterment describes handing leftover cents to the largest remainders (unverified: search excerpt only) ([Betterment](https://www.betterment.com/engineering/penny-precise-allocation-functions)).

Inference: Lightning gives a model for "where does the leftover go": it is never dropped silently, it is assigned to one named place, fees ([BOLT 3](https://github.com/lightning/bolts/blob/master/03-transactions.md)). Inference: "first in list order" and "largest remainder" give different answers for the same input, and the second needs a tie-break; DubPay's rule must fix which, including the tie-break ([allocate docs](https://github.com/dinerojs/dinero.js/blob/main/docs/api/mutations/allocate.md)).

### Properties that sources actually test

Core Lightning's amount fuzzers are the closest published template. One asserts "We should not crash when parsing any string" and that formatting "should inconditionally produce valid amount strings according to our parser" ([fuzz-amount](https://github.com/ElementsProject/lightning/blob/master/tests/fuzz/fuzz-amount.c)). The other checks arithmetic: operations report success only when the result equals the plain integer result; after adding a fee `total == original + fee`; after subtracting a fee and recomputing it, `output + fee <= input` ([fuzz-amount-arith](https://github.com/ElementsProject/lightning/blob/master/tests/fuzz/fuzz-amount-arith.c)). Bitcoin Core round-trips amounts through its formatter and parser ([integer fuzz target](https://github.com/bitcoin/bitcoin/blob/master/src/test/fuzz/integer.cpp)) and decodes the same transaction bytes two ways, asserting agreement ([transaction fuzz target](https://github.com/bitcoin/bitcoin/blob/master/src/test/fuzz/transaction.cpp)). rust-bitcoin puts the 21-million limit in the amount type itself, and its arithmetic returns a result type "which enforces checked arithmetic" ([amount module](https://github.com/rust-bitcoin/rust-bitcoin/blob/master/units/src/amount/mod.rs)).

For sequences of operations, Hypothesis compares the real code to "a simplified in memory model of its behaviour" and runs an invariant function "after every step" ([stateful docs](https://github.com/HypothesisWorks/hypothesis/blob/master/hypothesis/docs/stateful.rst)); proptest does the same in Rust and shrinks failures "to a minimal sequence of transitions" ([proptest](https://github.com/proptest-rs/proptest/blob/main/book/src/proptest/state-machine.md)). Jepsen's test suite for TigerBeetle names an `idempotence` workload that "tries to submit the same IDs multiple times" and an `indefinite` workload that measures how often timed-out operations actually succeeded ([README](https://github.com/jepsen-io/tigerbeetle/blob/main/README.md)).

At larger scale the method is deterministic simulation: TigerBeetle's simulator replaces "the clock, network, and disk" and "may drop and reorder packets, partition the network, or corrupt reads and writes", and any failure replays from its seed ([VOPR](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md)); FoundationDB's maintainers write that "It seems unlikely that we would have been able to build FoundationDB without this technology" ([testing.rst](https://github.com/apple/foundationdb/blob/main/documentation/sphinx/source/testing.rst)). An independent test still found "a correctness bug in what appeared to be a well-fuzzed component" of TigerBeetle (unverified: search excerpt only) ([Jepsen](https://jepsen.io/analyses/tigerbeetle-0.16.11)). Formal modelling of Lightning in TLA+ is reported (unverified: search excerpt only) ([arXiv](https://arxiv.org/abs/2307.02342)).

Gap: no documented property test of a remainder-allocation function in a Lightning or Cashu codebase was found; the Core Lightning arithmetic fuzzer is the nearest ([fuzz-amount-arith](https://github.com/ElementsProject/lightning/blob/master/tests/fuzz/fuzz-amount-arith.c)).

### Solvency checks while running

Nutshell's watchdog "shuts down the mint if the balance of the mint and the backend do not match"; it is off by default and checks every 60 seconds ([settings.py](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/cashu/core/settings.py), [.env.example](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.env.example)). It has two conditions: stop if issued ecash plus fees paid exceeds the backend balance, and stop if "the reserve gap between backend and issued balances is shrinking" ([watchdog.py](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/cashu/mint/watchdog.py)); it has its own tests ([test file](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/mint/test_mint_watchdog.py)). The accounting behind it appends each change "in the same database transaction as the corresponding signature or proof change", and the README calls the redemption balance check "a best-effort observation" ([README](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/README.md)); tests include `test_accounting_survives_restart_and_multiple_workers` ([test file](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/mint/test_mint_accounting.py)).

Outside the mint, a proposal for proof of liabilities would have mints publish lists of issued and redeemed tokens per key period; it states its own limits, including that funds in Lightning channels "cannot be publicly accounted for" ([gist](https://gist.github.com/callebtc/ed5228d1d8cbaade0104db5d1cf63939)). An auditor that makes real payments between mints and flags failures is described in its announcement (unverified: search excerpt only) ([Nostr post](https://nostr.at/nevent1qqs0tztadx8hm2jc56y45dtsv25nfd4cxtme4estyk0kr22u4pc90vgpyfmhxue69uhkummnw3ez6an9wf5kv6t9vsh8wetvd3hhyer9wghxuet5qhnrly)).

Inference: the watchdog's second condition catches a slow leak long before the first would fire ([watchdog.py](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/cashu/mint/watchdog.py)). Gap: no reserve check or watchdog was found in CDK's documentation or configuration at the commit read ([example config](https://github.com/cashubtc/cdk/blob/a982d66c0d1b1de345a86f8faa14390c8aefdc28/crates/cdk-mintd/example.config.toml)); no document explains why Nutshell's watchdog is off by default ([.env.example](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.env.example)).

## Fuzzing payment parsers

Fuzzing means running a piece of code on enormous numbers of generated inputs, steered towards code not yet reached, to find inputs that crash it or break a stated rule.

**How the projects run it.** Bitcoin Core keeps its inputs in a separate repository, and "Every single pull request submitted against the Bitcoin Core repo is automatically tested against all inputs" ([fuzzing.md](https://github.com/bitcoin/bitcoin/blob/master/doc/fuzzing.md)); its bech32 targets assert that anything that decodes re-encodes to the same string ([bech32 fuzz](https://github.com/bitcoin/bitcoin/blob/master/src/test/fuzz/bech32.cpp)). Core Lightning uses libFuzzer with sanitizers and has targets for amounts, bech32, invoices, offers and about fifty wire messages ([testing.md](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/contribute-to-core-lightning/testing.md), [fuzz directory](https://github.com/ElementsProject/lightning/tree/master/tests/fuzz)). LDK supports three engines and has targets for invoices, offers, refunds, bech32, onion messages and routing ([fuzz README](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/fuzz/README.md), [fuzz/src](https://github.com/lightningdevkit/rust-lightning/tree/main/fuzz/src)); a crashing input is saved and replayed as an ordinary test ([fuzz README](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/fuzz/README.md)). LND uses Go's built-in fuzzing, where "Fuzz tests can be run as normal tests, which only runs the seed corpus" ([fuzz.md](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/fuzz.md)). rust-bitcoin's CI fuzzes every target briefly ([fuzz README](https://github.com/rust-bitcoin/rust-bitcoin/blob/master/fuzz/README.md)). Among ecash projects, CDK has 42 targets ([fuzz targets](https://github.com/cashubtc/cdk/tree/a982d66c0d1b1de345a86f8faa14390c8aefdc28/fuzz/fuzz_targets)), Nutshell fuzzes model parsing and every mint endpoint ([fuzz test](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/fuzz/test_fuzz_mint_api.py)), and Fedimint fuzzes encoding of core types ([fuzzing doc](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/docs/fuzzing.md)).

**What it found.**
- Five Core Lightning invoice-parsing bugs, triggerable "by specially crafted invoices, enabling a malicious counterparty to crash the victim's node upon invoice payment"; one needed an extra mutator and was then found "within a few CPU hours" ([write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/cln-invoice-parsing.md)).
- An LND bug where "A simple fuzz test for onion packet encoding and decoding revealed this vulnerability"; "If basic fuzz tests had been written at the time the original onion decoding functions were introduced, the bug would have been caught before it was merged" ([write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/lnd-onion-bomb.md)).
- A newer tool, smite, "checks the target's behavior against the BOLTs" and "has directly found 32 bugs across the four implementations. Most are spec violations" ([write-up](https://github.com/morehouse/morehouse.github.io/blob/main/content/lightning/fuzzing-lightning-with-smite.md)).

**Comparing implementations against each other** (differential fuzzing) finds cases where one accepts what another rejects. The bitcoinfuzz project "compares the libraries and does not reimplement them" ([repository](https://github.com/bitcoinfuzz/bitcoinfuzz)). Sampled findings: Core Lightning accepted invoice fallback addresses that LND and LDK rejected ([CLN PR #8219](https://github.com/ElementsProject/lightning/pull/8219)); LND silently ignored some fallback versions, and the report notes BOLT 11 had no test vectors for these cases ([LND issue #9591](https://github.com/lightningnetwork/lnd/issues/9591)); rust-lightning did not validate a currency code, fixed by validating when the value is built and not only when parsed ([PR #3814](https://github.com/lightningdevkit/rust-lightning/pull/3814)); and a new test vector was added to BOLT 12 after implementations disagreed ([bolts PR #1279](https://github.com/lightning/bolts/pull/1279)).

**Parsers can stop a node, not just crash it.** LND 0.15.2 fixed "A wire parsing bug ... that would cause lnd to be unable _decode_ certain large blocks" ([release notes](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/release-notes/release-notes-0.15.2.md)), described by Optech as "a security critical emergency release" ([Optech 2022-10-12](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_posts/en/newsletters/2022-10-12-newsletter.md)); 0.15.4 fixed the same for "certain large transactions" ([release notes](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/release-notes/release-notes-0.15.4.md)).

**Formats DubPay will read.** Cashu tokens come in two forms (`cashuA`, JSON-based, and `cashuB`, CBOR-based); padding "can be omitted. Clients need to be able to decode both cases" ([NUT-00](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/00.md)).

Inference: the two LND parsing fixes concern inputs larger than anything a regtest suite that mines its own blocks would produce; the release notes do not say this ([release notes](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/release-notes/release-notes-0.15.2.md)). Gap: none of the four sampled differential findings concerns the invoice amount field; whether an amount-parsing disagreement has ever been found is unverified ([repository](https://github.com/bitcoinfuzz/bitcoinfuzz)). Gap: no source was found on fuzzing of payment-link (BIP 21) or LNURL parsers specifically, and Eclair's own fuzzing setup was not confirmed ([Eclair test directory](https://github.com/ACINQ/eclair/tree/master/eclair-core/src/test/scala/fr/acinq/eclair)).

## Idempotency: doing a thing once when the network makes you ask twice

Idempotency means a request can be repeated any number of times and still take effect only once. It matters because the sender often cannot tell whether a request that timed out was carried out.

### The general pattern

The IETF working draft sets the vocabulary. The key "MUST be unique and MUST NOT be reused with another request with a different request payload"; the server may store a fingerprint of the request to detect that; a retry after completion gets the original result; a retry "before the original request completed" gets a conflict; and the expiry policy should be published ([IETF draft](https://raw.githubusercontent.com/ietf-wg-httpapi/idempotency/main/draft-ietf-httpapi-idempotency-key-header.md)). Its status codes: 400 for a missing key, 422 for a key reused with different content, 409 for a retry while the first is still in progress ([IETF draft](https://raw.githubusercontent.com/ietf-wg-httpapi/idempotency/main/draft-ietf-httpapi-idempotency-key-header.md)).

The idempotency-keys article adds the engineering. Once a system makes its first change in another system, "we're committed one way or another. We've pushed data into a system beyond our own boundaries and we shouldn't lose track of it"; local changes "should be safely committed before initiating any foreign state mutation"; keys are scoped per user; a "completer" pushes abandoned requests to the end; and requests that cannot be finished go "in a list somewhere so that a human can find out what failed" ([article](https://raw.githubusercontent.com/brandur/sorg/master/content/articles/idempotency-keys.md)). On outcomes that cannot be known: "Indeterminate errors like a connection reset or timeout will have to be marked as failed" when the downstream call is not itself idempotent ([article](https://raw.githubusercontent.com/brandur/sorg/master/content/articles/idempotency-keys.md)). His companion article describes staging outgoing work in the database so it is never sent before the local transaction commits and never dropped after ([article](https://raw.githubusercontent.com/brandur/sorg/master/content/articles/job-drain.md)). TigerBeetle states the client's duty: generate the ID, persist it "before submission", reuse it on retries, with the goal "recorded once and only once -- even if some parts of the system fail" ([reliable submission](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/coding/reliable-transaction-submission.md)). Stripe's own client library says it adds idempotency keys "where appropriate to prevent duplication" when it retries ([stripe-node README](https://raw.githubusercontent.com/stripe/stripe-node/master/README.md)).

Payment-company documentation could not be opened. As reported: Stripe keeps keys at least 24 hours and treats a 500 response as indeterminate, advising to "reconcile it before starting another operation" (unverified: search excerpt only) ([Stripe](https://docs.stripe.com/error-low-level), [Stripe API](https://docs.stripe.com/api/idempotent_requests)); Stripe's blog recommends exponential backoff with random jitter (unverified: search excerpt only) ([Stripe blog](https://stripe.com/blog/idempotency)); Adyen signals retry-safe errors with a response header (unverified: search excerpt only) ([Adyen](https://docs.adyen.com/development-resources/api-idempotency)); Modern Treasury saves only successful results, for 24 hours (unverified: search excerpt only) ([Modern Treasury](https://docs.moderntreasury.com/reference/idempotent-requests)).

### Lightning

The payment hash (a fingerprint of the preimage, per [BOLT 11](https://github.com/lightning/bolts/blob/master/11-payment-encoding.md)) is the natural key, but the three implementations guard it differently.

- **LND** refuses: its payment database has errors for "already paid this payment hash" and for a payment "already 'in flight' on the network" ([errors.go](https://raw.githubusercontent.com/lightningnetwork/lnd/master/payments/db/errors.go)). Statuses are `IN_FLIGHT`, `SUCCEEDED`, `FAILED` and `INITIATED` ([lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)). A timeout applies only before the first attempt: "Once HTLCs are in flight, the payment will not be aborted until the HTLCs are either settled or failed" ([router.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/routerrpc/router.proto)).
- **Core Lightning** returns the earlier answer: "Once a payment has succeeded, calls to **pay** with the same *bolt11* will succeed immediately" ([pay schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/pay.json)); the same hash with a different amount or destination fails, which "prevents accidental multiple payments" ([sendpay schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/sendpay.json)). A wait that times out (error 200) is distinct from a payment that failed ([waitsendpay schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/waitsendpay.json)). The newer `xpay` command has an error for "Invoice has already been paid" ([xpay schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/xpay.json)).
- **LDK** guards only while pending: a second send with the same ID is refused while the first is in flight, but afterwards "LDK will not stop you from sending a second payment with the same `PaymentId`", so "you should implement your own tracking of payments" ([channelmanager.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/channelmanager.rs)). The guard lapses after a set number of timer ticks ([outbound_payment.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/outbound_payment.rs)). On the receiving side, "LDK will not stop an inbound payment from being paid multiple times" ([events](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/events/mod.rs)). There is a documented crash window: a payment begun just before a crash "may be lost on restart" ([channelmanager.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/channelmanager.rs)).

Event streams differ in what they promise. LDK will "persist Events and replay any unhandled events on startup" ([events](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/events/mod.rs)). LND's invoice subscription can replay from stored indexes so callers "catch up on any events they missed" ([lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)); Core Lightning's `wait` command works from indexes that "only monotoncally increase" ([wait schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/wait.json)). LND's HTLC event stream is "best-effort ... events are not persisted, delivery is not guaranteed" and should be "de-duplicated" ([router.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/routerrpc/router.proto)).

On receipts: the preimage "provides proof of payment" ([BOLT 11](https://github.com/lightning/bolts/blob/master/11-payment-encoding.md)), but it "can only demonstrate that an invoice was paid ... not who paid it" ([BOLT 12](https://raw.githubusercontent.com/lightning/bolts/master/12-offer-encoding.md)); BOLT 12 now defines signed payer proofs ([BOLT 12](https://raw.githubusercontent.com/lightning/bolts/master/12-offer-encoding.md)). The glossary definition is in [BOLT 0](https://raw.githubusercontent.com/lightning/bolts/master/00-introduction.md). On LND's development branch, invoice states carry warnings: a settled invoice may still have a later duplicate part pending, and for a state called `PENDING_SETTLE` the value "must not yet be credited" ([lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)). Hold-invoice calls are themselves repeat-safe: settling an already settled invoice "will succeed" ([invoices.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/invoicesrpc/invoices.proto)).

For wallet-connect and LNURL: NIP-47 responses reference the request, requests can carry an expiry, the failure message covers "a timeout, exhausting all routes, insufficient capacity or similar", and a lookup call reports `pending` among its states ([NIP-47](https://raw.githubusercontent.com/nostr-protocol/nips/master/47.md)). LNURL-withdraw identifies a withdrawal by a `k1` string and "will withdraw funds to anyone who can provide a valid ephemeral `k1`" ([LUD-03](https://raw.githubusercontent.com/lnurl/luds/luds/03.md)).

Inference: the node's one-payment-per-hash guard does not protect an application that fetches a fresh invoice for the same business purpose after a timeout, because the new invoice has a new hash; the business-level key has to be the application's own ([errors.go](https://raw.githubusercontent.com/lightningnetwork/lnd/master/payments/db/errors.go)). Inference: NIP-47 as read defines no idempotency key and says nothing on a request delivered twice; a client cannot tell from its failure message alone whether the payment reached a final state, and the lookup call is the documented way to ask ([NIP-47](https://raw.githubusercontent.com/nostr-protocol/nips/master/47.md)).

### Ecash (Cashu)

Cashu gives a wallet three ways to resolve an interrupted operation without blindly repeating it ([NUT-19](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/19.md), [NUT-07](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/07.md), [NUT-09](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/09.md)).

1. **Replay the identical request.** NUT-19 exists "To minimize the risk of loss of funds due to network errors during critical operations such as minting, swapping, and melting"; the mint keys stored responses on method, path and payload, stores only successful ones, and chooses how long to keep them ([NUT-19](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/19.md)). Nutshell's implementation states its limits: in memory by default, lost on restart, not shared between workers ([caching doc](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/docs/response-caching.md)).
2. **Ask for state.** A proof (one ecash token) is `PENDING` "if it is being processed in a transaction", `SPENT` if redeemed, otherwise `UNSPENT`; after an interrupted payment a wallet "can check all proofs marked as pending in her database to determine whether the payment is still in flight ..., it has succeeded ..., or it has failed" ([NUT-07](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/07.md)). Outgoing-payment quotes have states `UNPAID`, `PENDING`, `PAID` ([NUT-05](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/05.md)). A subscription must first send the current state ([NUT-17](https://raw.githubusercontent.com/cashubtc/nuts/main/17.md)).
3. **Restore.** Mints "must store the `BlindedMessage` and the corresponding `BlindSignature`" for everything they sign, so a wallet can recover "the response of an interrupted swap request" ([NUT-09](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/09.md)); wallets keep "a separate counter for each keyset" for this ([NUT-13](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/13.md)).

On the mint side, "Mints **MUST** remember which proofs are currently `PENDING` to avoid reuse of the same token in multiple concurrent transactions" ([NUT-07](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/07.md)), and error codes distinguish already spent (11001), pending (11002), outputs already signed (11003) and duplicate inputs (11007) ([error codes](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/error_codes.md)). The quote ID for minting is a secret: "A third party who knows the `quote` ID can front-run and steal the tokens" ([NUT-04](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/04.md)). The spec changed recently: mint quotes are now described by `amount_paid` and `amount_issued` counters, and the older three-state field is "deprecated" ([NUT-23](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/23.md)); "`expiry` is a deadline for payment, not for issuance" ([NUT-04](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/04.md)); and BOLT 12 offers "can be paid multiple times, allowing the wallet to mint multiple times for one quote" ([NUT-25](https://raw.githubusercontent.com/cashubtc/nuts/main/25.md)). A behavioural test vector for batched minting requires all-or-nothing: "no partial minting" ([NUT-29 vectors](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/tests/29-tests.md)).

Inference: because NUT-19 has no client-chosen key, a retry is recognised only if it is the same request byte for byte; a regenerated request with fresh outputs is a new operation ([NUT-19](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/19.md)).

## Reconciliation against the rail's own evidence

Reconciliation means checking that two independently kept records agree: here, DubPay's books against what the Lightning node or the mint itself recorded.

### What the rails record

**LND** lists every outgoing payment with its hash, preimage, amount, fee and status; invoices with indexes for paging; forwarded payments; channel balances split into local, remote, pending and unsettled; on-chain balances and transactions; and channels that are opening or closing ([lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)). Faraday, a companion tool, produces "accounting with both on-chain and off-chain reports" using read-only permissions ([README](https://raw.githubusercontent.com/lightninglabs/faraday/master/README.md)); it books fees as separate entries and lists its own blind spots, for example that after a channel close, a balance "encumbered behind a timelock, or in an unresolved HTLC ... must be resolved by follow up on chain transactions" ([accounting doc](https://raw.githubusercontent.com/lightninglabs/faraday/master/docs/accounting.md)). A monitoring tool, lndmon, exports channel and payment metrics ([README](https://raw.githubusercontent.com/lightninglabs/lndmon/master/README.md)).

**Core Lightning** ships a bookkeeper that "keeps track of coins moving through your Lightning node" ([README](https://raw.githubusercontent.com/ElementsProject/lightning/master/plugins/bkpr/README.md)). Its balance listing flags an inconsistent account: "its balance is reported as 0msat and a **BROKEN** line is logged" ([schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/bkpr-listbalances.json)). Its event list is append-only ([schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/bkpr-listaccountevents.json)). The notifications that feed plugins "are not confirmable by definition" ([notifications doc](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/developers-guide/plugin-development/event-notifications.md)); newer core commands list confirmed balance changes on-chain and in channels ([listchainmoves](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/listchainmoves.json), [listchannelmoves](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/listchannelmoves.json)).

**Cashu mints**: per-proof and per-quote state as above ([NUT-07](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/07.md), [NUT-05](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/05.md)); the outgoing-payment response carries the preimage and the fee reserve ([NUT-23](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/23.md)); Nutshell's journal and watchdog are described in the solvency section ([README](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/README.md)).

Inference: each side has a natural matching key: the payment hash for payments and invoices, channel and payment-part identifiers for forwards, transaction identifiers on-chain ([lightning.proto](https://raw.githubusercontent.com/lightningnetwork/lnd/master/lnrpc/lightning.proto)). Inference: a balance check needs more than "channel balances plus on-chain wallet", because the sources name items outside those two numbers ([accounting doc](https://raw.githubusercontent.com/lightninglabs/faraday/master/docs/accounting.md)). Inference: Nutshell's watchdog compares the mint's liabilities with the backend's reported balance; it does not prove that reported balance is itself right ([watchdog.py](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/cashu/mint/watchdog.py)).

### When books and rail drifted apart

The clearest Lightning case is LNbits with an Eclair backend: a payment not settled within an internal timeout of about 30 seconds was recorded as failed although it could still complete, and "This vulnerability can lead to a total loss of funds for the node backend"; the advisory recommends checking payment status after an error and assuming a payment is still in flight when unsure ([advisory](https://github.com/lnbits/lnbits/security/advisories/GHSA-3j4h-h3fp-vwww)). A Fedimint gateway bug is reported in which the check against paying the same invoice twice "ran too late in the payment flow" (unverified: search excerpt only) ([Stacker News](https://stacker.news/items/1589945)). LND development discussion describes payments that can become stuck in flight (unverified: search excerpt only) ([mirror of LND PR 10137](https://github.meowingcats01.workers.dev/lightningnetwork/lnd/pull/10137)). Optech's index records an LND bug in which a preimage could be revealed improperly, giving "proof of payment for stolen payments" ([Optech topic](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_topics/en/proof-of-payment.md)).

Outside Bitcoin, the Synapse bankruptcy is the cautionary case for books that cannot be reconciled: the trustee's first report is said to put the gap at about $85 million (unverified: search excerpt only) ([PYMNTS](https://www.pymnts.com/legal/2024/synapse-bankruptcy-trustee-finds-85-million-dollar-shortfall-amid-tangled-web-accounts/)); later estimates ranged from $65 million to $95 million (unverified: search excerpt only) ([BNN Bloomberg](https://www.bnnbloomberg.ca/business/company-news/2024/10/23/funds-frozen-in-synapse-to-be-returned-by-year-end-trustee-says/)).

Gap: no public post-mortem was found in which a routine reconciliation is credited with catching a Lightning or ecash ledger discrepancy before loss; that may reflect limited searching. The nearest case, the LNbits advisory, was found as a vulnerability and not by reconciliation ([advisory](https://github.com/lnbits/lnbits/security/advisories/GHSA-3j4h-h3fp-vwww)).

## Incidents, post-mortems and release practice

### A routine small enough to adopt

The one reference read in full is PagerDuty's public documentation. A post-mortem is "a blame-free, detailed description, of exactly what went wrong ..., along with a list of steps to take in order to prevent a similar incident from occurring again"; one named owner schedules the review "within 3 calendar days for a SEV-1 and 5 business days for a SEV-2"; the document starts with a timeline, and for each entry the owner should "identify a metric, or some third-party page where the data came from"; the review asks "Could it have been caught in tests, or loadtest environment?"; and follow-ups are kept few: "Be careful with creating too many tickets" ([post-mortem process](https://raw.githubusercontent.com/PagerDuty/incident-response-docs/master/docs/after/post_mortem_process.md)). There are five severity levels, and "If you are unsure ... treat it as the higher one" ([severity levels](https://raw.githubusercontent.com/PagerDuty/incident-response-docs/master/docs/before/severity_levels.md)). One incident commander decides and delegates; "Making the 'wrong' decision is better than making no decision" ([incident commander](https://raw.githubusercontent.com/PagerDuty/incident-response-docs/master/docs/training/incident_commander.md)). A public collection of post-mortems lists payment examples in its maintainer's one-line summaries ([danluu/post-mortems](https://raw.githubusercontent.com/danluu/post-mortems/master/README.md)).

Google's SRE book and Atlassian's handbook are reported to describe the same core: blameless reviews, triggers agreed in advance, tracked actions with deadlines (unverified: search excerpt only) ([Google SRE](https://sre.google/sre-book/postmortem-culture/), [Atlassian](https://www.atlassian.com/incident-management/handbook/postmortems)).

None of these pages could be opened; all are unverified.

- TSB, 2018: fined £48.65 million for failing to "organise and control the IT migration programme adequately" (unverified: search excerpt only) ([FCA](https://www.fca.org.uk/news/press-releases/tsb-fined-48m-operational-resilience-failings)).
- Stripe, 2019: a database failure caused a first outage and the rollback chosen in response caused a second (unverified: search excerpt only) ([Stripe RCA](https://stripe.com/rcas/2019-07-10)).
- Monzo, 2019: new database servers answered reads before holding data; afterwards the health check wrote known values and read them back (unverified: search excerpt only) ([Monzo](https://monzo.com/blog/2019/09/08/why-monzo-wasnt-working-on-july-29th/)).
- Coinbase publishes named incident post-mortems (unverified: search excerpt only) ([Coinbase](https://www.coinbase.com/blog/incident-post-mortem-june-1-2020)).

Earlier cases follow the same shape: in 2019 three implementations "did not confirm that channel open transactions paid the correct script, amount, or both" ([Optech 2019-10-02](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_posts/en/newsletters/2019-10-02-newsletter.md)), with a warning to upgrade issued weeks before details ([Optech 2019-09-04](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_posts/en/newsletters/2019-09-04-newsletter.md)); in 2020 LND could be tricked into revealing a payment secret before being paid ([Optech 2020-10-28](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_posts/en/newsletters/2020-10-28-newsletter.md)); in 2021 a few payments "could spend all of a channel's value to miner donations" ([Optech 2021-10-13](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_posts/en/newsletters/2021-10-13-newsletter.md)); in 2026 an LND bug in closed-channel handling after a chain reorganisation was disclosed ([Optech 2026-08-21](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_posts/en/newsletters/2026-08-21-newsletter.md)); and Eclair denial-of-service fixes in 2026 were merged in a refactoring "that did not mention the vulnerability" ([Optech 2026-10-02](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_posts/en/newsletters/2026-10-02-newsletter.md), [Optech 2026-10-16](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_posts/en/newsletters/2026-10-16-newsletter.md)). Optech's running list shows many more disclosures in 2026 ([Optech topic](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_topics/en/responsible-disclosures.md)).

**The people who found the bugs say what would have caught them.** A fuzz test ([onion bomb](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/lnd-onion-bomb.md)); a force-close test suite: "Had these tests existed from the start, this vulnerability would have been prevented" ([Eclair write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/eclair-preimage-extraction-exploit.md)); a stress test kept in the release process ([CLN race](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/cln-channel-open-race.md)); a code comment ([LDK duplicate HTLC](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/ldk-duplicate-htlc-force-close-griefing.md)); testing another implementation against your own, which is how a 2022 anchor-outputs problem was found ([Optech 2022-05-04](https://raw.githubusercontent.com/bitcoinops/bitcoinops.github.io/master/_posts/en/newsletters/2022-05-04-newsletter.md)); and keeping the specification current, since the failback behaviour had been fixed elsewhere but "by a strict interpretation" the specification "actually requires the incorrect behavior" ([write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/lnd-excessive-failback-exploit.md)).

**Being offline is a money risk.** After the second 2022 parsing bug, LND nodes that had not upgraded entered "a degraded state": they could still pay and forward but might miss on-chain events, which the advisory warns "can lead to loss of funds"; it offers a stopgap for operators who could not upgrade at once, changing channel policy so nothing routes through the node ([advisory](https://github.com/lightningnetwork/lnd/security/advisories/GHSA-hc82-w9v8-83pr)). Both 2022 fixes shipped as releases describing themselves as "an emergency hot fix release" ([v0.15.2](https://github.com/lightningnetwork/lnd/releases/tag/v0.15.2-beta), [v0.15.4](https://github.com/lightningnetwork/lnd/releases/tag/v0.15.4-beta)).

LDK shows a different publication style: a "Security" section at the top of release notes that says in plain words what is fixed, for example "fixes a funds-theft vulnerability when paying BOLT 12 offers" ([changelog](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/CHANGELOG.md)).

- **BTCPay Server, August 2026.** Release 2.4.2 "contains fix of a critical vulnerability that is being actively exploited. Its advisories page shows none published ([advisories](https://github.com/btcpayserver/btcpayserver/security/advisories)). - **LNbits, November 2026.** Releases titled "URGENT SECURITY UPDATE" and "SECURITY PATCH ... Inference: Nutshell's halt-on-exception feature, added in one release and disabled by default in the next because it would "lock all Lightning payments", shows a safety halt needs its false-alarm rate tested first ([releases](https://github.com/cashubtc/nutshell/releases?page=2)).

### Security policies, release integrity and operating rules

Security policies read: LND maintains "the two most recent lnd release lines" ([LND](https://raw.githubusercontent.com/lightningnetwork/lnd/master/SECURITY.md)); Core Lightning supports "the last two versions" ([CLN](https://raw.githubusercontent.com/ElementsProject/lightning/master/SECURITY.md)); LDK asks for reports of vulnerabilities "including denial-of-service vulnerabilities such as spurious panics" ([LDK](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/SECURITY.md)); Eclair lists a contact and key fingerprints ([Eclair](https://raw.githubusercontent.com/ACINQ/eclair/master/SECURITY.md)); BTCPay promises acknowledgement within 2 business days and aims to fix "within 90 business days" ([BTCPay](https://raw.githubusercontent.com/btcpayserver/btcpayserver/master/SECURITY.md)); LNbits fixes only the current release ([LNbits](https://raw.githubusercontent.com/lnbits/lnbits/main/SECURITY.md)); Cashu projects ask for no exploit details in public ([Nutshell](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/SECURITY.md)); Fedimint keeps reports private "until a fix is released and federation operators had time to upgrade" ([Fedimint](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/SECURITY.md)). Bitcoin Core's standard disclosure schedule is known only second-hand (unverified: search excerpt only) ([Bitcoin Core](https://bitcoincore.org/en/security-advisories/)); one example advisory was read, with report in 2020 and disclosure in 2024 ([example](https://raw.githubusercontent.com/bitcoin-core/bitcoincore.org/master/_posts/en/posts/2024-07-03-disclose-unbounded-banlist.md)).

Release integrity: LND's release pages give steps to verify signatures and hashes, and its binaries are reproducible so others can check them "without having to trust the release manager(s)" ([release page](https://github.com/lightningnetwork/lnd/releases/tag/v0.15.4-beta)); the release procedure builds a draft that is checked and signed before manual publication ([release.md](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/release.md)). Bitcoin Core's builds let people "audit and reproduce" the toolchain, with several builders signing the result ([Guix README](https://raw.githubusercontent.com/bitcoin/bitcoin/master/contrib/guix/README.md), [release process](https://raw.githubusercontent.com/bitcoin/bitcoin/master/doc/release-process.md)).

Operating rules specific to Lightning:
- Restoring an old channel database "is very risky and should _never_ be done"; the static channel backup is "the single most important file that needs to be backed up whenever it changes", but it only allows funds to be reclaimed by closing channels with the peers' cooperation ([LND safety](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/safety.md)).
- Core Lightning: "There is no single-seed backup for funds locked in channels"; live database replication is recommended ([CLN backup](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/beginners-guide/backup.md)).
- "It is extremely important to **never interrupt an `lncli` command** if it is manipulating the channel database" ([LND safety](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/safety.md)).
- Watchtowers are "a second line of defense" if the node is offline during an attempted theft ([watchtower doc](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/watchtower.md)).
- Eclair: changing the wallet "when you have channels open may result in a loss of funds" ([README](https://raw.githubusercontent.com/ACINQ/eclair/master/README.md)). Alby Hub: starting with channels while the chain backend is still syncing can force-close them ([README](https://raw.githubusercontent.com/getAlby/hub/master/README.md)).
- Mint operators: back up before upgrading and stop older workers ([Nutshell releases](https://github.com/cashubtc/nutshell/releases)); set balance and per-payment limits and rate limits ([.env.example](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.env.example)); keep a Lightning fee reserve as a percentage with a floor ([Nutshell](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.env.example), [CDK](https://github.com/cashubtc/cdk/blob/a982d66c0d1b1de345a86f8faa14390c8aefdc28/crates/cdk-mintd/example.config.toml)); keep the key phrase out of config files ([CDK example](https://github.com/cashubtc/cdk/blob/a982d66c0d1b1de345a86f8faa14390c8aefdc28/crates/cdk-mintd/example.config.toml)); monitoring dashboards ship with CDK's mint ([README](https://github.com/cashubtc/cdk/blob/a982d66c0d1b1de345a86f8faa14390c8aefdc28/crates/cdk-mintd/README.md)).
- Caution while new: Core Lightning recommends "experimenting on `testnet`" first ([README](https://raw.githubusercontent.com/ElementsProject/lightning/master/README.md)); LND shipped watchtowers with "a restricted set of features" until more were tested ([watchtower doc](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/watchtower.md)).

Regulators' incident-reporting rules were confirmed only at headline level: the EU's payment-specific guidelines were replaced by a harmonised regime in January 2025 (unverified: search excerpt only) ([EBA](https://www.eba.europa.eu/regulation-and-policy/payment-services-and-electronic-money/guidelines-on-major-incidents-reporting-under-psd2)).

Inference: because fixes are quiet and disclosure comes 6 to 24 months later, "which version of each dependency are we on" is itself a release-gate question ([LND SECURITY](https://raw.githubusercontent.com/lightningnetwork/lnd/master/SECURITY.md)). Inference: the usual safety net of restoring yesterday's backup or reinstalling the old version is unavailable or dangerous for channel state, so the checks have to carry the weight before release ([LND safety](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/safety.md)). Inference: LND's dry-run setting implies upgrades that migrate the database are one-way; no explicit "you cannot downgrade" sentence was found ([sample config](https://raw.githubusercontent.com/lightningnetwork/lnd/master/sample-lnd.conf)).

## Where the specs are silent or the sources disagree

**Specifications that leave a money question open**

- **BOLT 7 routing fee rounding.** The formula has no rounding statement ([BOLT 7](https://github.com/lightning/bolts/blob/master/07-routing-gossip.md)). Inference: the worked example only gives 10199 if 9999.998 is cut down to 9999, so rounding down is implied but not stated.
- **NUT-08 change that does not fit.** The text read does not say what happens to overpaid fees when the wallet sent no blank outputs or too few; change is returned "ONLY IF" blank outputs were provided ([NUT-08](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/08.md)). Inference: the remainder stays with the mint, which a wallet-side conservation rule must allow for.
- **NUT-08 blank-output count.** It is given as `ceil(log2(...))` ([NUT-08](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/08.md)) while NUT-02 warns against floating-point rounding for fees ([NUT-02](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/02.md)). Inference: a whole-number method avoids a mismatch at exact powers of two.
- **Failed outgoing payment in NUT-05.** No single sentence says the mint must release the wallet's proofs on failure; it is implied by "until it is `UNSPENT` again" ([NUT-07](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/07.md), [NUT-05](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/05.md)).
- **NUT-19 under concurrency and after eviction.** The spec does not say what happens when the same request arrives while the first is still running, or after the stored response is gone ([NUT-19](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/19.md)); Nutshell documents its own answer ([caching doc](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/docs/response-caching.md)).
- **How long to poll a pending melt.** No spec text was found on how long a wallet keeps asking or what to do if a mint never resolves it ([NUT-05](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/05.md)). The wallet-side wording on pending proofs is permissive ("can check") ([NUT-07](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/07.md)).
- **No test vectors for the accounting rules.** Vectors exist for cryptographic and encoding NUTs but not for NUT-03, 04, 05, 07, 08, 09 or 19 ([tests directory](https://github.com/cashubtc/nuts/tree/8f83a974503643d47fef12614039dca0e17e8ab1/tests)). Inference: conformance on balance, fee and change rules is established by cross-implementation tests, not by the spec repository.
- **Paying a hash twice.** A search of the current BOLT 11 did not find a sentence saying a payment hash must not be paid twice ([BOLT 11](https://github.com/lightning/bolts/blob/master/11-payment-encoding.md)); the rule lives in the implementations and LDK's advice that hashes "are not re-used" ([channelmanager.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/channelmanager.rs)).
- **Wallet-connect and LNURL.** NIP-47 as read defines no idempotency key ([NIP-47](https://raw.githubusercontent.com/nostr-protocol/nips/master/47.md)); nothing was found in LNURL-pay about duplicate callbacks, and LNURL-withdraw's text is the only one read ([LUD-03](https://raw.githubusercontent.com/lnurl/luds/luds/03.md)).
- **Spec behind practice.** One LND theft bug had been fixed independently elsewhere while the specification still described the incorrect behaviour ([write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/lnd-excessive-failback-exploit.md)).

**Sources that disagree with each other**

- **LND itest README versus MAKEFILE.** The README says the parallel-run defaults are 4 and 4 and that `parallel` must be less than or equal to `tranches` ([itest README](https://raw.githubusercontent.com/lightningnetwork/lnd/master/itest/README.md)); MAKEFILE.md says the default is 6 tranches and that `parallel` "Must be greater or equal to `tranches`, otherwise undefined behavior is expected" ([MAKEFILE.md](https://raw.githubusercontent.com/lightningnetwork/lnd/master/docs/MAKEFILE.md)). Not resolved.
- **409 versus 422.** The IETF draft uses 422 for a key reused with different content and 409 for a retry while the first is running ([IETF draft](https://raw.githubusercontent.com/ietf-wg-httpapi/idempotency/main/draft-ietf-httpapi-idempotency-key-header.md)); the idempotency-keys article's example returns 409 for both ([article](https://raw.githubusercontent.com/brandur/sorg/master/content/articles/idempotency-keys.md)).
- **How long a key is honoured.** The idempotency-keys article suggests "about 72 hours" ([article](https://raw.githubusercontent.com/brandur/sorg/master/content/articles/idempotency-keys.md)); NUT-19 leaves it to the mint ([NUT-19](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/19.md)); LDK measures it in timer ticks ([outbound_payment.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/outbound_payment.rs)); Stripe is reported as at least 24 hours and Modern Treasury as 24 hours (unverified: search excerpt only) ([Stripe](https://docs.stripe.com/api/idempotent_requests), [Modern Treasury](https://docs.moderntreasury.com/reference/idempotent-requests)); PayPal's and Square's periods were not found (unverified: search excerpt only) ([PayPal](https://developer.paypal.com/api/rest/reference/idempotency/), [Square forum](https://developer.squareup.com/forums/t/how-long-are-idempotency-keys-retained-for-the-createpayment-endpoint/28303)).
- **Which outcomes are stored.** NUT-19 stores only successful responses ([NUT-19](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/19.md)); Stripe is reported to store 500 errors and Modern Treasury only successes (unverified: search excerpt only) ([Stripe](https://docs.stripe.com/error-low-level), [Modern Treasury](https://docs.moderntreasury.com/reference/idempotent-requests)). Inference: storing errors makes a failure stick to the key; storing only successes means a retry after an error runs again.
- **What a node does with a repeated payment.** LND refuses ([errors.go](https://raw.githubusercontent.com/lightningnetwork/lnd/master/payments/db/errors.go)), Core Lightning returns the earlier success ([pay schema](https://raw.githubusercontent.com/ElementsProject/lightning/master/doc/schemas/pay.json)), LDK guards only while pending ([channelmanager.rs](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/lightning/src/ln/channelmanager.rs)).
- **Halt or continue.** TigerBeetle and Fedimint stop on a broken invariant ([VOPR](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md), [server core](https://github.com/fedimint/fedimint/blob/2448a1d296e0c3013bf30fb023f354f92082c1b3/fedimint-server-core/src/lib.rs)); Nutshell's watchdog is optional and off by default ([.env.example](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.env.example)); no equivalent was found in CDK ([example config](https://github.com/cashubtc/cdk/blob/a982d66c0d1b1de345a86f8faa14390c8aefdc28/crates/cdk-mintd/example.config.toml)).
- **Fee reserve defaults.** Nutshell's example config reserves 1.0 percent with a minimum of 2000 ([.env.example](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/.env.example)); CDK's example gives `fee_percent = 0.02` and a minimum of 2 sats ([example config](https://github.com/cashubtc/cdk/blob/a982d66c0d1b1de345a86f8faa14390c8aefdc28/crates/cdk-mintd/example.config.toml)). Inference: there is no agreed value; each deployment must choose and test its own.
- **Remainder rules.** Leftover to the first shares versus leftover to the largest remainders; both descriptions are second-hand (unverified: search excerpt only) ([Stack Overflow mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/1679292/proof-that-fowler-s-money-allocation-algorithm-is-correct), [Betterment](https://www.betterment.com/engineering/penny-precise-allocation-functions)).
- **Mint quote model.** Current NUT-04 uses counters and NUT-23 marks the state field deprecated ([NUT-04](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/04.md), [NUT-23](https://github.com/cashubtc/nuts/blob/8f83a974503643d47fef12614039dca0e17e8ab1/23.md)); mints in the field may still implement only the older states. Inference: tests should cover both.
- **Disclosure timing.** From the same day in release notes (LDK) to two years (LND gossip filter) ([changelog](https://raw.githubusercontent.com/lightningdevkit/rust-lightning/main/CHANGELOG.md), [write-up](https://raw.githubusercontent.com/morehouse/morehouse.github.io/master/content/lightning/lnd-gossip-timestamp-filter-dos.md)).
- **Within the research notes.** One note found no fuzzing in any Cashu implementation; another found CDK's 42 targets and Nutshell's fuzz tests, which this report follows ([fuzz targets](https://github.com/cashubtc/cdk/tree/a982d66c0d1b1de345a86f8faa14390c8aefdc28/fuzz/fuzz_targets), [fuzz test](https://github.com/cashubtc/nutshell/blob/b2f9ac5c21a960e07537fd0950a3cebdf0485146/tests/fuzz/test_fuzz_mint_api.py)). One note could not find a Cashu regtest repository; another read it ([cashu-regtest](https://raw.githubusercontent.com/callebtc/cashu-regtest/main/README.md)). Synapse shortfall figures differ between reports (unverified: search excerpt only) ([PYMNTS](https://www.pymnts.com/legal/2024/synapse-bankruptcy-trustee-finds-85-million-dollar-shortfall-amid-tangled-web-accounts/), [BNN Bloomberg](https://www.bnnbloomberg.ca/business/company-news/2024/10/23/funds-frozen-in-synapse-to-be-returned-by-year-end-trustee-says/)).
