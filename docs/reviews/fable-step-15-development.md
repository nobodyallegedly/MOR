## In plain words first

Development is the smallest MIR and carries the largest promise: that everything above the core can be named by anyone, checked by anyone, and carried to MOR 2 by anyone, with nothing held hostage. The promise holds where it rests on a hash of content: the same specification is the same wherever it is published, a successor by a stranger is shown as such, a creator's disowned publication leaves the specification "unclaimed" and nothing else, and a successor protocol's prefix keeps every act on its own side. The step 17 rehearsal ran the whole thing on throwaway homes and most of it passed from a stranger's seat. What follows is where the promise rests on something other than a hash.

**The trust root is written as six numbers and is in fact six texts (D3).** Rule 26 says a client learns the six MIR hashes "from that repository and its own build"; no client checks them against anything, since the build is what would be checked, and today every client carries test values. The only non-circular root is the frozen texts themselves: a client that ships the six canonical texts and recomputes their hashes can disagree with another client only about a text, which anyone can read. The rehearsal found the one thing that would make honest clients disagree about a text: the repository's files end with a line break that canonical text forbids, so a hash of the file is not the hash of the specification.

**The format leaves most of a specification's data optional, so two honest publishers of one cMIP produce two specifications (D1).** Tasks filled, types defined, dependencies, what a Module implements: each is an optional field, and the rehearsal publishes none of them. Two tools publishing the same text with different optional fields produce different hashes, and neither is wrong. Worse, F295 says an act "of a type its specification does not define" is invalid, and the types a cMIP defines are in field 3, which no founding cMIP will carry. Read by the letter, every act of every founding cMIP is invalid at step 17. The word "defines" has to mean the specification's text as implemented, and field 3 has to be discovery only, like field 12; or field 3 becomes required for a kind that defines types. Either is one sentence; the text has neither.

**Rule 22's frozen machine has no profile, no program and no vector (D4).** Every verification rule in the repository is native Rust; the payment cMIP and the rails say the RV32IM program comes "once the profile is published"; scenario 8.2 has nothing to run. The rule is scoped ("where a cMIP says anyone can run the same rule"), so the founding Modules are not in breach, but the suite claims a test that cannot be made, and the freeze procedure lists the profile as a parameter to settle at freeze. Either the profile and one compiled rule exist before the freeze, or scenario 8.2 is marked deferred and the founding specifications say plainly that their rules are reference implementations, not published machines.

Smaller: F295 names no verdict for an act naming a specification whose content is invalid, and the core library reads two fields of the format (D2); F301's two fields are already half-written as one enum, field 11, and the task table still hands the rail's kind to the cMIP (D5); the MICS, the suite and MOR 2's MIPs have no kind, so a listing would call them all MIRs (D6); a release names what it implements by a publication's act id rather than the specification's hash, so the claim depends on holding that one copy (D8). The creator is not the single point of failure it looks like (D7): an identity's hash survives its rotations, a thief's publication in the creator's name is disowned into "unclaimed", and the way to MOR 2 is clean; what is fragile is the order of step 17, where every founding hash is computed after one genesis that cannot be redone.

## Findings

Severity: **breaks a guarantee** / **leaves a gap** / **wording**. Kind: **text** / **code** / **instrument**. Pattern: one of the four of round 2, or "fits none", named.

### D1. What a specification must carry is not said, so two honest publishers make two specifications, and F295 makes every founding act invalid. Text. Leaves a gap. Pattern: a rule rests on a fact nobody can check (what a cMIP fills, defines or implements lives in its prose).

**Sentences.** Part three: `? 2 => [+ task-ref]`, `? 3 => [+ type-def]`, `? 4 => [+ hash]` (dependencies), `? 5 => hash` (implements): all optional. "The spec hash covers this content, not the act that publishes it, so the same specification can be published by anyone, anywhere, and remain the same specification (F41)." Rule 2: "Every act names its type within the specification that defines it." F295: "an act whose type its specification does not define ... is invalid". Rule 26: "every act it accepts names one of them or a specification that depends on them." The listing (website cMIP, 13c) shows "the task it fills or that it is an xtype ... the cMIP a Module works under" from "its own fields".

**Evidence.** `scripts/rehearsal/specs.ts` publishes every specification as `{0: kind, 1: creator, 9: text}` and nothing else; the rehearsal says so (item 5b: "the specifications' other fields ... are written down nowhere as data; ... so the listing cannot show which cMIP a Module implements"). Nothing in the core reads fields 2 to 5 (`development.rs` reads 0 and 12). So: (a) a second tool that writes field 2 for the split cMIP publishes a different specification with a different hash, and agreements naming either are naming different things, though the text is one; F41's "the same specification" holds only among tools that agree on which optional fields to write, which nothing states. (b) "A specification that depends on them" (rule 26) cannot be checked for a specification with no field 4. (c) F295, by the letter: the website cMIP's act types are defined in its text and in `clients/site`; its publication carries no field 3; so its acts are "of a type its specification does not define", invalid, in every client at step 17.

**Smallest fix.** One paragraph in Part three stating, per kind, which fields are required and which are discovery only: a cMIP filling a task carries field 2; a Module carries field 5; field 3 is discovery only, the types a specification defines being those its text defines, as a verifier that implements it knows them (F295's "unknown where the specification is not implemented" already says that the verifier's knowledge is the implementation, not the data); field 4 likewise, with rule 26's sentence reworded to "names one of them, or a specification whose text depends on them". And the rule that makes F41 true: *a publishing tool writes every required field and no optional one it cannot fill from the specification's text; two publications of one text that differ in optional fields are two specifications, and a listing shows them as versions of one text.* Cost: a sentence; the rehearsal's `specs.ts` writes field 2 and 5 from a small table. (Q1.)

### D2. F295 for specifications: no verdict for an act under an invalid specification, and the core reads two fields. Text and code. Leaves a gap. Pattern: fits none (a check in one place, the layer in another; the Agreements A6 shape).

**Sentences.** Field 10: "A specification whose field 10 carries any other value, or is not ascending, is invalid." `development.rs`: field 12 wrong "makes the specification invalid". F295 (MICS): an act outside its specification's format, or of an undefined type, is invalid; unknown where the specification is not implemented. The format itself: a map with twelve fields, two kinds of reference, a fee form.

**Evidence.** A specification is content a publication's media carries; the act that names it (any act's `spec` field) does not carry it. So "the specification is invalid" is a verdict on bytes a verifier may not hold, and the text says nothing about what it does to the acts that name the specification. `development.rs` decodes field 0 and field 12 only; field 10's rule is enforced nowhere in the core (`ext_layers` is a fact the caller states); fields 2 to 9 and 11 are never read. A publication carrying a specification with field 10 out of order is a valid Envelopes act with valid media, and nothing in any client says "invalid".

**Smallest fix.** Text: *a specification whose content is not in this format is no specification: a verifier holding its content shows it so, and an act naming it is unknown to every client, since no client can have adopted it (rule 10); a verifier not holding the content answers unknown as for any specification it has not adopted.* That is, invalidity of a specification produces *unknown* for acts, never *invalid*, because adoption is the verifier's own act and a malformed specification is one it cannot have adopted; F295's *invalid* stays for acts outside a specification the verifier implements. Code: a decoder of the whole format in `development.rs` (kinds, references, fee, fields 10 to 12 with their rules), used by the listing and by any client before adoption; the core verifier reads it only through adoption. Cost: one decoder, small; no change to `status_cx`. (Q2.)

### D3. The trust root is the texts, not six numbers; and the repository's files hash differently from the specifications. Text and instrument. Breaks a guarantee (two honest verifiers must agree on what MOR is). Pattern: a rule rests on a fact nobody can check (a number with no independent source).

**Sentences.** Rule 26: "Below the MICS there is one root: the six spec hashes of its frozen MIRs, published together alongside their texts in the genesis repository. A client learns them from that repository and its own build." Suite 8.1: "A read-only client shows them and checks the six hashes against its build." Open technical parameters: "How the MIRs themselves are published, so their spec hashes ... are fixed at freeze."

**Evidence.** No client checks six hashes against anything: `clients/*/src/specs.ts` carry test values ("fixed at the freeze"), and no code compares them to a published list; the suite's check has no code. If one existed, it would compare a build to a list published by the same author who signs the build: a client that trusts its release (release manifest, signed by the author) already trusts whatever six numbers it ships. The independent root is the texts: anyone can recompute `tagged_hash("MOR/spec", cbor({0: 4, 9: canonical text}))` from a frozen text. And the rehearsal found why two honest people would get two answers (item 5c): "the repository's files end with a line break, which canonical text forbids, so the published text is the file without it ... Anyone hashing the repository's file gets a different hash from the published one." The `compose` step also changed the shower text ("loses one trailing space"), so the published text is not the file.

**Smallest fix.** Rule 26 reworded: *the root is the six frozen texts, published as canonical text; their hashes follow from them, and a client ships the texts (or their canonical bytes) and recomputes the hashes it accepts, so that two clients can differ only about a text.* Instrument: the frozen files are committed as canonical text (no final line break, no trailing space; a check in CI that `compose(file) == file` for every frozen specification), so that the file, the publication and the hash are one. Suite 8.1: "checks the six hashes against its build" becomes "recomputes the six hashes from the texts it ships, and shows them". Cost: a CI check and a sentence; the client change is where the test values are replaced at step 16 anyway. (Q3.)

### D4. Rule 22's machine has no profile, no program and no vector; the suite tests what does not exist. Text and instrument. Leaves a gap. Pattern: a rule rests on a fact nobody can check (no rule can be run).

**Sentences.** Rule 22: "Where a cMIP or Module says 'anyone can run the same rule', its verification rule MUST be published as a program for RV32IM ... The profile ... is published with test vectors before freeze (F78). [for technical review at freeze]". `rule-ref = [bytes-hash, size, budget]`, "carried as a separate locked object". Suite 8.2: "A cMIP author publishes a split cMIP with a verification rule on the RV32IM profile, its binary carried as a locked object"; Part two's scenario: "A rail Module's verification rule run by two different clients on the RV32IM profile, giving the same answer". The payment cMIP: "the profile is not yet published, so this cMIP's steps 1 to 4 and each rail Module's rule are given as text and as a reference implementation ... Step 15 or 16 compiles them for the profile"; its own scenario 2.5: "Reasoned: one implementation so far; the RV32IM profile is open."

**Evidence.** No file in the repository is an RV32IM program, a profile, or a vector for one; every verification rule (`cmips/payment`, `modules/lightning`, `modules/onchain`, `cmips/split`) is native Rust compiled per platform. No specification carries field 6. Rule 22 is scoped to a cMIP that *says* anyone can run its rule, and none of the founding ones says so, so none is in breach; but the suite's 8.2 and the Part two scenario cannot be run, and "two clients run the same rule" is today "one implementation, reasoned".

**Smallest fix, two readings.** (a) Before the freeze: the profile (memory, encoding, entry point), one rule compiled to it (the split cMIP's division is the natural first: integer-only, small), its vector, and the locked-object carriage built; the suite's 8.2 then runs. Recommendation: (b), stated honestly, unless (a) is cheap for the team: the rule's value is in its promise ("a rule can never be right on one client and wrong on another"), and the promise is not kept by any founding Module today, which the texts should say. (Q4.)

### D5. F301's two fields against field 11, and the task table. Text. Wording with a format decision.

**Sentences.** Field 11 (draft 9, OF26 a): "a rail Module's kind: 0 a request rail, binding payee and purpose; 1 a push rail binding the commitment where the Module says; 2 a push rail binding nothing (Money rules 11, 18)". F301: "the Module format gains, for the Module kind, two fields: the rail's kind (request or push) and what its proof binds (a set: payee, purpose, previous hop)". Task 6's table line: a cMIP produces "whether each rail Module is a request rail or a push rail (F128, W4)".

**Evidence.** Field 11 already exists and folds kind and binding into one enum of three values, which cannot express "a push rail binding payee and purpose but not the previous hop" or "a request rail binding nothing"; F301 asks for a kind and a set. The task table still says the *cMIP* produces the rail's kind, which F301 moved to the Module's specification. The library reads neither: `push_rails` and `unbound_rails` are facts the caller states.

**Smallest fix.** Field 11 becomes the kind alone (0 request, 1 push); a new field, 13, the set of what the proof binds (ascending, from {0 payee, 1 purpose, 2 previous hop}); both required on a Module whose field 5 names the payment cMIP, the specification invalid without them; the task table's line reworded to "reads each rail Module's kind and binding from its specification (F301)". The payment cMIP reads them from the specification the receipt names. Development layer, a format change before the freeze, already decided; the encoding is the question. (Q6.)

### D6. The MICS, the test suite and MOR 2's MIPs have no kind. Text. Wording with a decision half taken (F291).

**Sentences.** Kinds: "0 cMIP, 1 Module, 2 unit, 3 media type, 4 MIR, 5 signature scheme". F291: two kinds added, the MICS document and a test suite, "not yet written". **Evidence.** The rehearsal publishes the MICS and the suite under kind 4, "PROVISIONAL", and the listing calls them MIRs. A MIP toward MOR 2, if published under kind 4, is a MIR to every reader, distinguishable only by not being one of the six; it has no creator either (kind 4 forbids one), so who drafted it is only the publication's signer, and the "fork that makes sense" F289 wants adoption to sort cannot be told from the protocol's own text by its kind. **Smallest fix.** Three kinds, not two: 6 the MICS document, 7 a test suite, 8 a MIP (a proposal toward a successor protocol; a creator required, since a proposal is somebody's; a predecessor field naming the MIR or MIP it forks). Cost: one line of the format; it is what F289's "anyone can fork it, if a fork makes sense people will be tempted to work off it" needs to be seen. (Q5.)

### D7. The creator's identity as a single point of failure: mostly held; the fragility is step 17's order. Text. Noted, with one wording.

- **A rotation changes nothing.** A spec hash covers the creator's identity hash, which is its genesis id and survives every rotation; a lost signing key, a new scheme, a succession leave every founding hash as it is.
- **A thief with the creator's signing key** publishes a malicious specification in the creator's name: rule 3 counts it as the creator's (signed by that key); the creator's rotation disowns it (Identity rules 15 to 17), and under F297 and rule 3's second sentence it becomes "unclaimed by that creator", shown. Agreements that named it keep naming a hash, and adoption was each user's choice: the harm is reputational and visible. One wording: rule 3 should say what a disowned publication does ("a publication the creator's rotation disowned leaves the specification unclaimed, as if never published by it").
- **A creator gone** (death, no succession): the specification stays frozen and usable; anyone publishes a successor naming it as predecessor (rule 25), shown with the creator mismatch; fees (field 7) default "paid: the creator", so they go to an identity that cannot sign receipts, which is a plan's business (rule 14: only the agreement's fee entry makes a fee owed; the owners stop naming it). Held.
- **The genesis repository** is on GitHub; F277 releases the code on MOR with the archive and browser both; F287 mirrors reports both ways. Nothing is held hostage that a release on MOR does not also carry.
- **The fragility.** Every founding cMIP's and Module's hash is computed after the author's genesis (the rehearsal's item 2), and every client is rebuilt with them; the genesis cannot be redone without redoing every hash and every release. The rehearsal exists for this and it is the right instrument; the only recommendation is that step 17's written order make the genesis the first act, computed and checked from outside before any hash depends on it, which the rehearsal already does.

### D8. "Implements" names a copy, not the specification. Text (the release manifest cMIP). Wording.

Field 6 of the manifest names "the act ids of the publications of the specifications it implements", so that "a reader finds the specification where the release points". A publication is one copy; the same specification published by three identities has three ids; a reader holding another copy than the one named shows "not found" (F298: unknown) for a specification it holds. Naming the spec hash is stable and copy-independent, and the listing already resolves a hash to every publication it found. Fix: field 6 names spec hashes; a publication id may be given beside each as a hint, never as the name. Development layer; one line. (Q7.)

### D9. Succession and forks of specifications; the way out to MOR 2. Text. Held, with two notes.

- **Who may publish the next version of a cMIP whose creator is gone:** anyone (rule 25), shown with the mismatch; adoption decides; no registry to capture. Held.
- **How MOR 2's MIPs fork (F286, F289):** the six texts are cloned as MIPs under their own kind (D6), forked freely; a successor protocol changes the prefix (rule 27), so every spec hash, including every cMIP's, changes with it: `tagged_hash("MOR/spec", ...)` is itself prefixed. Every agreement naming a cMIP by hash is therefore re-signed (cloned across) in MOR 2, never reinterpreted, as rule 27 says; the texts carry across unchanged. Held, and worth one sentence in rule 27: "a successor's specifications have new hashes, since the tag prefix is part of the hash; agreements name them afresh by cloning".
- **Identity's successor field** names a protocol by a string ("mor"); MOR 2's name is a MIP's to fix, and the link cMIP for "a succession to another protocol" (F300) does not yet exist. Noted for the path document.
- **Nothing held hostage:** the texts, the hashes, the releases and the reports are each publishable by anyone; the author's identity is needed to sign the first releases and nothing after.

## The verdict vocabulary

Development's own verdicts: *valid, invalid, pending, unknown* from a rule (rule 22's output), which are the core's; *unknown until adopted* (rule 10), which is the core's unknown; *unclaimed* (rule 3) and *creator mismatch* (rule 25), which are records a client shows, not verdicts, and should be said to be so; *invalid* for a specification's content (field 10, field 12), which decides nothing for any act until D2 says what it decides. Nothing here fails the admission test once D2 is written; "a specification is invalid" is the one phrase that today has no consequence a verifier produces.

## What held under attack

- The same text is the same specification wherever published, and a stranger's republication changes nothing (F41), within D1's caveat on optional fields.
- A specification naming a creator who never published it is unclaimed; a thief's publication in the creator's name is disowned into the same state.
- A binary rule in the content field is refused by the format (field 9 is text; `rule-ref` is a hash of a locked object).
- Six other hashes are a different protocol, and no act replays across the prefix.
- An extension relaxing a core rule is overridden by the core's own checks (rule 20; the split check in Agreements).
- The way to MOR 2 carries every text and holds nothing back.
