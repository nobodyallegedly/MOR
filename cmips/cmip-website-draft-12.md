## Reassessment (new in draft 12)

*In plain words: this cMIP still has its whole job; the redesign changed a few of its words and one of its rules.*

**What it still does.** *It makes a website out of signed files on relays: the list of files and fingerprints, the gateway that serves it, the small frame that checks every page in the visitor's own browser, and, on a page, films, a feed of public posts, a box to write to someone, and a listing of specifications. None of this is in the core, and none of it is about selling, so the redesign's publications and price tags never enter it.*

**What the redesign changed for it.** *Four things. The act that carries a version of a site was called a publication; it is a* ***bake*** *now, "I uploaded this", and "publication" is kept for the act that sells. A bake is* ***never withdrawn****: draft 11 let an owner withdraw a version and readers look for withdrawals; that rule goes, and an owner who wants a version gone uploads a later one, the old one staying on record, as every act does. A collective* ***has no key****: draft 11 had the collective sign its site with its own key; now a member uploads the site for the collective, naming it, as a release is uploaded. And* ***the layers are numbered anew****: a listing reads a specification's field 10 from 0 to 4 and names Text and Envelopes apart.*

**Should it retire?** *No. dubsar.org is served by it, and nothing else in MOR shows a site, a feed or a listing; draft 12 is draft 11 with these corrections.*

## In plain words

*A website is a handful of files: pages, a stylesheet, pictures. Here, the site's owner publishes a list of those files, each with its fingerprint, signed with their identity, on relays, the same way a release of the code is published. Anyone can fetch the list and the files and check that every byte is what the owner signed.*

*Most people do not fetch files from relays: they type a domain into a browser. A gateway is what stands at the domain. It fetches the site from relays, checks it, and serves it. But a browser trusts whoever answers at the domain, so a gateway could lie. That is why the pages never come alone: every page is shown inside a small frame of the gateway's own software, which carries the core library and checks, in the visitor's own browser, who signed the site and whether the page matches what they signed, and says so above the page. A page that does not match is not shown.*

*That frame is itself served by the gateway, so a gateway that is hostile could change the frame too. No page can check the code that checks it. What this cMIP does about that is to make the frame small, the same for every site, and taken from MOR's own signed releases, built so that anyone can rebuild the very same bytes from the source, so that anyone can compare what a gateway serves with what was released, from somewhere else; and to keep every byte of the site checkable without any gateway at all.*

*A page may also let a visitor write to some identities (draft 7): a small box, the frame's own, where the visitor chooses to whom, and whether the note is private (sealed so that only that identity can open it) or public (readable by anyone who holds it); either way it is signed by an identity made for that one note and forgotten. A public note appears on the page only once one of the identities answers it.*

*A page may also show what some identities say in public (draft 6): it names them, and the frame finds each one's posts through its homes and routes, checks every post in the visitor's browser, and shows them newest first, in the only order MOR can prove: an act signed after another names it. A post it cannot check is shown as not checked, and its words are not shown.*

*That order cannot say whether one person's post came before another's when neither names the other. So a page may also name a clock (draft 8): an identity that signs "I held this post at this time". Where the posts carry its stamps, the frame orders them by those times, across identities, and says whose order it is: the clock's word, nothing more. A reply still never comes before what it answers.*

*A page may also list specifications (draft 9): it names some relays, and the frame reads what is published there. First, the extensions: an extension is a cMIP an agreement names for work the core did not foresee, so each one marks a place a later protocol, MOR 2, may answer; the frame counts, from the public agreements it finds, how many name each one, and links to their terms. Private agreements cannot be read, so they are not counted, and it says so. Then (draft 10) it counts how much each xtype is used: an xtype defines new kinds of acts, so the public acts of those kinds found on the relays show who uses it, and private acts, whose kind cannot be read from outside, are not counted, which it says. Then it finds the cMIPs and Modules among it, checks each one in the visitor's browser, and shows what each says it is, who made it, its drafts in order, and whether code is released for it: from draft 10, a release says which specifications it implements in its own signed list, read first. It says first that it is one listing among any: anyone can read the same relays, or others, and list differently; being listed decides nothing (Development rule 17, "No core registry"). From draft 11, the proposals toward MOR 2, the MIPs, are shown in a part of their own: each forks a MIR, or another MIP, and the listing shows, for each MIR, the MIPs that fork it and how many fork each, since forks that make sense draw others to work from them. The MICS document and a test suite are shown as what they are, not as MIRs; and two bakes of one text that differ only in what their optional fields say are two specifications, shown together as versions of one text.*

*A gateway carries the sites its operator chose, and no others. For each, the operator says which version it serves. A site someone else uploads follows its owner's latest version, by default: when to change their content is the owner's call, not the operator's. The operator's own sites are set as the operator wishes; pinning one version guards against a stolen key. Whatever the gateway serves, the frame in the visitor's browser looks for later versions itself, and says when a newer one exists.*

## Purpose

This cMIP defines:

- the site manifest: a media type describing one version of a website, file by file;
- how a site is published, and what counts as a version of an identity's site;
- how a site is shown: what a display client checks and what it may display;
- what a gateway is: a display client served from a domain, carrying the sites its operator chose, each at the version its operator sets;
- which versions are later than another, with no clock;
- from draft 6, how a page shows the public posts of identities it names (rule 13a), from draft 7 the visitors' notes they answer, and from draft 8 their order by a clock the page names;
- from draft 7, a writing box: how a visitor writes to an identity a page names (rule 13b);
- from draft 9, a listing: how a page shows, from the relays it names, the cMIPs public agreements name as extensions, how often, and then the specifications published there (rule 13c); from draft 10, how much each xtype among them is used, by its public acts; from draft 11, the MIPs in a part of their own, by the MIR they fork, and versions of one text;
- what a hostile gateway can and cannot do (the stated cost of roadmap step 10a).

It fills no task of the MICS: it is a new kind of thing built from core pieces (Development rule 8a). It adds rules; it relaxes none.

## The site manifest

A version of a site is a media object, public, described by a bake (Envelopes type 0) whose media spec (field 0) is this cMIP's spec hash. The bake describes the manifest (Envelopes, "Media"): its work hash, locked hash, size, nonce and key are the manifest's own, and its field 6 lists where the manifest and every file can be fetched.

```cddl
site = {
  0 => tstr,            ; name: what the site is, e.g. "dubsar.org"; a label, never an address
  1 => hash / null,     ; previous: the act id of the previous version's bake; null for the first
  2 => [+ file]         ; every file, sorted by path (byte order of its UTF-8), no path twice
}

file = [                ; exactly as in the release manifest cMIP
  path: tstr,
  work: hash,           ; tagged_hash("MOR/work", the file's bytes)
  size: uint,
  locked: hash,         ; SHA-256 of the file's locked bytes, as stored
  nonce: bstr .size 24,
  key: bstr .size 32    ; its content key: a site is public
]
```

1. **Closed format.** A manifest with a key this cMIP does not define, a field of the wrong kind, an invalid path, or paths out of order or repeated, is invalid. Every `tstr` is canonical text (Text MIR).
2. **Paths.** A path is one or more segments separated by `/`. Each segment is made of the characters `a` to `z`, `0` to `9`, `-`, `_` and `.`, is not empty, does not start with `.`, and is at most 100 characters long; a path is at most 512 characters long. The last segment has an extension: a `.` followed by one of the extensions in rule 4. *Lower-case ASCII only: no two paths that look alike, nothing for a browser or a server to rewrite, and the same path on every operating system.*
3. **Addresses.** A file at path `p` is at the address `/p` under the place the site is served from. The file `index.html` of a folder, or of the site, is also at the folder's address followed by `/` (the site's own at `/`). *Links between pages are relative, so a site reads the same at a domain, at an onion address, or under any other address.*
4. **Kinds of file.** The extension of a path decides what its file is. A path with any other extension is invalid.

   | Extension | Kind | Shown as |
   | --- | --- | --- |
   | `.html` | page | a page (rules 11 to 17) |
   | `.css` | stylesheet | the look of the pages that name it; on its own, plain text |
   | `.jpg` | picture | a JPEG (the JPEG Module), stripped to the picture alone before publishing |
   | `.txt` | text | plain text, UTF-8 |
   | `.mp4` | film | a film (the video Module), stripped to the film alone before publishing (draft 4) |

   *Kept small on purpose. Each kind added is a kind every display client must show safely; a picture format other than JPEG, or a film in another format, waits for its own Module, and files to download belong in a release.*

5. **A site has a front page:** `index.html`. A manifest without it is invalid.
6. **Pictures carry only the picture.** A JPEG is published stripped to the picture alone (JPEG Module, rule 6): no location, camera data, previews or hidden pictures. *As a posting client does (decided by Nobody, allegedly, 30 September 2026, for posts).*
6a. **Films carry only the film.** A film is published stripped to the film alone (video Module, rule 10): no place, dates, titles, names, free space or unused data; and it is one the video Module plays (its rules 2 to 9), within its limits. *A publishing tool refuses any other film, saying why. A site accepts a film of at most 67,108,848 bytes (video Module, rule 9): one media object of 64 MiB once locked, what the homes accept by default. A longer or sharper film needs the media cMIP that serves one object in parts from many homes (F243), not yet written.*
7. **Files are media objects,** locked one by one (Envelopes, "Media": XChaCha20-Poly1305, no associated data). *A file unchanged since the previous version is the same object: the same locked bytes, nonce and key, so a new version uploads only what changed (release manifest cMIP, rule 2).*

## Publishing

1. **Uploaded for the site's owner** (rewritten in draft 12). A version is a public bake. A person's site is uploaded by the person, with their own key. **A collective's site is uploaded as its releases are** (release manifest cMIP draft 5, "Publishing", rule 1): a member uploads the bake with their own key, naming the collective in its `objects` (the collective's identity as chain, the decision the member acts under first; Agreements rule 58), and the members the collective's rule needs beyond the uploader add their signature acts ("What counts as a version", rule 3). *A bake carries no `for` (its field 8 is refused): the collective is named where every act for a collective names it.*
2. **The bake first,** then the manifest's locked bytes, then every new file's, on the relays named in field 6. *As for a release: a relay that keeps media only for bakes it holds then keeps the manifest.*
3. **Chains carried along.** The uploader carries their identity-chain acts to those relays, and, for a collective's site, the collective's (new in draft 12), so that whoever knows only a relay finds the genesis, and from it the homes.
4. **One version names the one before.** *Nothing is updated. A new version is a new act; the old one stays on record and still verifies.* A version names as its previous only a version of the same identity's site: for a collective, of the collective's, whichever member uploaded it (new in draft 12). *Publishing tools refuse otherwise; a manifest naming someone else's version is still a valid manifest, and it is simply never followed to (see "Later versions").*

## What counts as a version

A bake P is a version of identity S's site when:

1. P is valid (Envelopes, "The act"), public, of Envelopes type 0, and its media spec is this cMIP's hash;
2. **new in draft 12:** where S is a person (its genesis declares a signing key), P's uploader is S, and P's standing for S's identity chain is valid: bound by a counting chain act, and not voided by a later rotation (Identity). Where S is a collective (its genesis declares its founding agreement in place of a signing key; Identity rule 1), P's uploader is another identity, P names S in its `objects` as rule 1 of "Publishing" says, and P's standing for its uploader's identity chain is valid;
3. **Agreements' answer for P is met,** as for a release (release manifest cMIP draft 5, "What counts as a release", rule 3; **rewritten in draft 12**). Where S is a collective, **P counts for S** as Agreements judges an act done for a collective (rules 57, 58, 60, 65, 71 and 72): done (public, on S's chain, citing its latest decision as its uploader knew it), its uploader and the members whose signature acts name it meeting the rule that reaches it under the agreement in force for P: that of an area within the Envelopes layer whose kinds name Envelopes bakes, where one does, and otherwise the rule the founding names for the **Envelopes layer** (terms field 19, key 2; draft 11 said "the Envelopes and Text layer", one layer before the redesign). *A collective cannot give its site to one member and its releases to another by area alone, since both are Envelopes bakes, of one type (a stated cost, as F106's).* Where S is a person, S's own upload suffices. *Draft 11's reading of the collective's key and its declarations, and its wait for Agreements draft 7's approval, are gone: the collective has no key, and every collective now names a rule for each layer;*
4. *retired in draft 12:* draft 11's rule, "no withdrawal of P by S is found where the verifier looked", is gone with withdrawal itself: a bake is never withdrawn by the protocol (Envelopes rule 24, retired; an act of type 3 is invalid). *An owner who wants a version gone uploads a later one; the old one stays on record and still verifies, as every act does. The numbers of rules 1 to 5 are kept, so that what cites them still reads;*
5. the manifest is valid, and matches the bake's work hash and size.

*Which version is current is not something MOR can say: it has no clock. What it can say is which versions come after another, by the names they carry (see "Later versions"). A gateway serves the version its operator's settings lead to (see "Gateways"); a visitor sees which version that is, and is told when a newer one exists.*

## Later versions

*MOR has no clock, so "latest" is read from the versions themselves. Each version names the one before it; the versions after a version V are those that name V, then those that name them, and so on. Each must be a version in its own right.*

A. **A successor.** A version Q is a successor of a version P when Q is a version of the same identity's site as P (rules 1 to 5, that identity as the one expected: P's uploader, or, for a collective's site, the collective P names; new in draft 12) and Q's manifest names P as its previous.

B. **Later versions.** From a version P, following goes from P to its successor, and on, as long as there is exactly one. The **latest version from P** is where it stops: P itself when P has no successor found.

C. **A fork stops following.** Where a version has two or more successors, following stops at that version, and whoever follows says so, naming the successors. *Two versions naming the same one, both signed by the owner, mean that two people hold the owner's key, or that the owner made a mistake; either way, choosing one would be a guess. The owner settles it by a rotation that voids the thief's, or, for their own mistake, by a rotation whose kept history leaves out the version they disown (Identity rule 34). New in draft 12: draft 11's "by withdrawing one" is gone, a bake being never withdrawn.*

D. **Where it was looked for.** Successors are found among the bakes of P's uploader (for a collective's site, of its members, naming it) that the places asked hold (relay transport cMIP, "Following": the feed by signer), each checked in full. *Silence proves nothing: a later version on a relay nobody asks is not found. New in draft 12: draft 11's sentences on a withdrawn version are gone with withdrawal. For a collective's site, successors are found among the bakes naming the collective, whoever uploaded them, each a version only where rule 3 finds it counts for the collective.*

## Showing a site

A **display client** is software that shows a site to a person. It is given a version (P's act id), the identity it expects (S), and places to look. *The gateway's frame, below, is one; a command-line verifier that writes the files out is another.*

8. **Check before showing.** A display client shows a file only once P is a version of S's site, by the rules above, judged by the core library on the visitor's own device, and the file's bytes match their manifest entry (work hash and size). It never shows a file whose bytes it has not checked, whoever served them.
9. **Say who signed.** Beside every file it shows, outside the file's own display, a display client shows: whether the version verified, in plain words; the signer's whole fingerprint (the identity hash, as the web reader shows it); whether the signer is the identity the display client was told to expect; and P's act id. *Outside: a page cannot draw over it or remove it.*
10. **Fail visibly.** A version that does not verify, or a file that does not match, is shown as failing, with the reason, and the file is not shown. *Client conformance.* A display client SHOULD NOT fall back to bytes from another source for a file the gateway served wrongly without saying so: what a gateway served wrongly is itself what a visitor needs to know.

### Pages

A page is an HTML document, UTF-8. What it may use, and how a display client shows it:

11. **No code runs.** Nothing in a page runs: a display client shows a page in a context where scripts are disabled, and drops `script`, `noscript`, `iframe`, `frame`, `object`, `embed`, `form`, `base`, `meta` that refresh or redirect, every attribute starting with `on`, and `style` elements and attributes. *A site is pages to read, not a program. A page's look comes from its stylesheets. (Decided by Nobody, allegedly, 1 October 2026: a page is HTML with no scripts.)*
12. **Nothing from elsewhere.** A page uses only files of the same version: pictures (`img` with `src` naming a picture's path, relative to the page), stylesheets (`link` with `rel="stylesheet"` and `href` naming a stylesheet's path), an icon (rule 16a), and films (`video` with `src` naming a film's path, relative to the page, and optionally `poster` naming a picture's path, rule 12a; and, from draft 5, `mor-film` naming them the same way, rule 12b). A display client loads them only from what it has checked, and drops any other reference that would load something (an address on another site, `srcset`, `picture` sources, a `video` or `mor-film` naming anything but a film of the same version, a `video`'s `source` and `track` children, a `poster` naming anything but a picture of the same version, `audio`, a stylesheet's `@import` and `url()`). *A visitor's browser asks no third party for anything while a page is shown, so no third party learns who reads it.*

    12a. **Films.** A display client shows a page's film in its own player, in the place the `video` element takes, apart from the page (as it shows an act, rule 13): the page sets where the film goes and, with its stylesheet, how large its place is; nothing else of the `video` element counts (its `autoplay`, `loop`, `muted`, `controls` and `preload` are dropped).
    - **The poster** is a picture of the version, checked when the page is (rule 8): a poster that does not match fails the page, as a stylesheet does. It is shown in the film's place until the film plays.
    - **On the visitor's action.** A display client fetches a film only when the visitor asks to play it, then checks its bytes against the manifest (rule 8) and reads them by the video Module (its rules 2 to 9), and only then plays it: inline, with the player's controls, never starting with sound on its own (video Module, rule 11). *A film costs its size to fetch; a visitor who does not play it pays nothing, and the gateway learns who played it only from those who did.*
    - **When it does not match:** the film is not played, its place says so, and the line beside the page (rule 9) names it as failing, with the reason (rule 10). The page itself, checked on its own, stays shown.
    - **When it cannot be played:** a display client that cannot play a film (a browser that plays no H.264, a film the video Module refuses, a decoder that stops) says so in the film's place, leaves the poster, and names the film in the line beside the page as not played, and why; it fetches nothing it knows it cannot play (video Module, rule 12). *The rest of the page is unaffected. A gateway that cannot fetch a version's film whole does not serve that version (rule 18); following, it serves the one before (rule 23).*
    - The line beside the page (rule 9) lists every film the page shows, and whether it was fetched, verified, failing or not played.

    12b. **Films listed** (draft 5). *A page may show several films. The film shown in the page (rule 12a) is its main film; others can wait behind a short label, so that the page stays light: a visitor who does not ask for them fetches nothing of them.* An element `mor-film` whose `src` names a film of the same version, relative to the page, and optionally whose `poster` names a picture of the same version, lists that film. Its **label** is the element's text, its spaces run together; nothing else it holds counts (an element inside it is dropped with it), and a `mor-film` without text is labelled by the film's path. A display client shows a listed film as a small button carrying its label, in the place the `mor-film` takes, apart from the page (as for a film, rule 12a): the page sets where the button goes and, with its stylesheet, how it looks.
    - **Only what the version holds.** A `mor-film` naming anything but a film of the same version is dropped, label and all: no button is shown for it. *So a page may name a film that is not yet published; its button appears with the version that holds it.*
    - **The poster** is checked when the page is (rule 8), as for a film shown in the page: a poster that does not match fails the page. It is shown when the film is opened, until it plays.
    - **Played over the page.** Pressing the button opens the film over the page, in the display client's own player, under every rule of 12a: fetched only now, checked against the manifest and by the video Module, played inline, never starting with sound on its own, its failures said in its place and in the line beside the page. *The press is the visitor's ask to play it, so the player starts fetching at once.* A display client lets the visitor close it with a visible control, the Escape key, and a press outside it, and stops the film when it closes. It plays one film at a time.
    - The line beside the page (rule 9) lists every listed film with its label, and its state as for any film.
13. **Acts shown as acts.** An element `mor-act` whose attribute `act` holds an act id (64 lower-case hex digits) is shown as that act: fetched, checked and judged through its signer's identity chain by the display client, with its own signer and standing, as the web reader shows a post. A display client shows each act apart from the page's own styles, and lists every act the page shows, with its standing and its signer's fingerprint, beside the page (rule 9). *The site holds the link; the act stays the act, signed by whoever signed it, and is not copied into the site. A page's stylesheet could still draw over an act's box, so what counts is the list beside the page, which the page cannot touch.* A display client that cannot show it shows its id and why.

    13a. **Feeds** (draft 6, *new, for Nobody, allegedly, to approve*). *A page may show the public posts of identities it names, newest first, each checked in the visitor's browser as the page is. Which identities is the page's list: showing more is a new version of the site naming them, never a change to the display client.* An element `mor-feed` shows the public posts of the identities named by the `mor-author` elements it holds: each with an attribute `identity` holding an identity hash (64 lower-case hex digits), and its text, its spaces run together, the page's name for that identity. A `mor-author` without text is named by its fingerprint. A `mor-author` naming no identity hash, or one already named, is dropped; nothing else a `mor-feed` holds counts; a `mor-feed` naming no identity shows that it names none, and fetches nothing.
    - **Where the posts are looked for.** For each identity named, a display client looks it up (Identity, "Reaching an identity and relating to others"; relay transport cMIP, "Querying an identity"): its genesis from the places it was told to look (rule 21: the gateway's relays), its chain and routes from the homes its chain names. It asks for the identity's acts (relay transport cMIP, "Following: the feed", by signer) at the places its outbox route for the Text MIR names, or, with none, its outbox route for everything else, then at the places it was told to look. It does not try an address it cannot reach from the visitor's device (from a browser, an onion address or plain http), and says so (*client conformance*). A **post** is a public text act (Text MIR, type 0) the identity signed. *Silence proves nothing: a post at a place nobody asks is not found.*
    - **Each post checked.** A post is shown as verified only once the core library, on the visitor's device, judges it valid for its signer's identity chain, as the web reader shows a post; its pictures are shown only as the reader shows them, checked against their bake.
    - **A post it cannot verify** (its signer's chain not found, its standing not valid, the act unreadable) is shown in its place as not verified, under the name of the identity it names as its signer, with the reason; its words and pictures are not shown. *As rule 10 for a page: what failed is itself what the visitor needs to know, and unverified words are not shown as if they were someone's.*
    - **Signed order, newest first.** MOR has no clock (Envelopes rule 16), so a feed is in signed order, unless it is ordered by a clock the page names (below, draft 8): a post comes after every act it names by hash (its previous act in the signer's sequence, the acts it refers to, the chains it follows, the acts it acknowledges), followed through every act of the identities named that was found, not only their posts. A reply therefore comes after the post it answers, and an identity's own posts are never reversed. Where no signed link orders two posts, a display client lists them by the page's order of identities, then by the higher position in the signer's sequence, then by act id, and says that this order is not a time. A hint (Envelopes, the act's field 9) never orders a feed. *Decided by Nobody, allegedly, 12 October 2026: "Signed order only. There will be interactions between the two to sort."*
    - **Ordered by a clock** (new in draft 8). *Signed order cannot sort posts across identities when nothing links them; a plain timestamp clock can. "A feed like the public feed could easily rely on a dumb anchoring"; "Anchoring precision and probability only matter when there is something to protect" (Nobody, allegedly, 13 October 2026). A feed's order protects nothing, so the clock's word is enough, and the feed says whose word it is.* A `mor-feed` may hold an element `mor-clock` with an attribute `identity` holding an identity hash, and its text, its spaces run together, the page's name for it (named by its fingerprint where it has none): the **clock** the feed listens to, a timestamp clock (the timestamp clock Module, under the anchoring cMIP), on the reference `[ the Module, that identity ]`. Only the first `mor-clock` naming an identity hash counts; any other is dropped.
      - **Its stamps.** A display client looks the clock up as it looks up an identity named (above), and asks for its acts, by signer, at the places its outbox route for the timestamp clock Module names, or, with none, its outbox route for everything else, then at the places it was told to look; each stamp is judged valid for the clock's chain by the core library on the visitor's device (the Module's proof). A stamp signed by any other identity is never asked for, and orders nothing.
      - **Each post's time.** A post is placed at the earliest time among its own stamps and the stamps of every act found naming it, directly or through others (the Module's "Reading the stamps of linked acts"): *an act existed by the time anything naming it was stamped.*
      - **The order.** Where at least one post found carries a time, a display client orders the feed newest first by time, while still never showing an act before an act it names (signed order holds throughout): among the acts free to come next, a post with no time first (the clock has not stamped it nor anything naming it; *newest, as far as anyone can say*), then the later time, then as in signed order. Where no post found carries one, or the clock cannot be looked up, the feed is in signed order.
      - **Said.** A feed ordered by a clock says so in plain words, naming the clock by the page's name: "ordered by" its stamps, its word only; beside each post, the time the clock gives it (in UTC, the same on every device), or that it has none. Beside the page (rule 9), the clock with its whole fingerprint, where its stamps were asked for, how many were found and verified, and how many posts they place. *Client conformance.*
    - **Replies.** A post naming a text act among its references answers it. A display client shows a reply with the post it answers, when found: shown, checked as any post, when signed by an identity the feed names; named by its signer's whole fingerprint and not shown, when signed by any other; said to be not found otherwise. *Option (a), "keep it clean": a feed shows the words of the identities it names, and no one else's.*
    - **Visitors' notes** (new in draft 7, F275). Where a post the feed shows is signed by an identity it names and names among its references a public text act signed by an identity the feed does not name and addressed (`to`) to one it names, that act is a visitor's **note**: a display client shows it beside the post, above it, checked as any post (a note it cannot verify is shown as not verified, its words not shown). A note no such post names is never shown. *"If it's not worthy of fitting the tableau, it goes unanswered" (Nobody, allegedly). This replaces, for notes, the reply bullet's "named by its signer's whole fingerprint and not shown".* A display client looks for a note where the post's reference leads (the places it asks for the feed); once a reference names its signer (F272, Envelopes field 8), also at that signer's routes. It labels the note by **who picked it**, as the signed acts show:
      - **"Picked by"** the signer of a pick (nudge cMIP, type 2) the post names, signed by an identity the feed names, naming the post's signer as its agent (field 0) and the note as the act picked (field 2), public and valid for its signer's chain;
      - else **"Picked by"** the post's signer, where the post names a nudge (nudge cMIP, type 1) signed by an identity the feed names, naming the post's signer as its agent, with a count of at least 1, public and valid: the agent chose the note under it;
      - else no pick is shown, and the post, the answer, reads **"Answered by"** its signer.
      *As set by Nobody, allegedly, 13 October 2026: the note he picked shows "Picked by Nobody, allegedly", Machine, allegedly's reply below it under its name alone; a note Machine, allegedly, chose under his nudge, "Picked by Machine, allegedly"; his own replies, "Answered by Nobody, allegedly". A label rests on the signed acts only: whether the agent kept its published terms is the nudge cMIP's reading (its items 11 to 13), not made here (a stated cost).*
    - **Apart from the page, said beside it.** A display client shows a feed apart from the page's styles (as an act, rule 13), and lists beside the page (rule 9), for every feed, each identity it names with its whole fingerprint, where its posts were asked for, what could not be reached, and how many posts were found, shown and verified; from draft 8, its clock, as said above. *The names are the page's words; the identities are what was checked.*
    - **How many.** A display client MAY show only the first posts of the order (this cMIP's display client: 30), saying how many it leaves out.
    - **Read only.** Nothing in a feed signs, posts or sends; a display client keeps nothing of it in the visitor's browser, and asks nothing of anyone but the gateway and the places named above.

    13b. **A writing box** (new in draft 7, F275). *A visitor may write to an identity a page names, from the page. No code runs in a page (rule 11), so the box is the display client's own, laid over the place the page gives it, as a listed film's button is (rule 12b): MOR's released code, the same for every site (rule 20), never the page's.* An element `mor-write` holding `mor-author` elements (as in rule 13a) names the identities a visitor may write to; nothing else it holds counts, and one naming no identity shows that it names none. A display client shows in its place a box with a switch between the identities named, a switch between **private** and **public**, a place for the text, and a button to send; beside the box, in plain words, what the choice means and that nothing is kept in the browser (*client conformance*).
    - **Signed by a one-time identity.** A note is a text act (Text MIR, type 0) addressed (`to`) to the identity chosen, signed by an identity the display client makes for that one note in the visitor's browser, as the web reader does: its genesis receipted by the homes the gateway's settings name for it (rule 21) and carried to the inbox relays, its chain key committed and forgotten at once, its signing key forgotten once the note is signed. Nothing is kept in the browser.
    - **Private:** the note is sealed to the chosen identity's current encryption key (Envelopes, "Sealed containers") and left in its inbox. It is never shown on any page.
    - **Public:** the same note, carrying its content key, left unsealed in the chosen identity's inbox. Anyone who holds it can read it; a feed shows it only beside an answer (rule 13a, "Visitors' notes").
    - **Its inbox** is the chosen identity's inbox route for the Text MIR, or for everything else, read from its routes as the core library counts them. An identity that declares none, or, for a private note, has no encryption key that counts, cannot be written to; the box says so and sends nothing.
    - **Said beside the page** (rule 9): each box, with the identities it writes to by their whole fingerprints.
    13c. **Listings** (new in draft 9, F288). *A page may show the specifications published on relays it names: a window onto discovery through use (Development rule 17), one among any. Which relays is the page's list: reading another is a new version of the site, never a change to the display client.* An element `mor-listing` reads the relays named by the `mor-relay` elements it holds: each with an attribute `address` holding a relay's address (`https:`, or `http:`), and its text, its spaces run together, the page's name for it. A `mor-relay` naming no such address, or one already named, is dropped; nothing else a `mor-listing` holds counts; a `mor-listing` naming no relay shows that it names none, and reads nothing.
    - **One among any, said first.** A display client shows, before anything it lists and in its own words, that this is one listing among any, that anyone can run another, and that it decides nothing and refuses nothing: a specification is named by its hash, not by being listed (Development rules 1 and 17). *Client conformance.* It hides nothing it found: every bake of a specification found is shown, verified or not.
    - **Extensions first** (F288). *"What really matters for MOR2 is the tracking of extensions" (Nobody, allegedly). An extension is a cMIP an agreement names in its terms, field 15, for work the core did not foresee (Development rule 19): each marks work a MIP of MOR 2 may answer.* Before the specifications, a display client shows the extensions the agreements it read name, under the words "Each extension marks work the core did not foresee: the raw material of MOR 2." (*client conformance*):
      - **Which agreements.** Public terms (Agreements type 0) found at the relays named, each judged valid for its signer's chain, with the signature acts (type 1) found there and every party's chain looked up, all by the core library on the visitor's device. An agreement **counts** once the core library says it exists (every signature its signing rule asks for, a deal or founding terms) or, a collective's clone, that it is ready; terms not yet signed are proposals, not counted; terms invalid or not verified are not counted. The versions of one agreement (a clone naming its parent, field 11, followed back as far as found) are one agreement.
      - **Private agreements are not counted.** Their terms cannot be read. A display client says so in plain words beside the counts, with how many private acts and sealed containers it found and did not open, and how many proposals and terms it did not count. *Client conformance.*
      - **For each cMIP named as an extension** (terms field 15) by an agreement counted: how many agreements name it; its name where its specification is listed (below), else that it is not found at the relays read, by its hash; the **layers the work touches**: Development (an extension's own acts belong to Development, F106) and the layers its field 10 declares, where its specification is listed, else not said; and the public terms of each agreement naming it, by act id, each a link to it in the reader the `mor-listing`'s attribute `reader` names (an `https:` address, the act id after `#`), opening on the visitor's action outside the site (rule 14), or as plain text where it names none.
      - **Most named first,** then by name.
    - **Xtypes, by use** (new in draft 10). *F288's note: adoption, beside extensions. An xtype defines act types and fills no task (Development rule 18); every act names its type within the specification that defines it (Development rule 2), so an act of an xtype's type names the xtype's spec hash.* After the extensions and before the specifications, a display client shows, for each xtype it lists (below: a specification defining act types, field 3, and filling no task), the **public acts of its types** found at the relays named: public acts whose spec is the xtype's spec hash and whose type is one its field 3 defines, each judged valid for its signer's chain by the core library on the visitor's device. It shows how many, in all and by type (by the names field 3 gives), with how many it found that are not valid and did not count; each draft is its own specification, counted on its own; the most used first, then by name. The same count is shown on the xtype's card. **Private acts are not counted:** which specification a private act belongs to cannot be read from outside, and a display client says so in plain words beside the counts. *Client conformance.*
    - **What is read.** A display client asks each relay named for everything it serves (relay transport cMIP, "Following: the feed", with no filter), page after page; it does not try an address it cannot reach from the visitor's device (from a browser, plain http other than the visitor's own machine), and says so (*client conformance*). It MAY stop after a number of acts per relay (this cMIP's display client: 5,000), saying where it stopped. A **bake of a specification** (new in draft 12: drafts 9 to 11 said "a publication of a specification") is a public bake (Envelopes type 0) whose media spec (field 0) is the Development MIR's spec hash: the specification's content as its media (Development, Part three). *Silence proves nothing: a specification on a relay nobody reads is not listed.*
    - **Each one checked.** A specification is shown as verified only once: the bake is judged valid for its signer's identity chain by the core library on the visitor's device (its chain looked up from its homes, starting from the relays named, then the gateway's); its content, fetched from those places or the places its field 6 names, opens with its key and matches its work hash and size; and the content decodes strictly as Development's `spec` (only the keys it defines, each of its kind; field 9 canonical text; a creator for every kind but a MIR; field 10 ascending, from 0 to 4: **new in draft 12**, the six layers' numbers, 0 Identity, 1 Text, 2 Envelopes, 3 Money, 4 Agreements, where draft 11's 0 to 3 counted Envelopes and Text as one layer) in canonical encoding. **From draft 11, as Development draft 10 gives the format** (new in draft 11, F291, F322, F325): no creator for a MIR, the MICS document or a test suite (kinds 4, 6 and 7), a creator for every other kind, a MIP's (kind 8) included; and every field its kind requires, among them a Module's field 5, fields 11 and 13 on a Module whose field 5 names the payment cMIP (F301), and a MIP's predecessor (field 8), always, the MICS document for a MIP proposing a new layer (new in draft 11, F328, Q10). A content that does not decode so is no specification (F323), shown as below. Its spec hash is computed from the content (`tagged_hash("MOR/spec", content)`). Bakes of the same content are one specification.
    - **Versions of one text** (new in draft 11, F322). Two specifications whose content holds the same text (field 9) and differs only in other fields are two specifications, each with its own spec hash: *"two publications of one text that differ in optional fields are two specifications, which a listing shows as versions of one text." (F322's words, from before the redesign: "publications" there are what are now **bakes**, new in draft 12)* A display client shows them together, as versions of one text, each with its spec hash, its creator, the fields in which it differs from the others, and, on each, what agreements, acts and releases name that spec hash and no other; it never counts one for another. *A publishing tool writes every required field and no optional one it cannot fill from the text (Development draft 10, F322), so two honest tools publish one specification; versions of one text show where two did not.*
    - **What cannot be verified** (its signer's chain not found, its standing not valid, its content not found, not matching, or not a specification) is shown, in a part of its own, as not verified, with the reason and the act's id; nothing it says (its name, its fields) is shown. *As a feed does (rule 13a): unverified words are not shown as if they were someone's.*
    - **What each says it is,** from its own fields only, never guessed: its **name**, the first line of its text that holds a letter (a heading's `#` removed); its **kind** (field 0); the **tasks** it fills (field 2), each by its number and the name the Development MIR's table gives it, and its **layer**, the MIR the task names; for a Module, the **cMIP it works under** (field 5), by name where that cMIP is listed, its layer then that cMIP's, or the **MIR it works under** where field 5 names a MIR, its layer that MIR's (new in draft 11, F328, Q6); an **xtype**, where it defines act types (field 3) and fills no task (Development rule 18), its types by name; the layers it declares **for use as an extension** (field 10), each by its name, read in the six layers' numbers (new in draft 12); a rail Module's kind (field 11: a request rail or a push rail) and, from draft 11, the set its proof binds (field 13: payee, purpose, previous hop), as its fields give them (new in draft 11, F301); and **field 12**: that it checks proofs of proven deliveries (new in draft 12: Agreements' word, where draft 11 said "proven offers"), the field that serves discovery (Development, Part three). The layer of an xtype, or of a cMIP filling no task, is Development (its own acts belong to Development). A cMIP saying none of these is shown as naming no task and defining no act type. **The MICS document and a test suite** (kinds 6 and 7) are shown as such, by their kind's name, never as a MIR, and a MIR (kind 4) as a MIR (new in draft 11, F291); each with no creator, its bake's uploader shown only as who uploaded it (below, "Its creator"). *Being an extension is what an agreement makes of a cMIP (terms field 15), not what it says of itself; field 10 is what it says.*
    - **Its creator.** The creator's whole fingerprint (field 1). *A MIR, the MICS document and a test suite name none: the bake's uploader is shown, as who uploaded it, never as its creator (new in draft 11, F291).* A specification whose creator uploaded it is shown as uploaded by its creator; one whose creator's bake was not found is shown as **unclaimed by its named creator**, with who did upload it (Development rule 3; new in draft 12: "uploaded", Development's word, where draft 11 said "published").
    - **Its drafts in order.** A specification naming a predecessor (field 8) listed here follows it; a line of drafts starts from one naming no predecessor found here, and is shown oldest first, each numbered by its place, its newest draft heading it. Predecessors are claims (Development rule 25): a draft whose creator differs from its predecessor's is shown as **by another creator**, and two naming the same predecessor are both shown, each saying that another names it. One naming a predecessor not found here says so. *A MIP's predecessor is the MIR or MIP it forks, shown in the MIPs' part (below), never as a line of drafts (new in draft 11, F325).*
    - **MIPs, in a part of their own** (new in draft 11, F325). *A MIP is a proposal toward MOR 2, a successor protocol (F286): at the freeze the MICS and the six MIRs are published, each cloned as a MIP, and "anyone can fork it, if a fork makes sense people will be tempted to work off it. And fork that one" (Nobody, allegedly, F289). Adoption, not authority, sorts the forks; the listing shows them so they can be seen as forks.* After the xtypes and before the other specifications, a display client shows the MIPs it verified (kind 8), in a part of their own, under the words that a MIP is a proposal toward a successor protocol, not a rule of MOR:
      - **By the MIR they fork.** Each MIP is shown under the MIR its predecessor (field 8) leads to, followed back through the MIPs it names as far as found: a MIP forking a MIP stands under that MIP, a MIP forking a MIR directly under the MIR, and a MIP proposing a new layer, naming the MICS document, under the MICS document, shown with its MIPs as a MIR is (new in draft 11, F328, Q10). Each MIR found is shown with its MIPs, a MIR no MIP forks with none. A MIP whose line of predecessors leads to a specification not found here, or found and neither a MIR, the MICS document nor a MIP (the MICS document new in draft 11, F328, Q10), is shown in a group of its own, saying which, by its hash.
      - **How many fork each.** Beside each MIR and each MIP, how many MIPs found name it as their predecessor, directly, and how many stand under it in all; each draft its own specification, counted on its own.
      - **Each MIP** with its name, its creator (as above for every specification), its spec hash, and the code released naming it, as for any specification.
      - **Most forked first,** then by name, among the MIPs under one MIR or MIP; the MIRs in the order of their names.
      *A count of forks is of MIPs published at the relays read, not of agreement with them (a stated cost).*
    - **Code released.** A release (release manifest cMIP) naming a bake of the specification is code released for it. **A release's manifest is read first** (new in draft 10): where it holds field 6, "implements" (release manifest cMIP draft 3), the specifications it implements are the ones whose bakes that field names, and no other; where it holds none, as every release before draft 3, the specifications whose bakes its own bake names among its references, as in draft 9. **By spec hash** (new in draft 11, Development Q7, taken): a release's field 6 is read as release manifest cMIP draft 4 gives it, each entry naming a specification by its spec hash, so the specifications it implements are those whose spec hashes it names, and no other, whichever bake of each was found; the bake an entry gives beside its spec hash is a hint only, never read to match a release to a specification. A release whose manifest holds draft 3's field 6, naming bakes, is not a valid manifest under draft 4 and is shown as not verified, with the reason. A display client shows each, with whether it is by the specification's creator or by another identity, and its name and version label from its manifest, and which way it names the specification (its manifest's "implements", or its bake's references), once its bake is judged valid for its signer's chain and its manifest opens and matches; otherwise as not verified, with the reason. With none found: "no release naming it found at the relays read". *Its files are checked by the release manifest cMIP's verifier, not here.*
    - **Apart from the page, said beside it.** A display client shows a listing apart from the page's styles (as an act, rule 13), and lists beside the page (rule 9), for every listing, each relay named, how many acts it read there, how many public terms, private acts and bakes of specifications, what it could not reach or read, where it stopped, how many extensions and agreements it counted, from how many public terms, from draft 10 how many xtypes it listed and how many public acts of their types it counted, saying private acts are not counted, from draft 11 how many MIPs it listed and under how many MIRs, and how many versions of one text it found, and how many specifications it verified and how many bakes it could not.
    - **Read only.** Nothing in a listing signs, publishes or sends; a display client keeps nothing of it in the visitor's browser, and asks nothing of anyone but the gateway, the relays named, the homes of the identities it checks, and the places a bake names.
14. **Links on the visitor's action.** A link (`a` with `href`) to a path of the same version opens that page through the display client. A link to an `https:` or `mailto:` address opens on the visitor's action, outside the site. Any other link is shown as text. *Client conformance.* A display client SHOULD show where a link leaving the site goes before it is followed.
15. **Pages are designs, never terms.** A page is never terms. Anything signed to be agreed is a text act, shown as plain text in a client that keeps the Text MIR's bound (F102); a page may show the act (rule 13), in the display client's own rendering apart from the page's styles, but never stands in for it. *A stylesheet can hide words and move them; the bound governs text acts and their formats, not a site's pages (decided by Nobody, allegedly, 1 October 2026).*
16. **The title** of a page is its `title` element's text, shown by the display client as the page's title. A page without one is titled by its path.

    16a. **The icon.** A page may name an icon: a `link` whose `rel` includes `icon` and whose `href` names a picture's path of the same version, relative to the page. A display client MAY show that picture as the page's icon, such as on the browser tab, and only as bytes it has checked (rule 8), never from an address; a picture that does not match fails the page, as a stylesheet does. Only the first such `link` counts; any other `link` naming an icon is dropped. *A JPEG has no see-through parts, so an icon is a square picture. The tab belongs to the display client, and the page's own icon reaches it only through the check (decided by Nobody, allegedly, 8 October 2026).*
17. **A file that is not a page** is shown by its kind (rule 4): a picture as itself, a film in the player of rule 12a (played on the visitor's action), whether the site's pages show it or list it, a stylesheet or text as plain text, each with rule 9's line beside it.

## Gateways

A **gateway** serves a site at an address (a domain over HTTPS, an onion address) to browsers. It is two things at once: a server, which fetches a version from relays, checks it, and serves its files; and a display client, which runs in the visitor's browser.

18. **The gateway checks before it serves.** A gateway serves a version only once it has checked it by "What counts as a version", every file included. It serves the version its operator's settings lead to (rule 23); it never serves a version that did not verify, nor a file that did not match.
19. **Never a page alone.** At every address of the site, a gateway serves its display client, which fetches the file it is asked for and shows it by "Showing a site". A gateway serves a site's files themselves only as bytes for its display client to check, never as a document a browser would display on its own. *So no page of the site ever reaches a visitor's screen without passing the check.*
20. **The display client is MOR's released code.** The display client a gateway serves is MOR's own display client, as released: a release of software, published and verifiable by the release manifest cMIP, and the same for every site the gateway serves; a gateway SHOULD name the release it runs. *A site carries no code of its own (rule 11), so the code that checks is not the site's to choose, and it can be compared with its release by anyone, from anywhere (decided by Nobody, allegedly, 1 October 2026: "to keep it all in check").*

    20a. **Its built files are in the release, and rebuild the same.** The release carries the display client's built files, exactly the bytes a gateway serves, and the versions of the tools that built them. Its build is reproducible: built from the release's source with those tool versions, on any machine and in any folder, it gives the same bytes; nothing of the build machine (its folder names) is written into them. *So comparing a gateway with the release needs no build at all, and whoever doubts the built files can rebuild them and compare (decided by Nobody, allegedly, 1 October 2026: both).*
21. **What the gateway's settings say is a hint.** The version, the expected identity, the owner's name, how the version was chosen, the relays and, from draft 7, the homes that take a visitor's one-time identity (rule 13b) a gateway hands its display client are the operator's word: the display client checks the version against the relays and shows the signer's fingerprint, so that a visitor who knows the fingerprint can tell.
22. **A gateway carries the sites its operator chose.** A gateway serves only the sites its operator lists, each at the addresses the operator gives it (a domain, an onion address); at any other address it serves no site. *Carrying a site is the operator's choice, as keeping acts is a relay's policy. An owner a gateway refuses carries their site elsewhere: on another gateway, on their own, or with no gateway at all, since every byte is on relays (decided by Nobody, allegedly, 1 October 2026).*
23. **Which version, set per site.** For each site it carries, the gateway's settings say which version it serves:
    - **latest:** the latest version from a version the settings name ("Later versions"), looked for again from time to time. This is the default, and the rule for a site someone else uploads: *when their content changes is the owner's call, not the operator's;*
    - **pinned:** the version the settings name, and no other. *For the operator's own sites, set as the operator wishes: a pinned version guards against a stolen key, since a thief's new version is not served.*

    Any other arrangement between an operator and an owner, such as pinning a version of the owner's site, is a deal between them, outside this cMIP. Following, the gateway serves the latest version whose files all arrive and match; failing that, the one before it, and so on back to the version named. Where following stops at a fork (rule C), the gateway serves the version before it, and its operator is told.
24. **The display client looks for later versions.** Whatever version it is shown, and however the gateway chose it, a display client looks for later versions from it ("Later versions"), from the visitor's device, and says, beside the file it shows (rule 9), when a newer version exists, naming it, and when following stopped at a fork. *Client conformance.* It does so after showing the file, never holding it back. *A gateway pinned to an old version, or slow to follow, cannot keep a visitor from knowing that the owner has said more since.*

## Verifying

A verifier needs only a version's id, the identity expected, and one place to look.

1. Fetch P; recompute its id; open it with the key on its outside; check its type and media spec.
2. Resolve P's uploader's identity chain from its homes (relay transport cMIP, "Homes"), starting from its genesis; judge P's standing. **New in draft 12:** where S is a collective, resolve S's chain too, read its founding agreement and the decisions P cites, and ask Agreements whether P counts for S (rule 3); draft 11's "look for a withdrawal of P by S" is gone.
3. Fetch the manifest's locked bytes; check their SHA-256, open them, check the work hash and size; decode the manifest strictly.
4. For each file to be shown: take its bytes from wherever they come (a gateway, a relay, a disk), and check their work hash and size; or fetch its locked bytes, check their SHA-256, open them, and check the work hash and size.

The version verifies only if steps 1 to 3 pass; a file is shown only if step 4 passes for it.

## Stated costs

- **A hostile gateway (roadmap step 10a).** A browser trusts whoever answers at a domain over HTTPS, and runs whatever code they serve. A gateway that is hostile, or taken over, can serve a display client that lies: one that shows altered pages as verified, or no check at all. No page can prove the code that checks it. *What this cMIP settles, and how:*
  - *Every byte of a site is signed and named by hash, on relays, so it can be checked with no gateway at all: by any display client the visitor trusts, such as the command-line verifier, or a gateway the visitor runs (anyone can run one).*
  - *A gateway cannot pass off altered pages while serving the honest display client: the display client checks every file it is served against the signed manifest, in the visitor's browser, and shows a mismatch as failing (rule 10).*
  - *To lie, a gateway must alter the display client itself. The display client is the same for every site, is not minified, and is a signed release (rule 20), so what a gateway serves can be compared with the release from anywhere else, file by file (the command-line check, `mor-site check`, does it).*
  - *What remains: a gateway that serves altered code only to some visitors, and the honest code to whoever checks, is caught only by the visitors who check from their own device. A visitor who cannot check trusts the gateway, as with any website; the check makes a lie detectable, not impossible. Serving the site at a second address (an onion address) does not change this: each address is a gateway, trusted the same way.*
- **Pages without programs.** No script runs in a page, so a site cannot hold forms or anything interactive of its own; it links to clients for that (such as the web reader), or, from draft 7, names identities a visitor may write to in a writing box the display client draws (rule 13b): the code that signs is MOR's, not the site's.
- **A visitor's note costs a genesis** (draft 7): every note leaves a one-time identity's genesis at the homes that take it, and no reply can reach its writer; the box says so. How many a home accepts is its policy.
- **A public note is public before it is answered** (draft 7): left unsealed in an inbox, it is readable by anyone who holds it, answered or not; the feed shows only what is answered.
- **A pick shown is the picker's signed word** (draft 7): it says who picked a note, not that the agent kept its terms, which the feed does not judge; and the owner holds the agent's key (nudge cMIP, item 7c).
- **A note is found only where the feed looks** (draft 7): until a reference names its signer (F272), at the places asked for the feed; a note left only at an inbox no one asks is not shown beside its answer.
- **No clock, and versions found only where one looks.** MOR has no clock: "latest" means the end of the line of versions naming each other, as found at the places asked. A later version on a relay nobody asks is not found. A gateway following a site moves to a new version only when it looks again, so it can lag; the visitor's display client looks for itself (rule 24).
- **A stolen key moves the gateways that follow.** A thief holding the owner's signing key (for a collective's site, a member's, where the rule reaching the site lets one member act alone; new in draft 12) can upload a version naming the latest one, and every gateway following that site serves it, until the owner rotates (which voids the thief's acts; new in draft 12: draft 11's "or withdraws it" is gone, a bake being never withdrawn). A version the owner also publishes after the same one makes a fork, and following stops before it. Pinning guards against this, at the cost of serving only what the operator names (rule 23). *The same window as for any act signed with a stolen signing key (Identity).*
- **Relays learn what is fetched.** The visitor's browser fetches the version, its signer's chain and the signer's bakes (to look for later versions) from relays, which learn that someone opened the site; a gateway learns which pages.
- **Reproducible only with the same tools.** The display client's built files rebuild the same only with the tool versions the release names (the Rust compiler, wasm-bindgen, the bundler); other versions give other bytes, which prove nothing either way.
- **A film is fetched whole before it plays** (draft 4). Its work hash is over the whole file, so nothing plays until every byte has arrived and been checked: a film of 23 MB takes seconds on a good connection, longer on a phone's. Its size is bounded by one media object (rule 6a). *The media cMIP serving one object in parts from many homes, each part with its own hash, is what lets a longer film start sooner and grow beyond 64 MiB; not written yet (F243).*
- **Each listed film's poster is fetched with the page** (draft 5), whether or not the film is opened: the price of checking every picture a page shows before showing the page (rule 8). A JPEG poster is small; its film is fetched only when asked for.
- **A display client written for draft 4 shows a listed film's label as plain words,** and no button: the film is still in the version, at its own address (rule 17), but nothing on the page plays it. *Gateways are updated to the display client released with draft 5 before a version listing films is served.*
- **A gateway holds and serves every film whole.** A gateway checks every file of a version before serving it (rule 18), films included, so it fetches each film from relays and keeps it, whether or not anyone plays it.
- **A feed is not in time order** (draft 6). Signed order shows only what was signed after what: two posts no act links are listed by the page's order of identities, not by when they were written, and the feed says so. *Decided by Nobody, allegedly: replies and other interactions between the identities named order their posts.* From draft 8, a page may name a clock to order them by (below).
- **A clock's order is its operator's word** (draft 8). A timestamp clock's stamps prove only that its identity signed them: a clock that lies, or runs wrong, orders the feed wrongly, and the feed cannot tell; whoever holds its signing key can stamp anything at any time. Signed order still holds, so a reply never comes before what it answers. *Acceptable for a feed, which protects nothing (Nobody, allegedly); never for a payment or a lock change.*
- **A post is placed when the clock held it** (draft 8), not when it was signed: one the clock was given or found late is shown as newer than it is, and one it has not stamped yet comes first, said as not stamped.
- **A clock costs a lookup and its stamps on every visit** (draft 8): the clock's homes and outbox relays learn that someone opened the feed, as the identities' do, and its stamps are fetched whole; a clock stamping a great deal makes a feed slower to open.
- **A display client written for draft 7 ignores the clock** (draft 8) and shows the feed in signed order, saying it is not a time.
- **A feed tells the homes and relays who reads it** (draft 6). The visitor's browser looks up every identity named at its homes and asks its outbox relays for its posts, so each learns that someone opened the feed. Each identity named costs a lookup on every visit: a feed naming many identities is slow on a phone, and a window onto many would need paging, not written.
- **A post where a browser cannot reach is not shown** (draft 6): an outbox only at an onion address is not tried from a browser, and the line beside the page says so.
- **A display client written for draft 5 shows a feed's names as plain words,** and no post. *Gateways are updated to the display client released with draft 6 before a version holding a feed is served.*
- **Private agreements are not counted** (draft 9, F288). An agreement whose terms are sealed to its parties cannot be read, so an extension named only in private agreements does not appear, and counts are of public agreements only; the listing says so. Agreements on relays it does not read are not counted either. *How often an extension is named is a lower bound, never a measure of use.*
- **A count is of signed terms, not of use** (draft 9). An agreement counts once its parties signed it; whether it is still in force, or ever used the extension, is not read. Anyone can sign many agreements naming one cMIP to raise its count: the counts show what was signed, and each links to the terms counted, so a visitor can look.
- **A listing reads whole relays** (draft 9). It asks each relay named for everything it serves, so a large relay makes a listing slow to open, on a phone above all, and the display client stops at 5,000 acts a relay, saying so; a listing service reading many relays ahead of time is another listing, competing like any (Development rule 17). Each relay, and the homes of every signer checked, learns that someone opened the listing.
- **A listing shows only what its relays hold** (draft 9). A specification published elsewhere is not listed, and a predecessor or a release found nowhere it reads is not followed. *Silence proves nothing.*
- **What a specification says of itself is its creator's word** (draft 9). Its kind, tasks, layers and field 12 are shown as its fields say; whether its rules do what it says is for whoever adopts it. A Module's layer comes from the cMIP it names, when listed.
- **"Code released" is a release's word** (draft 9). A release naming a specification says nothing checked about whether its code implements it; the listing shows who released it, never that the code is right, and does not check the release's files. *From draft 10 the word is signed in the manifest's "implements", so it says what the release claims to implement; still a claim.*
- **Private acts are not counted** (draft 10). Which specification a private act belongs to cannot be read from outside, so an xtype used only in private shows no use, and every count is of public acts on the relays read. *A count of an xtype's use is a lower bound, never a measure of it.*
- **A count of acts is of acts signed, not of worth** (draft 10). Anyone can sign many acts of an xtype's types to raise its count; the count shows what was signed and checked, and each act is valid for a signer's chain, never that anyone else relies on it.
- **A count of forks is of MIPs published, not of agreement** (new in draft 11, F325). How many MIPs fork a MIR counts the MIPs verified at the relays read; anyone can publish many forks to raise a count, and a fork published elsewhere is not counted. *Adoption sorts the forks (F289); the count shows what was published, and each MIP counted is listed, so a visitor can look.*
- **Versions of one text are shown, not merged** (new in draft 11, F322). An agreement, an act or a release names one spec hash; counts and code released are shown per version, so a text published with different optional fields splits its counts among its versions, said beside them.
- **A release under draft 3's "implements" is not verified** (new in draft 11, Development Q7, taken). The release manifest cMIP's drafts 3 and 4 read field 6 differently and share one test value until step 17; a release naming field 6 under draft 3 is shown as not verified, with the reason. *Releases are made under draft 4 before a listing reading it is served.*
- **A display client written for draft 10 shows a MIP, the MICS document and a test suite by their kind numbers** (new in draft 11), as kinds it does not know, and a MIP's predecessor as a line of drafts. *Gateways are updated to the display client released with draft 11 before a listing is served once MIPs are published.*
- **A display client written for draft 8 shows a listing's relay names as plain words,** and reads nothing. *Gateways are updated to the display client released with draft 9 before a version holding a listing is served.*
- **Pages are not bound like text acts** (rule 15): a page can hide or move words with its stylesheet. Terms belong in text acts.

## Reasoning

- **Like a release.** *A site is files named by hash under a signed list, exactly as a release of the code is (release manifest cMIP). The same file entries, the same publishing order, the same reuse of unchanged files: one way to name files on MOR, not two.*
- **The check belongs to the visitor's browser, not to the gateway's word.** *A gateway that checked and said "trust me" would add nothing a plain web server does not. So the gateway checks for its own sake (it never serves a broken site), and the visitor's browser checks again for the visitor's.*
- **No code in a site.** *If a site could carry scripts, its own code could paint a fake "verified" or fetch something unchecked. Without them, what a visitor sees is what was signed, shown by a display client that is the same everywhere.*
- **The display client is MOR's code, released.** *The one thing a visitor must trust is then one small program, the same for every site, signed as a release: something that can be checked once, by many, rather than every site's code by every visitor. Its built files are in the release and rebuild the same, so checking it needs no trust in whoever built it.*
- **Per site, by whose site it is.** *Timing someone else's content is not a gateway's business, so by default it follows; its own site is its own business. Either way the visitor is told when there is more.*
- **Following by names, not by time.** *Versions name the one before, as routes acts do (Identity, "Routes"), and a fork is shown, never resolved by a guess.*
- **Forks seen as forks** (new in draft 11, F325). *A MIP published as a MIR would be a MIR to every reader, distinguishable only by not being one of the six, and would lose its creator; under a kind of its own, with its creator and the MIR it forks, F289's "fork that makes sense" can be seen by how many work from it.*
- **A listing decides nothing** (draft 9). *Specifications are named by their hashes, so no listing can give or take a name; this one shows what it found and how it checked it, and says that it is one among any.*
- **Acts stay acts.** *The site's owner points at acts; they are not copied into the site, so each keeps its own signer and standing, and is judged on its own.*
