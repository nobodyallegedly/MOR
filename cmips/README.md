# Founding cMIPs

Community specifications for the tasks the MIPs hand out, and for what no task foresaw. Not core: each is named by its hash, frozen at publication, and competes with any other cMIP for the same job.

Planned for MOR V1:

| cMIP | What it does |
| --- | --- |
| Relay transport (`cmip-relay-transport-draft-2.md`, draft 2, approved by Nobody, allegedly; `cmip-relay-transport-draft-3.md`, draft 3 adding the delivery record, F184, not yet approved) | How a client publishes, fetches and follows acts, delivers to an inbox, and asks a home for a receipt; in draft 3, how a relay signs a delivery record that counts as evidence once the payer's claim acknowledges it. The core deliberately leaves this open. |
| Release manifest (`cmip-release-manifest-draft-1.md`, draft 1, approved by Nobody, allegedly; `cmip-release-manifest-draft-2.md`, draft 2 for Agreements draft 7, not yet approved) | How the collective that governs the code publishes a release, file by file, with its members' visible signatures, and how anyone verifies it (roadmap step 5a). No task: a new kind of thing, named as an extension. |
| Payment (`cmip-payment-draft-2.md`, draft 2, experimental, not approved) | Task 6 (payment, F112): how rail Modules plug in, the payment commitment a rail carries, the proof a receipt or claim carries, how they are verified, and what a payer does when the vault leaves nowhere to pay (roadmap step 12). Code: `payment/` (crate `mor-payment`). |
| Anchoring (`cmip-anchoring-draft-3.md`, draft 3, experimental, not approved; drafts 1 and 2 kept, superseded) | The Envelopes' anchoring task (F173): one cMIP, each clock a Module under it (F202); the point on a block-based clock is the block, and an anchor may place a commitment naming its act (F201); a clock's data supplied by the client (F204). Draft 2 (roadmap step 14a): the batch (domain-separated, one proof per leaf), the pooled anchoring service paid per hash (offer with priced urgency tiers, tickets, signed publications), omission and default as provable from the service's own acts, each a refund, and what the service learns. First clock: `modules/module-bitcoin-clock-draft-2.md`. Code: `anchoring/` (crate `mor-anchoring`). |
| Long-form text format (`cmip-long-form-draft-1.md`, draft 1, approved by Nobody, allegedly) | Task 4 (text format): a strict subset of Markdown on top of canonical text, hiding only its declared markup, in its declared positions (F149), adding nothing and keeping the order of the bytes (roadmap step 8). |
| Website (`cmip-website-draft-4.md`, draft 4, **not yet approved**; drafts 2 and 3 kept beside it) | A site as a signed manifest naming each page and file by hash, published on relays; a gateway serving the sites its operator chose at their addresses, each at the version its operator sets (by default the publisher's latest), with MOR's released display client checking every page in the visitor's browser; a page's icon from one of the site's own pictures (draft 3); a film of the same version, played on the visitor's action in the display client's own player, checked by the video Module (draft 4, F243); the hostile gateway as a stated cost (roadmap step 10a). No task: a new kind of thing. |
| Live media (`cmip-live-media-draft-1.md`, draft 1, experimental, not approved) | The stream rules F230 to F232 placed in the core, moved here by F237 keeping their content: a stream named by its opening act (an announcement, to be renamed vow, or a first segment), only the opener's segments, a closing by the opener naming the last segment, forks shown, the recording's work hash computed from the segments in order, offers naming the stream with their words, the buyer's check; F230's cost as F237 corrects it. No code yet. |

Media types such as JPEG are Modules and live in `modules/`.
